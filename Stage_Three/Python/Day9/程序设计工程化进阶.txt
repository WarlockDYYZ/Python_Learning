一、ETL 入库脚本：多源抽取、清洗与批量入库

    1.1 ETL 架构设计原则
        针对「用户行为分析系统」的业务场景，采用增量抽取 + 批量加载 + 断点续传的生产级架构，核心流程：
            1. 抽取（Extract）：从两类数据源拉取数据：
                - 业务关系型数据库源：MySQL（存储用户基础行为）、PostgreSQL（存储用户标签数据）
                - 第三方 / 内部 API 源：用户行为上报 API、用户画像标签 API
            2. 清洗（Transform）：校验数据格式、脱敏敏感字段、去重、补全缺失字段、统一字段映射
            3. 加载（Load）：批量 / 增量写入分析库的user_behaviors、user_tags表，保障入库性能与数据一致性


    1.2 多数据库源连接（生产级方案）
    
        1.2.1 通用连接池封装（兼容 MySQL/PostgreSQL）
            禁止使用裸数据库连接，基于 SQLAlchemy 封装支持同步 / 异步的多源连接池，复用项目原有配置体系，从.env读取数据源配置，避免硬编码：
                db_pool.py

                多数据源数据库连接池管理器，专门服务于 ETL（数据抽取、转换、加载）场景。它通过字典结构管理多个数据库源，并区分同步与异步两种模式，
                以适配不同的数据处理需求。
                1. 核心设计模式
                    - 多数据源字典管理
                        sync_pools / async_pools: 使用 Dict[str, sessionmaker] 结构，以 source_name 作为键。
                        优势: 允许 ETL 任务同时连接多个不同的数据库（如 MySQL、PostgreSQL、Oracle），通过名称动态获取对应的会话工厂，避免了硬编码。
                    - 同步/异步双模支持
                        同步模式 (init_sync_pool): 使用 create_engine + Session，适用于传统阻塞式 ETL 脚本或全量数据迁移。
                        异步模式 (init_async_pool): 使用 create_async_engine + AsyncSession，适用于高并发增量同步或异步任务调度框架
                                （如 FastAPI + Celery/AsyncIO）。
                2.  关键连接池配置解析
                    参数	                    值	            作用与 ETL 场景意义
                    pool_pre_ping	        True	        断连检测: 每次从池中取出连接前发送轻量 SQL 检测有效性。ETL 任务通常运行时间长，
                                                            此配置可避免因数据库超时断开导致的任务失败。
                    pool_size	            10	            常驻连接数: 池中保持的最小连接数。10 是一个平衡值，既避免频繁创建/销毁连接的开销，
                                                            又不会过度占用数据库资源。
                    max_overflow	        20	            弹性扩容: 当 10 个连接被占满时，最多额外创建 20 个临时连接。
                                                            应对 ETL 任务中的并发查询峰值，防止连接耗尽导致任务阻塞。
                    echo	                settings.DEBUG	SQL 日志: 仅在调试模式下打印 SQL 语句。生产环境关闭可减少 I/O 开销，提升 ETL 性能。
                    autocommit	            False	        事务安全: 禁用自动提交，确保 ETL 操作在显式事务中执行，支持回滚，保证数据一致性。
                    class_=AsyncSession	    -	            异步绑定: 明确指定异步会话类，使 get_async_session() 返回的对象支持
                                                            async with 和 await 语法。
                3. ETL 场景适配说明
                    - 全量同步 → 同步会话
                        get_sync_session(): 返回标准 Session 对象。
                        适用场景: 大批量数据一次性迁移、历史数据初始化、不依赖异步框架的定时脚本。
                        使用示例:
                            session = get_sync_session("source_mysql")
                            try:
                                result = session.execute(text("SELECT * FROM large_table"))
                                session.commit()
                            finally:
                                session.close()  # 必须手动关闭，归还连接到池
                    - 增量同步 → 异步会话
                        get_async_session(): 返回 AsyncSession 对象。
                        适用场景: 实时数据流处理、高频小批量更新、与异步 Web 框架集成。
                        使用示例:
                            async with get_async_session("source_pg") as session:
                                result = await session.execute(select(User).where(User.updated_at > last_sync_time))
                                await session.commit()
                            # 异步上下文管理器自动关闭会话

                提供 close_pool() 方法：在应用优雅退出或热重载时，应调用 engine.dispose() 释放所有连接，避免资源泄漏。
                从 settings 中读取 pool_size 和 max_overflow，允许不同数据源根据负载特性配置不同的池大小。
                提供上下文管理器封装：管理会话生命周期。

                4. 数据库会话获取函数
                    是连接池管理器对外暴露的核心接口，负责将底层的“连接池（sessionmaker）”转化为业务代码可以直接使用的“数据库会话（Session）”。
                    1. get_sync_session(source_name: str) -> Session
                        函数作用
                            - 根据传入的数据源名称（如 "source_mysql"），从同步连接池字典 sync_pools 中获取对应的 sessionmaker 工厂，
                                并立即实例化返回一个标准的同步 Session 对象。
                        核心特性
                            - 非上下文管理器：这个函数直接返回一个 Session 实例，不会自动帮你管理事务的提交（commit）或回滚（rollback），
                                也不会在函数结束时自动关闭连接。
                            - ETL 场景适配：专为传统的全量数据迁移、大批量历史数据初始化等阻塞式任务设计。
                        修改：添加自动关闭机制
                                session.commit()  # 手动提交
                            except Exception as e:
                                session.rollback()  # 异常时手动回滚
                                raise
                            finally:
                                session.close()  # 必须关闭，将连接归还给连接池

                    2. get_async_session(source_name: str) -> AsyncSession
                        函数作用
                            - 根据数据源名称，从异步连接池字典 async_pools 中获取对应的异步 sessionmaker 工厂，
                                    并立即实例化返回一个 AsyncSession 对象。
                        核心特性
                            - 支持异步上下文管理器：虽然函数本身只是返回一个实例，但 SQLAlchemy 的 AsyncSession 原生支持 async with 语法。
                            - ETL 场景适配：专为增量同步、实时数据流处理、高并发小批量更新等场景设计。
                        修改：
                            添加上下文管理器

                补充：
                    - 建立数据库连接时使用的的参数较详解
                        参数	                    值	            作用与 ETL 场景意义
                        pool_pre_ping	        True	        断连检测：每次从池中取出连接前，发送一条轻量级 SQL（如 SELECT 1）
                                                                检测连接是否有效。
                                                                ETL 任务通常运行时间长，数据库端可能因超时主动断开空闲连接。
                                                                此配置能避免任务因使用“死连接”而失败，是长时任务的生命线。
                        pool_size	            10	            常驻连接数：连接池中保持的最小连接数。
                                                                10 是一个平衡值，既避免了频繁创建/销毁连接的开销，又不会过度占用数据库资源。
                                                                对于 ETL 任务，这代表了常规同步/增量处理时的基础并发能力。
                        max_overflow	        20	            弹性扩容上限：当 pool_size 中的连接被全部占用时，允许额外创建的临时连接数。
                                                                在 ETL 任务遇到数据量突增或并发查询峰值时，这 20 个额外连接能防止任务因
                                                                “连接耗尽”而阻塞或失败。
                                                                峰值总连接数为 pool_size + max_overflow = 30。
                        echo	                settings.DEBUG	SQL 日志开关：仅在调试模式下打印所有生成的 SQL 语句。
                                                                在生产环境关闭此选项可显著减少 I/O 开销和日志体积，提升 ETL 性能。
                                                                调试时开启则便于排查慢查询和逻辑错误。
                        autocommit	            False	        事务安全：禁用自动提交，确保所有数据库操作都在显式事务中执行。
                                                                这对于 ETL 至关重要，它保证了数据操作的原子性，当任务失败时可以通过
                                                                rollback() 回滚，避免产生脏数据。
                        class_=AsyncSession	    -	            异步会话绑定：明确指定异步会话类。
                                                                这确保了 get_async_session() 返回的对象原生支持 async with 上下文管理和
                                                                await 语法，是异步数据库操作的基础。

                    - 关于 pool_pre_ping
                        虽然 pool_pre_ping 对同步连接池是标准且推荐的配置，但在异步连接池中需要特别注意：
                            - 驱动兼容性：部分异步数据库驱动（如 asyncpg）对 pool_pre_ping 的支持有限或实现方式不同。
                            - 潜在风险：如果使用的异步驱动不完全兼容该参数，可能会在初始化或运行时抛出异常，导致异步连接池无法正常工作。
                            - 建议：在部署前，务必查阅你所使用的具体异步驱动（如 asyncpg, aiomysql 等）的官方文档，
                                确认其对 pool_pre_ping 的支持情况。
                                如果存在兼容性问题，可能需要移除该参数或寻找驱动特定的替代方案来实现连接有效性检测。

                    - 关于连接处创建
                        连接池的惰性创建：SQLAlchemy 的连接池（无论是同步还是异步）默认都不会“预先创建”连接。池中的连接是在首次被请求时才创建的。
                                因此，pool_size=10 并不意味着应用启动时就会建立 10 个数据库连接，而是指池最多会维持 10 个空闲连接。
                        参数调优：pool_size 和 max_overflow 的值不应是固定的。
                                在生产环境中，应根据数据库服务器的最大连接数限制（如 MySQL 默认的 151）以及 ETL 任务的实际并发负载进行动态调整，
                                确保 pool_size + max_overflow 的总和留有安全余量，避免耗尽数据库连接资源。

                    - 关于异步会话中和 finally 块
                        异步会话（AsyncSession）自身已经实现了异步上下文管理器协议（即内置了 __aenter__ 和 __aexit__ 方法）。
                        1. 底层机制：AsyncSession 自带了“清理逻辑”
                            在 SQLAlchemy 的异步实现中，当你使用 async with session: 时，SQLAlchemy 会在后台自动处理资源的释放。
                            它的内部逻辑大致等价于：
                                async def __aexit__(self, exc_type, exc_val, exc_tb):
                                    # 无论是否发生异常，退出时都会自动关闭会话
                                    await self.close()
                            因此，在 get_async_session_ctx 中，我们直接使用了 async with get_async_session(source_name) as session:，
                            这就已经确保了 session 一定会被安全关闭，无需我们再画蛇添足地加一层 finally。
                        2. 代码结构：try...except 与 async with 的嵌套关系
                            让我们对比一下同步和异步的写法：
                            - 同步会话（需要手动 finally）：
                                因为普通的 Session 不支持 with 语法，我们必须手动管理：
                                    session = get_sync_session(source_name)
                                    try:
                                        yield session
                                        session.commit()
                                    except Exception:
                                        session.rollback()
                                        raise
                                    finally:
                                        session.close()  # 必须手动关闭
                            - 异步会话（不需要手动 finally）：
                                因为 AsyncSession 支持 async with，清理工作交给了它自己：
                                    async with get_async_session(source_name) as session:
                                        try:
                                            yield session
                                            await session.commit()
                                        except Exception:
                                            await session.rollback()
                                            raise
                                    # 这里的 async with 代码块结束时，SQLAlchemy 会自动调用 await session.close()

            在app/etl/__init__.py中加载多源库连接，同时遵守最小权限原则：ETL 数据库账号仅赋予SELECT权限，目标分析库账号仅赋予INSERT/UPDATE权限：
                __init__.py

                1. ETL 系统的启动引导（Bootstrap）代码
                    负责在应用启动时，根据配置信息集中初始化所有的数据库连接池。
                    通过调用 db_pool.py 中定义的函数，将数据库配置与连接池管理进行解耦。
                    规划 ETL 系统的数据流向：
                        1. 业务 MySQL 源库 (biz_mysql)
                            作用：作为 ETL 的数据源（Source）。
                            配置：同时初始化了同步和异步连接池。这意味着该库既支持传统的全量数据拉取，也支持高并发的增量数据捕获（如基于 CDC 的实时同步）。
                        2. PostgreSQL 用户标签源库 (user_pg)
                            作用：另一个异构数据源。
                            配置：同样配置了双模连接池。在实际业务中，用户标签数据可能存储在专门的 NoSQL 或分析型数据库中，ETL 需要跨库拉取这些数据。
                        3. 目标分析库 (target_mysql)
                            作用：作为 ETL 的数据目的地（Sink/Target）。
                            配置：复用了项目主库的配置（settings.SQLALCHEMY_DATABASE_URL）。
                                这通常意味着清洗、转换后的数据最终会被写入到业务系统的核心分析库中，供下游 BI 报表或算法模型使用。

                2. “最小权限原则”
                    ETL 架构和数据库安全管理中，最小权限原则（Principle of Least Privilege, PoLP） 是一个核心的安全基石。
                    核心定义：任何用户、程序或进程（在这里指 ETL 程序）只应被授予完成其当前任务所必需的最少权限，且仅在最短的必要时间内拥有这些权限。
                    在 ETL 数据库连接中的具体体现：
                        1. 源库（Source）权限控制：
                            ETL 程序连接 biz_mysql 和 user_pg 的目的是读取数据。
                            正确做法：为 ETL 创建专用的数据库账号，仅授予 SELECT 权限。
                            错误做法：复用业务系统的管理员账号，或者授予 DELETE、DROP、UPDATE 权限。
                                    一旦 ETL 代码出现 Bug（例如错误的 SQL 拼接），可能会误删源库数据，造成灾难性后果。
                        2. 目标库（Target）权限控制：
                            ETL 程序连接 target_mysql 的目的是写入数据。
                            正确做法：仅授予 INSERT、UPDATE 以及必要的 CREATE TABLE（如果 ETL 需要动态建表）权限。
                            错误做法：授予 DROP 或 ALTER 权限，防止 ETL 误删目标库的核心表结构。
                        3. 隔离性：
                            源库和目标库应使用完全不同的数据库账号。
                            即使 ETL 程序被黑客攻破，攻击者也无法利用同一个账号既窃取源数据，又篡改目标数据。
                    总结：
                        在架构上做到数据源和目标库的清晰分离。
                        在实际部署时，务必确保 settings 中配置的各个数据库 URL，使用的是严格遵循“最小权限原则”的专属账号，
                            这是保障 ETL 系统稳定和数据安全的第一道防线。


            补充：
                ETL 系统
                    ETL 是 Extract（抽取）、Transform（转换）、Load（加载） 三个英文单词的首字母缩写。它是现代数据架构和数据工程的核心基石。
                    简单来说，ETL 就像是数据世界的“中央厨房”：
                        它负责把分散在各地的“生鲜食材”（原始数据）收集起来，经过清洗、切配和烹饪（加工处理），最后端上餐桌或存入冷库（数据仓库/分析库），
                        供“食客”（BI报表、算法模型、业务系统）享用。

                    可以将 ETL 系统拆解为三个核心阶段：
                        1. Extract（抽取）：把数据搬过来
                            - 动作：从各种异构的数据源中读取数据。这些数据源可能是关系型数据库（如代码中的 biz_mysql、user_pg）、日志文件、
                                    API 接口或消息队列。
                            - 策略：
                                全量抽取：每次把整张表的数据全部拉取一遍（适合数据量小、变化不频繁的场景，对应代码中的同步会话）。
                                增量抽取：只拉取自上次同步以来新增或修改的数据（适合海量数据、实时性要求高的场景，对应代码中的异步会话）。
                        2. Transform（转换）：把数据洗干净
                            这是 ETL 中最复杂、最耗时的一步。原始数据通常是“脏乱差”的，不能直接使用。
                            - 清洗：去除重复数据、处理空值（NULL）、纠正错误格式（例如把日期 2026-08-05 统一转换为时间戳）。
                            - 关联与聚合：将多张表的数据拼接在一起（如将“用户表”和“订单表”通过 User_ID 关联），或者进行汇总计算
                                    （如计算每个用户的总消费金额）。
                            - 脱敏与合规：对敏感数据（如手机号、身份证、密码）进行加密或掩码处理，确保符合隐私法规。
                        3. Load（加载）：把数据存起来
                            - 动作：将转换后的高质量数据写入到目标存储系统中。
                            - 目标：通常是数据仓库（Data Warehouse）、数据湖（Data Lake）或专门的分析型数据库（如你代码中的 target_mysql）。
                            - 策略：支持全量覆盖，也支持增量追加（Append）或更新（Upsert）。
                        从 ETL 到 ELT

                    在大数据和云原生时代，ETL 正在向 ELT 演进。
                        传统 ETL：在数据加载到目标库之前进行转换（因为目标库算力弱）。
                        现代 ELT：先把原始数据全部加载（Load）到强大的云数据仓库（如 Snowflake, ClickHouse）中，
                                然后再利用目标库强大的算力进行转换（Transform）。
                                这种方式更灵活，且支持随时回溯原始数据。

                    总结：
                        ETL 系统就是企业数据的“搬运工”和“加工厂”。
                        之前编写的 Python 代码，正是系统中负责数据搬运（连接池管理）和数据加载（会话控制）的底层基础设施。

                讲解：
                    - __init__
                        Python 中，__init__ 是一个特殊方法（Magic Method / Dunder Method），通常被称为构造方法或初始化方法。
                        作用是：当创建一个类的新实例（对象）时，Python 会自动调用这个方法，用来给这个新对象设置初始状态或属性。
                        1. 代码实例解析
                            在外部代码中执行 client = ETLApiClient("https://api.com", "my_ak", "my_sk") 时，Python 在后台做了两件事：
                                a. 创建对象：在内存中开辟一块空间，创建一个 ETLApiClient 的空对象。
                                b. 自动调用 __init__：把 "https://api.com", "my_ak", "my_sk" 这三个参数传递给 __init__ 方法。
                                c. 绑定属性：通过 self.xxx = xxx，将这些配置绑定到了这个特定的对象上，同时顺手初始化了一个 HTTP 客户端。
                        2. self 到底是什么？
                            self 就是对象自己。
                                - 当调用 client = ETLApiClient(...) 时，Python 会自动把刚刚创建的那个 client 对象作为第一个参数传给 __init__。
                        3. __init__ 的常见误区
                            - 它不是创建对象的函数：真正在内存中创建对象的是 __new__ 方法。__init__ 只是在对象创建之后，对其进行初始化。
                            - 它不需要返回值：__init__ 只能返回 None。如果你试图 return 一个具体的值，Python 会直接报错。
                            - 它不是必须的：如果你的类不需要任何初始属性，完全可以不写 __init__，Python 会提供一个默认的（什么都不做的）初始化方法。

                        ETL 系统中，__init__ 承担了“环境准备”的重任。
                        无论是数据库连接池（init_sync_pool 中配置引擎参数），还是 API 客户端（配置 AK/SK 和超时时间），__init__ 确保了：
                            只要这个对象被创建出来，它就是完全配置好、随时可以投入工作的。
                        这避免了在每次调用业务方法时都要重复检查“配置有没有传”、“连接有没有建”，极大地提升了代码的健壮性和可读性。

                    - 签名生成函数
                        _generate_signature 函数是 ETL 客户端与第三方 API 进行安全通信的“防伪印章”。
                        在开放 API 架构中，为了防止请求在传输过程中被篡改，服务端通常会要求客户端提供一个签名。

                        核心安全机制拆解，防御了网络攻击中的三大经典威胁：
                            1. 防篡改（Integrity）
                                原理：SHA256 是一种单向散列函数，具有“雪崩效应”。
                                    如果黑客在传输过程中修改了任何一个参数（例如把 amount=100 改成了 amount=1000），重新计算出的哈希值将发生变化。
                                结果：服务端用同样的规则重新计算签名，发现与客户端传来的 sign 不一致，直接拒绝请求。
                            2. 防伪造（Authentication）
                                原理：拼接字符串的最后一步是加入 sk。
                                    因为 sk 只有编程者和第三方服务器知道，黑客即使抓包看到了请求参数，由于没有 sk，也无法伪造出合法的签名。
                            3. 防重放攻击（Anti-Replay）
                                原理：虽然这个函数本身没有体现，但在 request 方法中注入了 timestamp（时间戳）。
                                结果：每次请求的参数都不同，生成的签名也不同。
                                    黑客如果录制了你的请求，过了一分钟再发送给服务器，服务端发现时间戳已过期，会直接丢弃该请求。
                        补充：
                            为什么必须排序？
                                字典（Dictionary）在 Python 中是无序的（或者说顺序不保证）。
                                如果客户端和服务端在遍历参数时顺序不一致，拼出来的字符串就会是 a=1&b=2 和 b=2&a=1，导致最终算出的签名完全不同。
                                按字母排序（Lexicographical Sorting） 是业界生成签名的标准规范（如微信支付、支付宝、AWS 等），
                                        它确保了无论在哪台机器上，相同的参数集合永远能生成相同的签名。
                        注意：
                            1. 数据类型陷阱：代码中使用了 f"{k}={v}"。
                                如果 v 是布尔值（True/False）或 None，Python 会将其转换为字符串 "True" 或 "None"。
                                但如果第三方服务端是用 Java 写的，它可能会将其转换为 "true" 或 "null"。这会导致签名验证失败。
                                建议：在拼接前，确保所有值都被显式转换为字符串，并确认大小写规范。
                            2. 特殊字符编码：如果参数值中包含 &、= 或空格，直接拼接会破坏参数结构。
                                通常需要对 Value 进行 URL Encode 处理后再参与签名计算。
                            3. 注释的准确性：hashlib.sha256 生成的是 HMAC-SHA256 或简单的 SHA256 摘要。
                                建议将注释修正为“此处为 SHA256 摘要签名示例”。

                            这个函数是 ETL 客户端的安全基石。

                    - 装饰器 @retry
                        Python 中 tenacity 库的经典用法，它通过 @retry 装饰器为异步函数注入了高可用容错机制。
                        在 ETL 数据抽取场景中，网络请求是最不稳定的环节，代码确保了程序在遇到临时性网络故障时不会直接崩溃，而是进行自我恢复。
                        1. stop=stop_after_attempt(3)：重试终止条件
                            含义：设置最大尝试次数为 3 次。
                            关键细节：这里的 3 次指的是总共的尝试次数，即“1 次初始请求 + 2 次重试”。
                                    如果 3 次尝试全部失败，tenacity 将放弃重试，并将最后一次捕获到的异常抛出给上层调用者。
                                    这避免了因无限重试导致的任务死锁或资源浪费。
                        2. wait=wait_exponential(multiplier=1, min=2, max=10)：指数退避等待策略
                            含义：在每次重试之间，程序不会立即发起下一次请求，而是会等待一段时间。等待的时间呈指数级增长。
                            参数解析：
                                - multiplier=1：乘数因子，决定了退避的基数。
                                - min=2：最小等待时间为 2 秒（即第一次重试前至少等 2 秒）。
                                - max=10：最大等待时间上限为 10 秒。
                            实际表现：如果请求失败，程序会依次等待 2秒、4秒、8秒、10秒（触达上限后不再增长）。
                            ETL 场景意义：这种“指数退避（Exponential Backoff）”策略是应对服务过载或网络抖动的最佳实践。
                                    它能给下游服务器留出喘息和恢复的时间，有效避免大量并发重试引发的“重试风暴”或雪崩效应。
                        3. retry=retry_if_exception_type(...)：精准重试触发条件
                            含义：明确告诉 tenacity，只有当捕获到指定类型的异常时，才触发重试机制。
                            指定异常：
                                httpx.NetworkError：网络连接层面的错误（如 DNS 解析失败、连接被拒绝等）。
                                httpx.TimeoutException：请求超时异常（服务端响应太慢）。
                            ETL 场景意义：“防呆”设计。
                                如果第三方 API 返回了 400 Bad Request（参数错误）或 403 Forbidden（鉴权失败），这属于业务逻辑错误，
                                        重试 100 次结果也是一样的。
                                通过限定异常类型，程序可以跳过无效重试，直接报错，极大地提升了 ETL 任务的执行效率。
                        补充：
                            一个重试前的日志回调
                            当 ETL 任务发生重试时，如果没有日志，运维人员会以为程序卡死了。
                            加上 before_sleep 后，每次重试都会在控制台或日志文件中留下一条 Warning 级别的记录，便于排查生产环境的网络抖动问题。
                            （例如：Retrying request in 2.0 seconds as it raised NetworkError...）

                - 关于 wait=wait_exponential(multiplier=1, min=2, max=10)：指数退避等待策略
                    1. multiplier 单词的含义是倍数的意思，为什么是指数级增长？
                        因为在数学公式中，这个“乘数”是作为指数（Exponent）的乘数因子存在的，而不是作为底数的倍数。
                    2. 底层数学公式
                        tenacity 的指数退避（Exponential Backoff）计算公式大致如下：
                            等待时间=multiplier×(2^重试次数)
                    3. 为什么叫 multiplier 而不是 exponent？
                        因为在数学表达式 a×2^n 中，multiplier 控制的是整个指数函数的缩放比例（Scaling Factor）。
                            - 如果 multiplier = 1，等待时间就是标准的 2, 4, 8, 16...
                            - 如果 multiplier = 2，等待时间就会变成 4, 8, 16, 32...（整体变慢）
                            - 如果 multiplier = 0.5，等待时间就会变成 1, 2, 4, 8...（整体变快）
                    总结：
                        multiplier 本身不是指数，它是乘在指数结果上的那个系数。
                        但因为整个公式的核心是 2^n 这个指数函数，所以这种等待策略在计算机科学中被统称为“指数级增长”或“指数退避”。

                - 异步分页拉取数据
                    在 ETL 工程中，处理大数据的标准做法是“边拉取，边处理，边写入”。将函数改造为异步生成器（Async Generator）：
                        async def fetch_paginated_data(self, endpoint: str, page_size: int = 500):
                            """流式分页拉取API数据，避免内存溢出"""
                            page = 1
                            while True:
                                # 发起异步网络请求（挂起，等待API响应）
                                resp = await self.request("GET", endpoint, params={"page": page, "page_size": page_size})

                                # 如果当前页没数据，说明拉完了，彻底结束生成器
                                if not resp["data"]:
                                    break

                                # 将当前页数据抛出给调用方，并冻结当前函数状态
                                yield resp["data"]

                                # 调用方处理完数据后，函数从这里恢复执行
                                # 主动休眠100ms，给第三方API喘息时间，防止触发限流（429错误）
                                await asyncio.sleep(0.1)

                                # 5. 页码加1，进入下一次循环拉取下一页
                                page += 1
                    调用：
                        # 边拉取边写入数据库，内存占用始终保持在极低水平
                        async for page_data in client.fetch_paginated_data("/v1/users"):
                            await db.bulk_insert(page_data)  # 每次只处理 500 条

                    Python 异步编程与 ETL 架构结合的最高级形态。
                    将普通的异步函数改造为异步生成器（Async Generator），彻底解决了海量数据抽取时的内存溢出（OOM）问题。

                    核心改动点：从 return 到 yield
                        普通函数中，all_data = [] 收集数据，最后 return all_data。这意味着必须等所有页都拉取完，才会把数据交给调用方。
                        而在改造后的代码中，核心变成了：
                            yield resp["data"]
                        作用：yield 关键字将这个函数变成了一个异步生成器。
                                它不再一次性返回所有数据，而是每次只“吐”出当前页的数据。
                        状态挂起：当执行到 yield 时，整个函数的状态（包括 page 变量的值、当前执行到哪一行）会被冻结并保存。
                                控制权会交还给调用方（即 async for 循环）。
                        状态恢复：当调用方处理完这一页数据，进入下一次循环时，函数会从 yield 的下一行（即 await asyncio.sleep(0.1)）继续执行，
                                直到遇到下一个 yield。

                    异步生成器模式（流式处理优势）
                        - 内存恒定（O(1)）：无论 API 有 1000 页还是 100 万页，Python 进程在任意时刻的内存中，只保留当前正在处理的 500 条数据。
                                处理完这 500 条，内存就会被垃圾回收器（GC）释放，内存占用曲线是一条极其平稳的直线。
                        - 流水线作业（Pipeline）：数据“拉取 -> 清洗 -> 写入数据库”是并行流水线。
                                拉取第 2 页数据的同时，第 1 页的数据可能正在写入数据库。极大地缩短了 ETL 任务的总耗时。
                        - 断点续传能力：如果在拉取第 500 页时程序崩溃，前 499 页的数据已经安全落库，不需要从头再来。

                    生成器必须配合 async for 使用：
                        # 边拉取边写入数据库，内存占用始终保持在极低水平
                        async for page_data in client.fetch_paginated_data("/v1/users"):
                            # page_data 就是当前页的 500 条数据列表
                            await db.bulk_insert(page_data)
                        - async for 会在底层不断调用生成器的 __anext__() 方法。
                        - 每次拿到 page_data，执行 bulk_insert。
                        - 写入完成后，async for 再次向生成器索要下一页数据，触发 yield 之后的代码继续执行。

                - 关闭客户端及异步函数的上下文管理
                    1. 异步函数有自己的上下文管理，为什么还要显式关闭？
                        普通的 async def 函数并没有内置的上下文管理（自动清理）机制。
                            - 普通异步函数的局限：async def 仅仅定义了一个协程（Coroutine）。当你调用它时，它只负责执行里面的逻辑。
                                    当函数执行完毕或抛出异常时，Python 的垃圾回收器（GC）可能会在某个不确定的时间点回收内存，
                                    但它不会自动触发底层网络连接的断开。
                            - 上下文管理器 (async with)：只有实现了 __aenter__ 和 __aexit__ 协议的对象，才能配合 async with 使用，
                                    从而在退出代码块时自动执行清理逻辑。
                            - httpx.AsyncClient 的特殊性：httpx.AsyncClient 内部维护了一个连接池（Connection Pool）。
                                    如果不显式关闭，底层的 TCP 连接、DNS 缓存和 Socket 文件描述符就会一直挂起，
                                    导致严重的资源泄漏（Resource Leak）。
                    2. aclose() 与 close() 有什么区别？
                        在 httpx 库中，这两者的核心区别在于是否阻塞事件循环（Event Loop）。
                        - close()：同步关闭方法
                            适用对象：httpx.Client（同步客户端）。
                            行为：它是阻塞的。当调用 client.close() 时，它会立刻执行清理操作，直到连接彻底断开才会返回控制权。
                            绝对不能在 async def 异步函数中调用同步的 close()。这会阻塞整个异步事件循环，导致所有其他并发任务全部卡死。
                        - aclose()：异步关闭方法
                            适用对象：httpx.AsyncClient（异步客户端）。
                            行为：它是协程（Coroutine）。
                                调用 await client.aclose() 时，它会向事件循环提交一个“关闭连接”的任务，然后挂起当前协程。
                                在等待底层 Socket 优雅断开（发送 FIN 包、等待服务端确认）的过程中，事件循环可以去执行其他任务。
                            在 Python 异步编程规范中，所有的异步资源释放方法通常都以 a 开头（如 aclose, aread, aiter_bytes），
                                以明确告诉开发者“这是一个需要 await 的异步操作”。
                        因为 self.client 是 httpx.AsyncClient，必须使用 await 配合 aclose() 来异步、优雅地释放底层的网络连接池，
                                既避免了资源泄漏，又不会阻塞整个异步 ETL 系统的运行。

                补充：
                    - 关于 async 和 await
                        async 和 await 在代码中不同位置出现，是因为它们分别承担了“定义规则”和“执行规则”两个不同的任务。
                        1. async 永远出现在函数声明（定义）或控制流结构中，它的作用是打标签。
                            - async def（异步函数）：相当于告诉 Python 编译器：
                                “这个函数内部可能会有耗时的操作（比如等网络、等数据库），把它包装成一个协程（Coroutine），不要让它阻塞主线程。”
                            - async for（异步迭代器）：相当于告诉 Python：
                                “循环里的数据不是一次性准备好的，而是异步生成器（Async Generator）边拉取边吐出来的。
                                    每次循环都需要等待数据准备好才能进行下一步。”
                            总结：async 是声明性的，它只负责定义“这里需要异步机制”，它本身不执行任何耗时操作。
                        2. await 永远出现在函数体内部（执行流程中），它的作用是真正触发等待。
                            - await save_to_database(page_data)：当程序执行到这里时，它会向数据库发送写入请求。
                                因为数据库写入需要时间，await 就会挂起（Suspend）当前协程，把控制权交还给事件循环（Event Loop）。
                                在等待数据库响应期间，程序可以去处理其他任务。
                                等数据库返回结果后，再恢复执行。
                            总结：await 是执行性的，它只负责在具体的耗时操作处“暂停并等待”。
                        3. 为什么 await 会出现在“返回值部分”？
                            await 出现的地方不固定如：
                                return await client.fetch_paginated_data(...)
                                resp = await self.request("GET", endpoint)
                            本质原因：在 Python 中，不能直接返回一个协程对象，必须等待它执行完毕拿到结果。
                                    当调用一个 async def 定义的函数时，它不会立刻执行，而是返回一个“协程对象（Coroutine Object）”。
                                    如果直接 return client.fetch_paginated_data()，返回的只是一个“未执行的空壳”。
                                    加上 await，意思是：“请立刻执行这个协程，等它彻底运行完、拿到最终结果后，再把结果返回出去。”

                            Python 异步编程中，有一条铁律：
                                只要 await 出现了，它的“祖先”函数声明上必须带有 async。
                                    - 因为 await 只能在 async def 函数内部使用。
                                    - 如果函数 A 内部用了 await，那么 A 就是 async def。
                                    - 如果函数 B 调用了函数 A，那么 B 内部也必须用 await，且 B 也必须是 async def。
                                    - 这就像“病毒传染”一样，异步机制会沿着调用链一路向上传递，直到最顶层的入口（比如 FastAPI 的路由，
                                        或者 asyncio.run()）。


    1.4 数据清洗与转换

                意义：这是数据安全与隐私合规（如 GDPR）的强制要求。

            2. 业务规则过滤（白名单机制）
                只允许预设的 5 种行为类型通过，遇到未知的类型（如爬虫产生的异常行为）直接跳过。
                意义：防止下游分析报表或算法模型被脏数据污染。
                        同时，通过 logger.warning 记录异常数据，方便后续排查上游接口是否发生了变更。
            3. 完整性校验（必填字段检查）
                拦截缺少核心标识（用户ID或行为类型）的残缺数据。
                意义：在数据仓库中，没有 user_id 的行为数据是毫无价值的，强行入库只会浪费存储空间并导致 SQL 查询报错。
            4. 格式标准化（时间戳转换）
                将上游 API 返回的 Unix 时间戳（整数）转换为 MySQL 兼容的 YYYY-MM-DD HH:MM:SS 字符串格式。
                意义：上游数据源可能使用毫秒级时间戳或 ISO 格式，而目标数据库通常要求特定的时间格式。
                        这一步确保了异构数据源在目标库中的统一性。
            5. 强类型校验（Pydantic 兜底）
                将清洗后的字典实例化为 BehaviorCreate 模型。
                意义：Pydantic 不仅会校验数据类型（比如确保 user_id 是字符串而不是列表），还会自动拦截多余的未知字段。
                        如果数据有任何问题，Pydantic 会抛出异常，被外层的 try...except 捕获。

            隔离故障：在 ETL 中，绝对不能因为一条脏数据导致整个批次任务崩溃。
                    try...except 配合 continue，确保了即使某条数据引发异常（如时间戳转换时格式错误），程序也会记录日志并跳过它，

            可追溯性：日志中不仅打印了异常信息，还打印了 idx（行号）和 原始数据。为运维人员排查问题提供了完美的“案发现场”。

    1.5 批量入库与增量更新
        1.5.1 批量入库工具类
            基于 SQLAlchemy 封装批量插入、增量更新的通用方法，采用1000 条一批次提交，避免大事务锁表，生产环境建议用临时表过渡后 Rename 正式表，
            保障数据平滑落地：
                app/etl/load/bulk_loader.py

                ETL 系统中 Load（加载） 阶段的核心组件。
                承接异步 API 抽取和 Pydantic 数据清洗，将处理好的“标准件”高效地写入目标数据库。
                这段代码展示了 SQLAlchemy 在 ETL 场景下的最佳实践：抛弃 ORM 的逐条插入，全面拥抱 Core 层的批量操作。
                1. 性能基石：Pydantic 到字典的转换
                    insert_data = [item.model_dump(exclude_unset=True) for item in data]
                    作用：将 Pydantic 模型对象转换为纯 Python 字典。
                    意义：SQLAlchemy 的 ORM 插入（session.add_all()）需要构建大量 ORM 实例，内存开销极大。
                        通过 model_dump() 转换为字典后，可以直接使用 SQLAlchemy Core 层的 insert().values() 方法。
                        这种方式绕过了 ORM 实例化过程，直接构造底层 SQL，吞吐量可提升数4。
                    细节：exclude_unset=True
                        确保只序列化在清洗阶段被显式赋值的字段，忽略模型中带有默认值但未被赋值的字段，防止无意义的默认值覆盖掉数据库中已有的数据。
                2. 全量加载：bulk_insert_behavior
                    stmt = insert(UserBehavior).values(insert_data)
                    result = await self.db.execute(stmt)
                    作用：将一批数据（如 1000 条）合并为单条多行的 INSERT INTO ... VALUES (...), (...) 语句一次性发送给数据库。
                    意义：极大地减少了 Python 与数据库之间的网络往返（Round-trip）通信开销。
                        配合之前设置的 batch_size = 1000，在内存占用和写入性能之间取得了完美的平衡。
                3. 增量同步：upsert_behavior
                    stmt = stmt.on_duplicate_key_update(
                        action_type=stmt.inserted.action_type,
                        # ... 其他字段
                    )
                    作用：这是 MySQL 特有的 INSERT ... ON DUPLICATE KEY UPDATE 语法在 SQLAlchemy 中的实现。
                    意义：这是实现增量同步（Incremental Sync）和断点续传的神器。
                        如果这批数据中包含已经存在于目标表中的记录（即主键或唯一索引冲突），数据库不会报错，而是自动执行 UPDATE 操作，
                        将最新的数据覆盖旧数据。
                    细节：stmt.inserted.action_type 代表“本次尝试插入的新值”。
                        这种写法避免了硬编码，确保了 SQL 的健壮性。
                4. 事务安全与容错
                    try:
                        await self.db.execute(stmt)
                        await self.db.commit()
                    except Exception as e:
                        await self.db.rollback()
                        raise
                    作用：确保批量操作的原子性。
                    意义：在批量写入 1000 条数据时，如果第 999 条因为格式错误导致插入失败，rollback() 会回滚整个批次，
                            避免数据库中产生“只写了一半”的脏数据。
                        logger.error 记录了异常，raise 则将异常抛给上层的 ETL 调度器，以便触发告警或重试机制。
                优化：
                    1. 引入 SQLAlchemy 的 bulk_insert_mappings：
                        对于全量插入，除了使用 Core 层的 insert().values()，还可以考虑使用 SQLAlchemy 提供的
                            session.bulk_insert_mappings(UserBehavior, insert_data)。
                        它的底层机制更加激进，不仅绕过 ORM 实例化，还跳过了部分生命周期事件钩子，在 ETL 纯数据导入场景下性能更高。
                    2. 分批提交（Batch Commit）防止长事务。

                补充：
                    - 关于 continue 和 break 在 try ... except ... 中的作用
                        1. 遇到 continue 后，序会报错时，程序会直接跳过 try 块中剩余的所有代码，进入外层循环的下一次迭代。
                        2. 可以用 break 控制流程，在 except 块中使用 break 会直接终止整个外层循环。

                        try...except 本身不是循环结构，它只是一个“异常监控与处理块”。
                        continue 和 break 的作用对象永远是包裹着 try...except 的外层循环。

                        continue 在 except 中的真实作用：
                            for idx, item in enumerate(raw_data):  # 【外层循环】
                                try:
                                    # 步骤1: 脱敏IP
                                    # 步骤2: 过滤无效行为
                                    # 步骤3: 校验必填字段
                                    # 步骤4: 统一时间格式
                                    # 步骤5: Pydantic校验
                                    cleaned.append(BehaviorCreate(**item))
                                except Exception as e:
                                    logger.error(f"清洗第{idx}条数据失败：{str(e)}，原始数据：{item}")
                                    continue  # 【关键控制点】
                            当 try 块中发生异常时：
                                假设程序在执行“步骤2：过滤无效行为”时抛出了异常。
                                    1. 立即中断：try 块中步骤2之后的所有代码（步骤3、4、5）会被瞬间跳过，绝不执行。
                                    2. 进入 except：控制权跳转到 except 块，执行日志记录。
                                    3. 遇到 continue：continue 指令直接作用于最外层的 for 循环。
                                        它会立即结束当前这一轮循环，将 idx 加 1，拿到 raw_data 中的下一条数据，重新从头开始执行 try 块。

                        如果在 except 中使用 break
                            一旦遇到第一条脏数据，程序会记录日志，然后直接摧毁整个 for 循环。raw_data 中哪怕还有 9999 条合法数据，
                                程序也不会再处理了，直接跳到 for 循环之后的代码。
                            适用场景：这通常用于“遇到致命错误，必须立即停止整个 ETL 任务”的场景（例如数据库连接断开、核心配置缺失）。

                        总结：
                            Python 官方文档和底层设计明确指出：try-except 并非循环结构，因此 continue 和 break 关键字仅对 for/while 循环有效，
                                    它们可以毫无障碍地穿透 except 块去控制外层循环。
                            在 ETL 的数据清洗（Transform）阶段，except + continue 是最经典的黄金搭档。
                                    它确保了清洗流水线具有极强的鲁棒性：
                                        哪怕上游传过来的数据格式千奇百怪，清洗程序也能做到“遇到坏数据就跳过并报警，遇到好数据就继续清洗”，
                                            绝不会因为单条数据的异常而导致整个批处理任务崩溃。

                    - 关于循环结构中的 finally
                        在 Python 中，finally 可以出现在循环结构中，是一种非常强大但容易被忽视的语法特性。
                        finally 是 try...except 异常处理块的专属后缀。
                        finally 不属于循环，它属于 try 块。
                        当 try 在循环里，finally 跟着循环逐次执行（适合单条数据的资源清理）。
                        当循环在 try 里，finally 跟着循环整体执行（适合整个 ETL 任务的全局收尾）。

            4. expire_on_commit=False：在异步会话工厂中加入了这个参数。
                这是异步 SQLAlchemy 的最佳实践，防止在 commit() 之后访问模型属性时触发隐式的懒加载（异步环境下懒加载会报错）。

            async with get_async_session_ctx("target_mysql") as session:

        关于之前修改代码时的 logger 及 logging
        logger 和 logging 是 Python 官方标准库内置的模块。
        在 Python 中，logging 是专门用于输出运行日志的官方标准模块。
        比在开发中常用的 print 强大得多，可以设置不同的日志等级、输出格式以及保存路径。
        - logging 是什么？
            logging 是 Python 内置的日志模块本身。
            在代码中，logging.WARNING 是一个常量，代表“警告”这个日志级别。
            当 tenacity 库在执行重试前，会去读取这个常量，从而知道需要打印一条警告级别的日志。
        - logger 是什么？
            logger 是 logging 模块中的一个类的实例（对象）。
            它是通过 logging.getLogger(__name__) 创建出来的。
            在 Python 中，我们通常不会直接去实例化 Logger，而是通过这种模块级方法来获取。
                它的作用：logger 对象扮演了“记录器”的角色，它负责决定如何处理日志信息，并将日志传送给相关的处理器（Handler）。
                它的命名：__name__ 是 Python 的一个内置变量，代表当前模块的名称。
                        使用它作为 logger 的名字，可以形成一种树状的层级结构（例如 app.etl.api_client）。
                        这种命名方式的好处是，子 logger 会自动继承父 logger 的配置，极大地方便了大型项目的日志管理。
        - 如何协同工作？
            import logging  # 1. 引入官方的日志模块
            logger = logging.getLogger(__name__)  # 2. 通过模块获取一个专属的“记录器对象”
            before_sleep=before_sleep_log(logger, logging.WARNING)
            # 3. 把“记录器对象”和“警告级别常量”一起打包，传给 tenacity 库。
            # 当发生重试时，tenacity 就会调用这个 logger 对象，以 WARNING 级别把重试信息打印出来。

            补loguru 也是可选的日志库
            虽然 logging 是 Python 官方自带的标准库，但在实际的 ETL 或 Web 开发中，也有开发者觉得官方库配置起来比较繁琐，
                从而选择使用第三方日志库（比如之前清洗代码中用到的 loguru）。

        关于 api_client.py 的 fetch_paginated_data
        是 ETL 系统中数据抽取（Extract）阶段的典型实现，专门用于处理第三方 API 的分页接口。
        在 ETL 场景中，数据量通常非常庞大，API 接口会限制单次返回的数据量（如每次最多返回 500 条），因此必须通过循环翻页来拉取全量数据。
        1. 初始化数据容器与页码
            all_data = []
            page = 1
            创建一个空列表用于汇总所有页的数据，并将起始页码设为 1。
        2. 无限循环与自动翻页
            while True:
                resp = await self.request("GET", endpoint, params={"page": page, "page_size": page_size})
            通过 while True 构建一个无限循环，每次循环自动将 page 参数传入请求。
            利用了之前封装的 request 方法，自动完成了鉴权、重试等底层逻辑，业务代码简洁。
        3. 终止条件（防死循环机制）
            if not resp["data"]:
                break
            检查当前页返回的数据列表是否为空。如果为空，说明已经拉取到了最后一页，跳出循环。
            这是分页拉取标准的“探底”策略，避免了硬编码总页数（因为总页数可能会在拉取过程中发生变化）。
        4. 数据追加与主动限流
            将当前页的数据合并到总列表中，然后休眠 100 毫秒，最后页码加 1。
            asyncio.sleep(0.1) 主动限流（Rate Limiting）设计。
            ETL 抽取速度极快，如果不加休眠，可能会在几秒内发出上百个请求，直接触发第三方 API 的 429 Too Many Requests 限流规则，甚至导致对方服务宕机。

        后修改为异步生成器的提升：
            1. 内存恒定（O(1)）：无论 API 有 1000 页还是 100 万页，Python 进程在任意时刻的内存中，只保留当前正在处理的 500 条数据。
                处理完这 500 条，内存就会被垃圾回收器（GC）释放，内存占用曲线是一条极其平稳的直线。
            2. 流水线作业（Pipeline）：数据“拉取 -> 清洗 -> 写入数据库”是并行流水线。
                拉取第 2 页数据的同时，第 1 页的数据可能正在写入数据库。极大地缩短了 ETL 任务的总耗时。
            3. 断点续传能力：如果在拉取第 500 页时程序崩溃，前 499 页的数据已经安全落库，不需要从头再来。
            从 return 到 yield
                在普通函数中，使用 all_data = [] 收集数据，最后 return all_data。这意味着必须等所有页都拉取完，才会把数据交给调用方。
                而在改造后的代码中，核心变成了：
                    yield resp["data"]
                作用：yield 关键字将这个函数变成了一个异步生成器。它不再一次性返回所有数据，而是每次只“吐”出当前页的数据。
                状态挂起：当执行到 yield 时，整个函数的状态（包括 page 变量的值、当前执行到哪一行）会被冻结并保存。
                        控制权会交还给调用方（即 async for 循环）。
                状态恢复：当调用方处理完这一页数据，进入下一次循环时，函数会从 yield 的下一行（即 await asyncio.sleep(0.1)）继续执行，
                        直到遇到下一个 yield。


二、权限控制与异常捕获处理

    2.1 三层权限控制方案
        覆盖接口级权限、数据级权限、数据源级权限，保障数据和接口的访问安全，适配 ETL 脚本、业务接口、管理端接口不同的权限需求。

            2.1.1 接口级权限（FastAPI 依赖注入实现）
                基于 JWT 身份认证 + 角色校验，区分普通用户、管理员、ETL 系统账号的权限，通过依赖项校验接口访问权限，复用之前的用户表结构，
                新增role字段区分角色：
                    app/api/deps.py

                FastAPI 的权限控制实现，利用 FastAPI 的依赖注入（Dependency Injection）系统，将“身份认证”与“权限校验”进行解耦。
                1. 身份认证：get_current_user
                    这个异步函数的作用是“确认你是谁”，它是整个权限体系的基石。
                        提取凭证：通过 OAuth2PasswordBearer 自动从 HTTP 请求头（Authorization: Bearer <token>）中提取 JWT 令牌。
                        解析令牌：使用 jose 库解码 JWT，提取出 sub（通常是用户名或用户ID）声明。
                                如果令牌无效或过期，会抛出 401 Unauthorized 异常。
                        查询数据库：拿到用户名后，通过 user_crud 去数据库查询真实的用户对象。
                                这一步非常关键，它能防止令牌被吊销后用户依然能访问系统（即解决了 JWT 无状态带来的无法主动失效问题）。
                        返回用户对象：校验通过后，返回完整的 User 模型对象，供后续依赖或路由函数直接使用。

                    详解：
                        函数签名与依赖声明
                            - async def：声明为异步函数，因为内部包含了数据库查询等 I/O 操作，异步可以提升并发性能。
                            - token: str = Depends(oauth2_scheme)：FastAPI 会自动调用 oauth2_scheme。
                                如果请求头中没有携带合法的 Authorization: Bearer <token>，FastAPI 会直接返回 401 Unauthorized，
                                        根本不会进入这个函数的内部逻辑。
                            - db: Session = Depends(get_db)：自动注入一个 SQLAlchemy 的数据库会话（Session），用于后续的数据库查询。
                            - -> User：类型提示，明确告诉 FastAPI 和其他开发者，这个依赖最终会返回一个 User 模型对象
                        定义统一的异常处理
                            预先定义了一个 401 异常。
                            在 JWT 校验中，出于安全考虑，不应该向客户端暴露具体的失败原因（比如“Token已过期”、“签名错误”、“用户不存在”等），
                                    统一返回“身份校验失败”可以防止攻击者通过不同的错误提示来探测系统内部逻辑。
                            WWW-Authenticate: Bearer 是 HTTP 标准规范，告诉客户端需要使用 Bearer 认证方式。
                        解析 JWT 令牌
                            - jwt.decode：使用配置的密钥（SECRET_KEY）和算法（如 HS256）解码 Token。
                                如果 Token 被篡改或已过期，jose 库会抛出 JWTError，此时会被 except 捕获并抛出 401 异常。
                            - payload.get("sub")：JWT 的 Payload 中通常包含 sub（Subject）字段，这里约定 sub 存放的是用户的 username。
                                如果解析出的 payload 中没有 sub 字段，同样抛出 401 异常。
                        数据库二次校验（关键安全点）
                            JWT 本身是无状态的，一旦签发，在过期前始终有效。
                            如果管理员在后台封禁或删除了某个用户，该用户手里的 Token 依然有效。
                                通过每次请求都查询数据库，可以确保“即使 Token 有效，但如果用户在数据库中不存在或被禁用，依然无法通过校验”。
                            返回用户对象：校验全部通过后，将完整的 User 对象返回。
                            后续的路由函数或其他依赖（如 check_user_permission）就可以直接拿到这个 user 对象，无需再次查询数据库。

                    遵循了 “Token 验证 -> 提取标识 -> 数据库核实” 的标准安全流程。
                    不仅解决了“你是谁”的问题，还利用 FastAPI 的依赖注入，将复杂的认证逻辑从业务路由中完全剥离，使得业务代码只需一行
                        Depends(get_current_user) 就能获得当前登录用户的完整信息。

                    补充：
                        - 依赖注入 Depends(get_current_user)
                            FastAPI 依赖注入系统（Dependency Injection System）中最核心的机制之一。
                            简单来说，它的作用机制是：
                                声明的代码运行需要什么（依赖），然后由 FastAPI 系统负责执行必要的逻辑，为你提供这些依赖（注入）。
                            1. 显式声明，告别“隐式全局变量”
                                在传统的 Web 框架（如 Flask）中，获取当前登录用户通常依赖隐式的全局上下文（例如从 request 或 flask.g 中取值），
                                    这违背了 Python “显式优于隐式”的哲学。
                                在 FastAPI 中，Depends() 把依赖关系直接写进了函数签名里。
                                    当写下 current_user: User = Depends(get_current_user) 时，你是在明确声明：
                                        这个路由函数的执行，强依赖于 get_current_user 的返回值。
                                    任何人看这个函数签名，都能立刻知道它需要“当前登录用户”。
                            2. 自动解析依赖树
                                FastAPI 知道 current_user 的类型是 User，并且它来自依赖项而非客户端的输入。
                                当请求到达时，FastAPI 会在路由匹配后、视图执行前，自动解析整个依赖图：
                                    - 它识别到 Depends(get_current_user)。
                                    - 发现 get_current_user 本身也是可调用对象，且它内部嵌套了 Depends(oauth2_scheme) 和 Depends(get_db)。
                                    - FastAPI 会递归解析这条依赖链，先执行底层的提取 Token 和获取数据库会话，然后将结果传入 get_current_user，
                                        最终把返回的 User 对象注入到路由函数参数中。
                            3. 请求级缓存（避免重复劳动）
                                默认情况下，在同一个请求中，如果同一个依赖项被多次使用，FastAPI 只会执行一次，然后缓存结果。
                            4. 极致的代码复用与可测试性
                                通过 Depends(get_current_user)，实现了“安全和依赖注入的代码只需要写一次”。
                                业务解耦：就算系统有数千个需要鉴权的端点，它们都可以复用这同一个安全系统，每个路由只需短短几行代码就能接入完整的鉴权逻辑。
                                易于测试：每个依赖项都是一个独立可调用的单元。
                                        在进行单元测试时，可以非常容易地单独 mock 掉 get_current_user 函数，而不影响其他业务逻辑的测试。

                            Depends(get_current_user) 并不是简单地“调用了一个函数”，而是利用类型安全的、可组合的方式，
                                重新组织了后端架构中最容易写成“意大利面条”的鉴权逻辑，让的代码既安全又优雅。

                2. 权限校验：check_user_permission
                    这个函数的作用是“确认你能不能做”，它实现了基于角色的访问控制（RBAC）。
                        闭包设计：它接收一个参数 required_roles（允许访问的角色列表），并返回一个真正的依赖函数 permission_checker。
                                这种闭包设计使得权限检查器变得高度可配置和可复用3。
                        嵌套依赖：注意 permission_checker 的参数 current_user: User = Depends(get_current_user)。
                                FastAPI 会自动先执行 get_current_user 获取当前用户，然后再将其传入 permission_checker。
                        角色比对：检查当前用户的 role 是否在允许列表中。如果不在，直接抛出 403 Forbidden 异常，拦截请求。

                    详解：
                        利用 Python 的闭包（Closure）和 FastAPI 的动态依赖生成机制，实现了一个高度可配置的权限拦截器。
                            1. 闭包与动态依赖生成
                                外层函数：check_user_permission 本身不是一个 FastAPI 依赖，它只是一个普通的工厂函数。
                                        它接收一个参数 required_roles（比如 ["admin", "editor"]）。
                                内层函数：它返回了一个真正的异步函数 permission_checker。
                                        因为 Python 的闭包特性，内层函数可以“记住”外层函数传入的 required_roles 变量。
                                动态生成：每次在路由中写 Depends(check_user_permission(["admin"])) 时，
                                        FastAPI 实际上注入的是这个已经绑定了特定角色列表的 permission_checker 函数。
                                        这就是为什么它能做到“高度可配置”。
                            2. 嵌套依赖注入
                                机制核心：permission_checker 声明了一个参数 current_user，并且它的默认值是 Depends(get_current_user)。
                                执行顺序：当 FastAPI 执行到这一层时，它会发现需要先获取 current_user。
                                        于是它会先去执行 get_current_user（解析 Token、查数据库）。
                                        如果那一步失败（比如 Token 无效），请求直接返回 401 Unauthorized，根本不会进入 permission_checker 内部。
                                如果 get_current_user 成功返回了用户对象，FastAPI 会将这个对象注入到 current_user 参数中，
                                    然后继续执行 permission_checker 内部的逻辑。
                            3. 权限比对与拦截
                                角色比对：拿到真实的 current_user 对象后，检查该用户的 role 属性是否存在于外层传入的 required_roles 列表中。
                                403 拦截：如果用户的角色不在允许列表中，说明身份合法但权限不够，此时抛出 403 Forbidden 异常，直接拦截请求。
                                放行并透传：如果校验通过，函数返回 current_user。
                                        这意味着，不仅请求被放行了，而且这个带有完整信息的用户对象还会被注入到最终的路由函数参数中。

                调用：
                    # 只有 admin 角色可以访问
                    @app.get("/admin/dashboard")
                    async def admin_dashboard(current_user: User = Depends(check_user_permission(["admin"]))):
                        return {"msg": f"欢迎, {current_user.username}"}

                    # admin 和 editor 角色都可以访问
                    @app.post("/articles")
                    async def create_article(current_user: User = Depends(check_user_permission(["admin", "editor"]))):
                        return {"msg": "文章创建成功"}

                优化(这是很以后的事情了，先学明白再说吧)：
                    1. 支持角色层级（Role Hierarchy）：目前的逻辑是严格的列表匹配。
                        如果系统中存在 admin > editor > viewer 的层级关系，可以引入一个角色优先级映射表（字典），
                        将比对逻辑改为“判断用户角色等级是否大于等于所需最低等级”，这样扩展性会更强。
                    2. 细粒度权限（ABAC/数据级权限）：当前代码只控制了“接口级”的访问。
                        如果业务需要控制“用户只能修改自己创建的文章”，还需要在路由函数内部结合 current_user.id 与数据记录的 owner_id 进行二次校验，
                        防止越权访问（IDOR漏洞）。

                补充：
                    FastAPI 的依赖注入机制
                    FastAPI 的依赖注入（Dependency Injection, DI）系统是其最核心、最强大的特性之一。
                    简单来说，它的核心思想是：只需声明代码运行需要什么，框架会自动负责执行逻辑并提供这些资源。

                    1. 核心组件：Depends()
                        在 FastAPI 中，依赖注入是通过 Depends() 函数来实现的。它通常被放在路由处理函数的参数默认值中。
                            - 声明式编程：当写下 current_user: User = Depends(get_current_user) 时，并没有主动去“调用” get_current_user 函数，
                                    而是向 FastAPI “声明”了这个依赖关系。
                            - 自动参数解析：FastAPI 会自动扫描依赖函数的参数。
                                    例如， get_current_user 需要 token 和 db，FastAPI 会自动从 HTTP 请求（Header、Query、Form 等）中提取 token，
                                        并从它的依赖树中获取 db，然后自动传入。
                    2. 底层执行流程：构建依赖树
                        当客户端发起一个 HTTP 请求时，FastAPI 并不是按照代码从上到下的顺序执行的，而是按照依赖树（Dependency Tree）的拓扑顺序来解析。
                            - 解析阶段：框架首先扫描路由函数的参数，识别出所有的 Depends() 声明。
                            - 递归实例化：如果依赖项本身还有依赖（比如 check_user_permission 依赖 get_current_user，
                                    而 get_current_user 又依赖 oauth2_scheme 和 get_db），FastAPI 会递归地构建一棵完整的依赖树。
                            - 注入阶段：从最底层的依赖开始执行，逐层向上，最终将结果注入到目标路由函数的参数中。
                    3. 请求级缓存机制（性能优化）
                        FastAPI 的依赖注入系统在同一个请求的生命周期内具有缓存特性。
                            - 默认情况下，对于同一个请求，如果某个依赖项被多次声明（例如在嵌套依赖中），FastAPI 只会执行一次该依赖函数，
                                    并将结果缓存起来供后续使用。
                            - 即使被多次引用，系统也不会重复去解码 JWT 或查询数据库，极大地提升了高并发场景下的性能。
                    4. 依赖注入的核心优势
                        为什么顶级团队和现代框架都推崇依赖注入？主要有以下三个技术真相：
                            - 极致的代码解耦与复用（DRY原则）：将横切关注点（如鉴权、日志、限流、数据库连接）从业务逻辑中完全剥离。
                                只需要写一次 get_current_user，成百上千个接口都可以直接复用。
                            - 提升测试效率与模拟能力：在编写单元测试时，你可以非常容易地替换真实的依赖为模拟对象（Mock）。
                                例如，可以使用 FastAPI 提供的 app.dependency_overrides 机制，在不改动主逻辑的前提下注入测试数据库会话，实现真正的隔离测试。
                            - 自动文档与类型安全：因为依赖项也是通过 Python 类型提示声明的，FastAPI 能够自动将依赖中的参数（如查询参数、请求头）整合到
                                Swagger/OpenAPI 文档中，同时提供严格的数据验证和错误处理。
                    (朦朦胧胧的)


                接口权限应用示例：
                    app/api/v1/behaviors.py

                        展示 FastAPI 在实际业务中应用基于角色的访问控制（RBAC）。
                        定义了两个关于“用户行为数据”的接口，并通过依赖注入实现了不同级别的权限拦截。

                        1. 路由模块化设计
                            没有直接使用 app，而是实例化了一个 APIRouter。生产级 FastAPI 项目的标准做法。
                            通过将路由拆分到不同的模块（如 behaviors.py），然后在主入口文件中通过 app.include_router(router) 进行挂载，
                                可以保持项目结构的清晰和解耦。
                        2. 接口一：高敏感的全局操作（严格权限）
                            业务场景：这是一个批量导出接口，涉及全量数据，通常属于高敏感操作。
                            权限控制：Depends(check_user_permission(["admin"]))。
                                    列表中只有 "admin"，这意味着只有管理员才能调用此接口。
                                    如果普通用户（user）尝试访问，FastAPI 会在依赖阶段直接抛出 403 Forbidden 异常，根本不会进入函数体内部。
                        3. 接口二：常规的个人操作（宽泛权限）
                            业务场景：这是用户查看自己行为记录的接口，属于常规业务。
                            权限控制：Depends(check_user_permission(["admin", "user"]))。
                                    列表中包含了 "admin" 和 "user"，这意味着管理员和普通用户都可以访问。
                            设计意图：管理员可能需要排查问题或查看特定用户的状态，因此也需要拥有访问 /mine 数据的权限。
                        4. current_user 的无缝透传
                            虽然 check_user_permission 的主要作用是“拦截非法请求”，但它的内部函数 permission_checker 最终 return current_user。
                            这意味着，当请求成功通过权限校验后，FastAPI 会自动将解析出的 User 对象注入到 current_user 参数中。
                            因此，在函数体内，不仅拥有了安全的环境，还直接拿到了当前登录用户的完整信息，后续如果需要结合 current_user.id
                                去数据库查询具体的行为记录，可以直接使用，无需再次查询用户表。
                        完善：
                            实际开发中，如果这个接口支持传入 user_id 参数，有水平越权（IDOR漏洞）。

            2.1.2 数据级权限（行级 + 列级控制）
                - 行级权限：限制用户只能操作自己的业务数据，管理员无限制，在业务层拼接数据过滤条件，避免越权访问：
                    app/crud/behavior.py

                    防范水平越权漏洞（IDOR），在 CRUD（数据访问）层实现行级权限控制（Row-Level Security / Data-Level Permissions）。
                    确保你只能打开属于自己的那个柜子。

                    1. 行级数据归属校验
                        在接口级权限（RBAC）通过后，系统还需要进行数据级的校验：
                            - current_user.role != "admin"：如果当前用户是管理员，则拥有“上帝视角”，直接放行，允许查看任何人的数据。
                            - current_user.id != user_id：如果当前用户不是管理员，系统会严格比对“当前登录用户的ID”和“请求查询的目标用户ID”。
                                    如果不一致，说明普通用户试图通过篡改 URL 中的 user_id 来偷窥他人数据。
                            - 抛出 403 异常：一旦越权，立即拦截并返回 403 Forbidden。
                    2. 参数设计：无缝衔接依赖注入
                        函数的参数定义契合 FastAPI 的依赖注入生态：
                            - db: Session：数据库会话，通常由路由层通过 Depends(get_db) 获取后传入。
                            - user_id: int：客户端传入的路径参数或查询参数（例如 /behaviors/{user_id}）。
                            - current_user: User：由路由层通过 Depends(get_current_user) 或 Depends(check_user_permission(...)) 获取后传入。
                        这种设计让 CRUD 函数保持了纯粹性：它不需要自己去解析 Token 或操作请求对象，它只关心“业务逻辑”和“数据校验”。
                        所有的安全上下文都由上层（路由层）准备好并“喂”给它。
                    3. 数据查询逻辑
                        通过行级权限校验后，执行标准的 SQLAlchemy 查询，返回指定 user_id 的所有行为记录。

                    分层的意义：
                        高复用性：如果以后还有一个接口需要查询用户行为（比如“删除某条行为记录”），只需要在删除的 CRUD 函数里复用
                                if current_user.role != "admin"... 的校验逻辑即可，完全不需要重写。
                        职责单一：路由层（Router）只负责处理 HTTP 请求和响应，CRUD 层负责数据安全和数据库操作。
                                即使有人绕过了路由直接调用这个 CRUD 函数，数据依然会受到保护。

                    - 关于分层架构（Layered Architecture）
                    在 FastAPI 等现代 Python Web 框架的实战中，这通常演变为一种三层架构（3-Tier Architecture）。
                    这种架构的核心思想是“关注点分离（Separation of Concerns）”：
                        让每一层只负责自己最擅长的事情，互不干扰。

                    FastAPI 项目，一个完整且健壮的生产级架构通常包含以下三个核心层（有时还会加上 Schema 层）：
                        1. 路由层（API / Router Layer）—— “前台接待员”
                            对应：app/api/v1/behaviors.py
                            核心职责：处理 HTTP 协议。
                                    它负责接收客户端的请求（解析路径参数、查询参数、请求体），调用依赖注入（鉴权、获取数据库会话），
                                    然后调用业务层或 CRUD 层，最后将结果转换为标准的 HTTP 响应（如 JSON）。
                            原则：路由层应该极其“薄”。
                                    它不应该包含任何复杂的业务判断逻辑，也不应该直接写 SQL 或 ORM 查询语句。
                        2. CRUD 层（Data Access Layer / 数据访问层）—— “仓库管理员”
                            对应：app/crud/behavior.py
                            核心职责：纯粹的数据读写。
                                    它负责与数据库打交道（增删改查），封装 SQLAlchemy 的查询语句。
                            原则：它只关心“数据怎么存”和“数据怎么取”。
                                    它不知道什么是 HTTP 请求，也不知道什么是 Token。
                        3. 业务逻辑层（Service / Business Logic Layer）—— “车间主任”（完整架构中不可或缺）
                            核心职责：处理复杂的业务规则。
                                    如果仅仅是“查一条数据”，路由层可以直接调用 CRUD 层。
                                    但如果业务很复杂，这些逻辑就不应该写在路由层，也不应该写在 CRUD 层。
                                    （例如：用户注册时，需要校验用户名是否重复 -> 创建用户记录 -> 初始化用户的钱包表 -> 发送欢迎邮件 -> 记录注册日志）
                            原则：它是整个系统的核心大脑，负责协调多个 CRUD 操作，确保数据的一致性和业务规则的正确性。

                        (补充)
                        Schema 层（Pydantic Models）—— “质检员”
                            在 FastAPI 中，通常还会把 app/schemas/ 单独抽离出来。它定义了数据的输入和输出格式。
                            请求校验：客户端传来的 JSON 必须符合 Schema 的定义，否则直接报 422 错误，根本不会进入路由函数。
                            响应序列化：确保返回给前端的数据格式是固定的，不会不小心把用户的密码等敏感字段暴露出去。

                    完整架构的执行链路：
                        如果加上业务层，一个完整的请求流转过程是这样的：
                            1. 客户端发起请求：POST /api/v1/orders
                            2. 路由层 (Router)：验证 Token，解析请求体，调用 order_service.create_order(...)
                            3. 业务层 (Service)：检查商品库存是否充足 -> 计算折扣 -> 调用 user_crud.deduct_balance() 扣款 ->
                                调用 order_crud.create() 创建订单。
                            4. CRUD层 (CRUD)：执行具体的 db.session.add() 和 db.session.commit()。
                            5. 路由层 (Router)：拿到业务层返回的订单对象，将其转换为 JSON 返回给客户端。

                    设计架构优势：
                        极高的可测试性：你可以单独写单元测试去测业务层，完全不需要启动 FastAPI 服务器，也不需要发真实的 HTTP 请求。
                        易于维护：如果以后要把 MySQL 换成 PostgreSQL，你只需要改 CRUD 层，路由层和业务层一行代码都不用动。
                        代码复用：如果后台管理系统和面向用户的 App 都需要“创建订单”的功能，它们可以调用同一个 Service 层，而不用把业务逻辑写两遍。

                - 列级权限：通过 Pydantic 响应模型排除敏感字段，避免返回用户隐私、数据库密钥等敏感信息，例如在用户响应模型中排除password_hash字段：
                    app/schemas/user.py

                    数据序列化过滤（Data Serialization Filtering）或响应模型过滤。
                        列级权限：通常指在数据库层面（如 PostgreSQL 的 GRANT SELECT (col1, col2)）控制某个用户能不能查询某列。
                        响应模型过滤：指在后端代码中，主动决定“哪些字段允许返回给前端，哪些字段必须被拦截”。
                    在 FastAPI 中，是保护敏感数据（如密码）的最后一道防线。
                        1. 核心机制：白名单过滤
                            Pydantic 的 BaseModel 采用的是白名单机制。在这个类中，只定义了 5 个字段。
                            这意味着，无论数据库查出来的 User 对象里有多少个字段（比如 password_hash、is_active、update_time 等），
                                    只要没有在这里显式声明，它们在转换为 JSON 响应时都会被自动丢弃。
                        2. 安全兜底：from_attributes = True
                             Pydantic V2 中的一个关键配置（在 V1 中叫 orm_mode = True）。
                            它的作用：告诉 Pydantic，“要转换的数据是一个 ORM 对象（比如 SQLAlchemy 的 Model），
                                    请通过属性访问（.）而不是字典键访问（[]）来获取数据”。
                            在路由层，通常会直接写 return UserResponse.model_validate(db_user)。
                                    如果没有这个配置，Pydantic 会报错，因为它不知道怎么从一个 SQLAlchemy 对象中提取数据。
                        3. 防御性编程：明确排除 password_hash
                            虽然白名单机制已经自动排除了 password_hash，但加上这行注释是非常好的工程习惯。
                            它向未来的维护者明确传达了安全意图：“这个 Schema 是对外暴露的，绝对不能包含密码字段”。

                - 架构视角：在三层架构中的位置
                    路由层（Router）

                    假设路由层代码：
                        @router.get("/me", response_model=UserResponse) # 1. 声明响应模型
                        async def get_my_profile(current_user: User = Depends(get_current_user)):
                            return current_user # 2. 直接返回 ORM 对象

                    当 FastAPI 处理这个响应时，它会在后台自动执行 UserResponse.model_validate(current_user)。
                        - 如果没有这个 Schema：FastAPI 会尝试把 current_user 的所有属性（包括致命的 password_hash）全部序列化成 JSON 返回给前端，
                                造成严重的数据泄露。
                        - 有了这个 Schema：FastAPI 就像一个严格的“安检员”，只放行 id, username, email 等字段，把密码永远锁在了后端。

                    代码虽然简短，但它是整个系统安全架构中不可或缺的一环。
                    利用 Pydantic 的白名单特性，在数据离开后端之前，完成了一次自动化的敏感数据脱敏。

            2.1.3 数据源级权限（ETL 脚本专属）
                ETL 脚本访问数据库和 API 时，遵循最小权限原则，严格管控数据源凭证：
                    1. 数据库权限：ETL 使用专属数据库账号，仅赋予源库SELECT权限、目标库INSERT/UPDATE权限，禁止使用高权限账号
                    2. API 权限：ETL 调用第三方 API 时，使用 AK/SK 签名认证，避免明文传输密钥，SK 使用环境变量加密存储，不硬编码在代码中
                    3. 凭证管理：生产环境使用 HashiCorp Vault 配置中心存储所有数据源凭证，脚本动态拉取，避免明文存放在.env文件或代码仓库中


        2.2 分层异常捕获与处理
            搭建全局异常拦截 + 业务场景专项异常处理机制，保证系统出现异常时能精准定位、正常回滚、及时告警，覆盖 ETL 脚本、Web 接口、数据库访问、
            外部 API 调用四大场景。

            2.2.1 自定义业务异常类
                统一业务异常结构，区分系统异常、业务异常、权限异常、数据异常，便于日志分类和告警：
                    app/exceptions/base.py

                    结构化的自定义异常处理机制，通常用于 Python Web 框架（如 FastAPI、Flask）或后端服务中。
                    它通过面向对象的方式，将业务逻辑中的错误与系统底层的异常区分开来，便于统一捕获和处理。

                    1. 核心基类：BusinessException
                        继承自 Exception：这是所有自定义异常的根节点。
                        标准化属性：强制要求每个业务异常必须包含三个要素：
                            - code：业务状态码（如 400, 403, 500 等），用于前端或调用方判断错误类型。
                            - message：面向用户的简短提示信息。
                            - detail：可选的详细信息，通常用于开发调试或记录日志。
                        调用 super().__init__(self.message)：将 message 传递给 Python 内置的 Exception，这样当异常未被捕获直接打印时，
                        也能看到可读的报错信息。
                    2. 具体业务异常子类
                        代码定义了三个具体的异常，分别对应不同的业务场景：
                            - PermissionDeniedException (权限不足)
                                默认 code=403。
                                适用场景：用户尝试访问没有权限的资源或执行越权操作。
                            - DataInvalidException (数据校验失败)
                                默认 code=400。
                                适用场景：前端传入的参数缺失、格式错误，或数据库约束校验失败。
                            - ETLTaskException (ETL任务执行异常)
                                默认 code=500。
                                适用场景：数据处理、抽取、转换、加载等后台任务发生不可恢复的错误。
                    3. 代码设计的亮点与优势
                        1. 解耦业务与框架：框架抛出的异常（如 ValueError, KeyError）通常是系统级的，而 BusinessException 是业务级的。
                            两者分开处理，逻辑更清晰。
                        2. 默认值机制：子类通过设置默认参数（如 message="权限不足"），在业务代码中抛出异常时可以极简调用，
                            例如 raise PermissionDeniedException()，无需每次都传参；同时也支持自定义覆盖，
                            如 raise PermissionDeniedException("您无权删除此文章")。
                        3. 便于全局异常处理器拦截：在 Web 框架中，通常只需注册一个针对 BusinessException 的全局拦截器，
                            就能自动将 code、message 和 detail 转换为标准的 JSON 响应格式返回给前端，避免在业务代码中到处写 return jsonify(...)。
                    优化：
                        添加枚举体系
                            将状态码（code）用 Enum（枚举）管理，是后端开发中非常推荐的工程化实践。
                            能彻底消除代码中的“魔法数字”，让错误码集中维护，且支持 IDE 自动补全和类型检查。
                        优势：
                            1. 告别魔法数字：业务代码中不再出现 raise BusinessException(code=40001, ...) 这种容易写错且难以理解的代码，
                                    而是变成语义清晰的 raise DataInvalidException(detail="缺少必填字段")。
                            2. 集中管理：如果未来需要修改某个错误的默认提示文案，只需在 ErrorCode 枚举中修改一处，全局生效。
                            3. HTTP 状态码与业务码解耦：枚举中同时包含了 http_status（如 400）和 code（如 40001）。
                                    全局异常处理器返回响应时，可使用 http_status 作 HTTP 响应码，将 code 放在 JSON Body 中供前端做业务逻辑判断。
                            4. IDE 友好：在编写代码时，输入 ErrorCode. 即可看到所有可用的错误类型，极大降低出错率。

                    应用(其实下面马上就会用到)：
                        from fastapi import Request
                        from fastapi.responses import JSONResponse

                        @app.exception_handler(BusinessException)
                        async def business_exception_handler(request: Request, exc: BusinessException):
                            return JSONResponse(
                                status_code=exc.http_status,
                                content={
                                    "code": exc.code,
                                    "message": exc.message,
                                    "detail": exc.detail
                                }
                            )

                    在main.py中注册全局异常处理器：
                        main.py

            2.2.2 FastAPI 全局异常处理器
                拦截所有异常，统一返回标准错误响应，同时记录全链路日志，方便问题追踪：
                    app/api/error_handlers.py

                    构建了一个企业级的三层异常防护网。
                    1. 整体架构设计
                        代码封装在 register_exception_handlers(app: FastAPI) 函数中。
                        这种工厂函数模式非常优雅，主程序（main.py）只需调用这一行代码，就能把复杂的异常处理逻辑全部注入到 FastAPI 应用中，
                        保持了主程序的整洁。
                    2. 第一层防线：业务异常处理器
                        business_exception_handler
                        - 拦截目标：专门捕获自定义的 BusinessException 及其所有子类（如 PermissionDeniedException 等）。
                        - 核心优化（HTTP 状态码与业务码解耦）：
                            以前直接用 exc.code 作为 HTTP 响应码，但自定义的业务码（如 40001）不是合法的 HTTP 状态码，会导致网关或前端报错。
                            现在改为使用 status_code=exc.http_status（如 400, 403, 500），确保 HTTP 协议层绝对标准。
                            真正的业务码 exc.code 被放到了 JSON 响应的 Body 中，供前端做具体的业务逻辑判断。
                        - 日志记录：使用 logger.error 记录请求地址和异常详情，方便排查业务逻辑问题。
                    3. 第二层防线：参数校验异常处理器
                        validation_exception_handler
                        - 拦截目标：这是新增的处理器，专门捕获 FastAPI + Pydantic 校验失败时抛出的 RequestValidationError
                            （比如前端少传了必填字段，或者类型传错了）。
                        - 统一响应格式：如果不拦截它，FastAPI 会返回它自己默认的错误格式。
                            拦截后，我们将其转换为与 BusinessException 完全一致的 JSON 结构（包含 code, message, detail）。
                        - 优势：前端只需要写一套统一的错误提示逻辑（Toast 弹窗等），不需要针对参数校验失败做特殊的兼容处理。
                            HTTP 状态码使用了标准的 422 Unprocessable Entity。
                    4. 第三层防线：全局兜底异常处理器
                        - 拦截目标：这是整个应用的“最后防线”。
                            所有没有被前两层捕获的、意料之外的系统级异常（如数据库断连、空指针、第三方接口超时等）都会被它兜住。
                        - 安全脱敏机制：
                            is_production = os.getenv("APP_ENV") == "production"
                            detail_msg = "系统繁忙，请稍后重试" if is_production else str(exc)
                        - 完整堆栈记录：使用 traceback.format_exc() 将完整的错误调用栈记录到日志中，这对于排查复杂的系统级 Bug 至关重要。

                    实现了三个关键目标：
                        1. 协议合规：HTTP 状态码绝对标准，业务码独立在 Body 中。
                        2. 格式统一：无论是业务报错、参数校验报错，还是系统崩溃，前端收到的 JSON 结构永远是一致的。
                        3. 安全与可维护性：生产环境自动隐藏敏感信息，开发环境保留调试细节；同时通过 loguru 留下了完整的排查线索。

            2.2.3 典型场景异常处理
                （1）ETL 脚本异常处理
                    在 ETL 的抽取、清洗、加载各步骤添加专属异常处理逻辑，支持重试、跳过脏数据、任务失败告警、数据库事务回滚：
                        app/etl/load/bulk_loader.py

                        数据库批量写入（Bulk Insert）异常处理范式。
                        在 ETL（抽取、转换、加载）流程中，数据入库是最后也是最关键的一环。这段代码不仅处理了数据，还妥善地管理了数据库事务和系统级异常。

                        1. 防御性编程：空数据快速返回
                            作用：在执行任何数据库操作之前，先检查传入的数据列表是否为空。
                            优势：避免了向数据库发送无意义的空 SQL 语句，减少了网络开销和数据库解析压力，提升了 ETL 任务的整体性能。
                        2. 数据清洗：exclude_unset=True
                            作用：这是 Pydantic V2 的一个非常实用的特性。它只导出在实例化时显式赋值过的字段。
                            优势：在批量插入时，如果前端或上游系统没有传入某个可选字段，exclude_unset=True 会将其从字典中剔除。
                                这样数据库在执行 INSERT 时，就会自动使用表结构中定义的 DEFAULT 默认值，而不是被强制覆盖为 None，
                                有效防止默认值失效问题。
                        3. 核心机制：事务回滚 (rollback)
                            作用：批量插入通常在一个数据库事务中进行，如果中途发生任何错误（如主键冲突、字段超长、数据库断连等），事务会处于失败状态。
                            优势：如果不执行 rollback()，数据库连接可能会一直处于“挂起”或“脏事务”状态，导致后续所有的 SQL 操作都会失败。
                                主动回滚确保了数据库的原子性（ACID 特性），保证了数据的一致性。
                        4. 异常转换：从系统异常到业务异常

                （2）接口权限异常处理
                    在权限校验逻辑中捕获权限异常，返回标准的 403 错误响应，同时记录非法访问日志，便于后续安全审计：

                （3）数据库 / API 访问异常处理
                    利用tenacity库实现网络异常、数据库连接异常的自动重试，重试失败后抛出业务异常，由全局处理器统一处理：

    3.2 接口性能优化四大维度
        先使用locust对接口进行压测，定位性能瓶颈，再从数据库层、缓存层、应用层、架构层四层优化，目标是将核心接口的 QPS 提升到 1000+，
        99% 响应时间控制在 100ms 以内。

        3.2.1 数据库层优化（核心）
            1. 索引优化
                为用户行为表设计覆盖索引，避免回表操作，减少数据库的随机 IO 开销，复用之前的联合索引，调整索引顺序，将等值过滤字段放在最前面，
                范围过滤字段放在最后：
                    -- 优化联合索引，适配按用户、按行为类型、按时间查询的场景
                    CREATE INDEX idx_user_action_created ON user_behaviors(user_id, action_type, created_at);
                    -- 为统计查询添加覆盖索引，避免回表
                    CREATE INDEX idx_user_created ON user_behaviors(user_id, created_at);
                使用explain analyze验证索引生效，确认Extra列显示Using index，表示触发覆盖索引，无需回表。
            2. SQL 语句优化
                - 禁止使用SELECT *，仅查询业务需要的字段，减少网络传输和内存开销
                - 优化大分页查询：用id > 上一页最大ID的方式替代OFFSET分页，避免越往后分页查询越慢：
                    # 优化后的分页查询，避免OFFSET大分页问题
                    query = db.query(UserBehavior).filter(
                        UserBehavior.user_id == user_id,
                        UserBehavior.id > last_max_id  # 上一页的最大ID，替代OFFSET
                    ).order_by(UserBehavior.id.asc()).limit(page_size)
                - 复杂统计 SQL 改用嵌套子查询或JOIN语句，避免在 SQL 中使用函数计算，减少 CPU 开销。
            3. 数据库架构优化
                - 读写分离：使用 SQLAlchemy 的RoutingSession实现读写分离，查询接口走只读从库，写入接口 / ETL 入库走主库，提升查询性能：
                    app/database.py
                - 分表分库：行为表按月分表，将历史冷数据归档到单独的存储节点，减少单表的数据量，提升查询和写入性能。

        3.2.2 缓存层优化
            采用多级缓存 + 精细化缓存策略，减少数据库查询次数，将热点数据的响应时间控制在 10ms 以内。
                1. 多级缓存架构
                    本地缓存：使用cachetools实现本地 LRU 缓存，存储热点字典数据（如行为类型映射表），有效期 5 分钟，避免重复请求 Redis
                    分布式缓存：使用 Redis 存储用户行为统计、用户行为列表等热点数据，采用 JSON 格式序列化，方便部分更新
                2. 缓存策略优化
                    Cache Aside Pattern：先写数据库，成功后删除缓存，保证缓存与数据库的最终一致性
                    缓存预热：系统启动时，异步将最近 7 天的热门用户行为统计数据加载到 Redis，避免缓存冷击穿
                    缓存穿透：使用布隆过滤器提前拦截非法用户 ID、不存在的行为类型查询，避免请求打到数据库
                    缓存击穿：对热点 key 添加互斥锁，避免缓存失效瞬间，大量请求打到数据库
                    缓存雪崩：设置缓存 TTL 时添加随机偏移量，避免大量 key 同时失效，导致数据库压力骤增
                3. 缓存代码优化
                    使用 Redis 管道批量执行缓存操作，减少网络往返次数，优化统计接口的缓存逻辑：
                        app/crud/behavior.py

        3.2.3 应用层优化
            1. 全链路异步化
                将同步数据库驱动、同步 HTTP 客户端替换为异步驱动，实现全链路异步，提升单接口的并发能力：
                    - 用asyncmy替代pymysql，使用异步数据库会话
                    - 用httpx.AsyncClient替代requests，异步调用第三方 API
                    - 用aioredis替代同步 Redis 客户端，异步执行缓存操作
            2. 接口合并与精简
                将多个并行的小接口合并为一个接口，减少 HTTP 往返次数，例如将「用户基本信息」「用户行为统计」
                「用户最近行为列表」三个接口合并为一个「用户中心数据」接口，一次性返回所有数据。
            3. 连接池优化
                调整数据库、Redis 连接池的大小，匹配 FastAPI 的工作进程数，避免频繁创建和销毁连接，减少网络开销：
                    app/database.py

        3.2.4 架构层优化
            1. 接口限流：使用slowapi+Redis 实现接口限流，限制普通用户的行为查询接口每分钟请求次数，避免恶意请求压垮服务：
                app/api/v1/behaviors.py
            2. 异步消息队列：将行为数据写入、ETL 同步操作改为异步执行，用 RocketMQ/Kafka 削峰填谷，接口直接返回任务受理状态，由消费者异步执行入库逻辑。
            3. 负载均衡：用 Nginx 配置 FastAPI 多实例负载均衡，提升系统整体并发能力，避免单实例 CPU 瓶颈。

五、生产级踩坑指南
    5.1 ETL 脚本坑
        增量同步断点续传：记录上一次同步的最大时间戳，采用last_modified > 上一次时间戳的方式增量抽取，避免重复抽取数据
        时区统一问题：数据库、ETL 服务器、API 服务端统一使用 UTC 时区，避免时间戳转换错误，导致漏同步 / 重复同步数据
        大批次入库死锁：批量入库时减小批次大小，按主键顺序插入，避免触发数据库的死锁机制
        API 限流与重试：抽取第三方 API 数据时，设置合理的请求间隔和重试次数，避免触发平台限流封禁
    5.2 权限控制坑
        JWT 密钥泄露：生产环境将SECRET_KEY配置在配置中心，不存放在代码或.env文件中，定期轮换密钥
        行级权限漏判：在数据库层拼接过滤条件时，注意对管理员角色做特殊处理，避免管理员无法查询所有数据
        敏感日志打印：禁止在日志中打印用户密码、JWT 令牌、数据库凭证等敏感信息，对敏感字段做脱敏处理
    5.3 接口优化坑
        缓存不一致：采用「先更新数据库，再删除缓存」的策略，同时设置缓存的短 TTL，保证最终一致性；对强一致场景，采用延时双删策略
        异步事务问题：全链路异步时，确保数据库事务的提交和回滚在异步上下文中执行，避免事务提交过早 / 过晚
        大响应体问题：接口返回大量数据时，采用流式响应或分片下载，避免占用过多内存，导致服务 OOM
        过度优化问题：先通过压测定位真实瓶颈，再针对性优化，避免提前优化、过度优化，增加代码维护成本
