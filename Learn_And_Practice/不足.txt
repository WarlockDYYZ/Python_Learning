自评：
    我写的时候意识到了最后一个数，不参与计算，甚至特意减一排除影响，没有考虑到覆盖原数据和会减少可能组合的情况；
    我以为复杂度是 n^2，实际应该是2^n，反过来了，下面是准确且客观的评价

1. 致命缺陷：破坏了原有的数字组合
    在你的代码中，你使用了一个 result 列表，既用来存“单个数字”，又用来存“相加后的和”。
    最严重的问题在于，你直接在原列表上做了修改（result[i] = result[i] + num）。
    让我们用你的测试用例 [1000, 2000, 3000] 来模拟一下：
        - 第一步：num = 1000，result 变为 [1000]。
        - 第二步：num = 2000，进入循环，result[0] 被修改为 1000 + 2000 = 3000。
                此时 result 变成了 [3000]，然后 append 2000，最终 result 是 [3000, 2000]。
        - 问题出现了：原本的 1000 已经消失了！当第三步 num = 3000 来的时候，
                你的程序已经永远失去了“1000 + 3000 = 4000”或者“1000 + 2000 + 3000 = 6000”这些组合的可能性，
                因为 1000 已经被你覆盖掉了。
    正确的动态规划思路是：计算新的和时，绝对不能修改上一轮已经存在的和，必须基于“旧的快照”去生成“新的和”
            （或者用倒序遍历来防止状态覆盖）。

2. 逻辑缺陷：if num not in result 的判断是无效的
    你原本的意图可能是想区分“这是第一次遇到这个数”还是“这个数已经存在”。
    但在子集和问题中，每个数字都是独立的个体。
    比如列表 [2000, 2000, 6000]，目标是 10000。我们需要用到两个 2000。
    你的 if num not in result 会导致逻辑混乱，因为它把“数值相等”和“是否是同一个元素”搞混了。

3. 复杂度缺陷：实际远超 O(n²)，且存在致命 Bug
    - 时间复杂度：假设列表里的数都不重复，你的 result 列表长度会随着 nums 遍历呈指数级增长（1, 2, 4, 8...）。
            你的内层循环 for i in range(len(result)-1) 会导致整体复杂度接近 O(2^n)，
            这在数字稍微多一点时就会直接卡死。
    - 致命 Bug：for i in range(len(result)-1) 这里你减了 1，
            导致每次都会漏掉 result 列表里的最后一个元素没有参与相加，这会漏掉大量可能的组合。
总结一下：
    虽然代码表面上只写了两个 for 循环（通常会觉得是 n×n），但因为内层循环的边界 len(result) 不是一个固定的 n，
    而是一个随着外层循环呈指数级爆炸增长的变量，所以它直接把算法拖进了指数级复杂度的“深坑”。
    这也是为什么在处理子集和问题时，必须用动态规划（O(n×target)）来代替这种暴力枚举的原因。
