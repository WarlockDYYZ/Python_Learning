D2：数据清洗 + 日期/渠道筛选 + 筛选联调

    generate_data.py

    造一份“带脏”的电商日度渠道销售表，用于后续的数据清洗、异常检测、指标口径对齐等练习或测试。

    一、整体结构

        import 标准库
            ↓
        generate_sales_data(n_days, seed)   # 纯函数：返回一个带问题的 DataFrame
            ↓
        main()                              # 工程外壳：建目录、落盘 CSV、打印数据画像
            ↓
        if __name__ == "__main__": main()   # 可被 python 直接跑，也可被别的脚本 import

        生成逻辑和 I/O 完全解耦；想把同一份数据喂给单元测试、Airflow 任务或 Notebook，只需调用 generate_sales_data()，不用改任何代码。


    二、头部：路径与环境

        把项目根目录塞进模块搜索路径，这样从 scripts/ 里也能 import src.xxx。两点提醒：
            1. __file__ 在交互式环境（Jupyter / python -c）下不存在，会抛 NameError。

    三、核心：generate_sales_data

        1. 可复现性
            np.random.seed(seed)
            设置固定种子，确保生成的结果可复现，生产环境通常会把 seed 做成参数并记录到元数据里。

        2. 维度定义
            时间：从 2025-09-01 起 365 天 → 覆盖到 2026-08-31。
            渠道：抖音、小红书、淘宝、微信、自然流量（5 个）。
            基础体量 base_gmv 体现渠道差异：淘宝 1500 > 抖音 1200 > 小红书 800 > 微信 600 > 自然流量 400。
            注意：此时生成的数据只有水平差异，没有趋势和季节性，所以生成的数据是“平稳的”，适合练清洗，不适合练趋势预测。

        3. 双层循环
            每天 × 每渠道 = 1825 行，量级很小，循环完全够用；而且每个单元格都要独立抽随机数，写成循环反而比 np.where 堆叠更易读。
            如果行数上百万，就该改成向量化：先生成 (n_days, n_channels) 的随机矩阵再 melt。

        4. GMV 的生成公式
            gmv = base * noise * weekend_factor * holiday_factor
            典型的乘法分解模型，对应真实业务里的“基线 × 随机扰动 × 周期效应 × 事件效应”。
            因子	    代码	                            含义      	细节
            基线	    base_gmv[ch]	                渠道固有体量	决定量纲
            噪声	    np.random.lognormal(0, 0.25)	日内随机波动	中位数 = e⁰ = 1，所以不改变基线期望；
                                                                σ=0.25 时约 95% 落在 [0.61, 1.64]。
                                                                用对数正态而非正态，是为了保证 GMV 恒正且右偏——真实销售额就是右偏的
            周末效应	0.85 if d.weekday()>=5 else 1.0	周末跌 15%	weekday() 返回 0=周一、...、6=周日，所以 5/6 即周六日
            事件效应	一系列 if/elif	                大促翻倍	    互斥（elif），同一天只取最高档
            【1】

        5. 其他指标-派生指标：自顶向下造数
            “从 GMV 倒推漏斗”的做法，优点是指标之间天然自洽（不会出现点击大于曝光这种荒谬值），缺点也很明显：
                相关性过强：曝光、点击、成本全部由 GMV 线性派生，算出来的相关系数会接近 1。
                        真实数据里成本是投放预算驱动的，常常先于 GMV 变化。用它练回归/归因，模型会拿到“作弊级”的信号。
                max(0, ...) 在这里是冗余的（正数取整不可能为负），但作为防御式编程保留也无妨。
                没有 order_count（订单数）和 uv，导致没法算客单价 gmv/orders，后续练习转化率时会有点受限。
            【2】

        6. 引入脏数据环节
            ① 缺失值（20 行 gmv → NaN）
                无放回抽样保证 20 个不同行。
                最常见的“系统丢数”场景，练 fillna、插值、以及“缺失是否非随机（MNAR）”的判断。
                注意它只污染 gmv，同行的 cost 还在——这会导致 ROI = gmv/cost 变成 NaN。
            ② 异常尖峰（10 行 gmv ×6）
                先抽再剔除已缺失的行，避免“尖峰被 NaN 覆盖而消失”。
                【3】
                ×6 的放大倍数很讲究：它落在“看起来像真的、但又明显离谱”的区间——不会被 3σ 规则轻易当成录入错误删掉，却又足以拉高日均 GMV。
                这是练稳健统计（中位数、截尾均值、IQR fences、Isolation Forest）的典型靶子。
            ③ 重复行（追加 8 行）
                整行复制后 concat，而不是 df.duplicated() 那种标记。
                这样做的好处是：重复行继承了该行已有的所有毛病（NaN、×6 尖峰都会被原样复制），能制造出“同一个尖峰出现两次”的复合问题，
                非常贴近 ETL 重跑造成的真实重复。
            ④ 排序重置
                两个作用：一是让 CSV 肉眼可读；二是打乱注入顺序，让清洗者无法靠“问题都堆在尾部”来作弊。
                reset_index(drop=True) 也很关键，否则索引会带两套 0~1824，后续按位置切片必出错。


    四、main：主函数
        目录结构遵循经典的 data/raw 分层（raw → processed → feature），exist_ok=True 保证幂等可重跑。
        encoding='utf-8-sig'：写入 BOM，让 Excel 双击打开不乱码。
        中文环境，但要注意下游若是 Spark/Hive 读取，BOM 会让第一列列名变成 \ufeffdate，引发 KeyError。
        结尾那段 print 是数据画像自检：行数、列名、日期范围、渠道枚举、缺失统计、重复计数。
        【4】
        预期输出：1825 + 8 = 1833 行，9 列，日期 2025-09-01 ~ 2026-08-31，gmv 缺失 20 行，duplicated() 报 8 行（若复制的 8 行互不相同）。

    二、代码拆解
        0. 日志与签名
            用 __name__ 命名 logger、用 type hint 标输入输出、docstring 写了步骤和 Args/Returns，工程习惯。
            【6】

        1. 去重
            经典的计数错误：
                duplicated(keep=False) 标记的是所有参与重复的行（包括每组第一次出现的那一行）。
                drop_duplicates(keep="first") 删掉的是每组里除了首行之外的行。
            所以 n_dups ≠ 删除行数。
            以上游生成器为例：追加了 8 行副本，若这 8 行各自对应不同的原行，则 dup_mask.sum() == 16，
            日志会打印"去除重复行: 16 行"，实际只删了 8 行，夸大一倍。
            【7】
            另外两个细节：
                drop_duplicates() 默认看全部列。将来如果给数据加了 id / batch_id 这种唯一键，去重会瞬间失效（因为整行不再完全相同）。
                        应显式指定业务主键：subset=["date", "channel"]。
                pandas 的 duplicated 把 NaN 视作相等。所以两条 gmv 同为 NaN 的完全重复行会被正常合并，符合预期，但值得知道。

        2. 日期
            errors="coerce" 把非法字符串变成 NaT，再统一删掉，这是处理脏日期的标准做法。
            日志用 WARNING 报不可解析条数也合适（属于数据质量问题，不该静默）。
            两点优化：
                1、记录被删掉的原始日期字符串长什么样（df.loc[df["date"].isna(), "date"].unique()），否则不知道是格式问题还是真的乱码；
                2、删完后应校验日期范围是否合理（有没有 1970 年、有没有未来日期、跨度是否覆盖预期区间）

    filters.py

    一、logger = logging.getLogger(__name__) 的意义
        Python 标准库 logging 模块的推荐写法，核心作用是创建一个与当前模块绑定的日志记录器。

        1. __name__ 的作用
            __name__ 是当前模块的名字（比如在 filters.py 里就是 "filters"）。
            用模块名作为 logger 的名字，日志输出时会带上来源，比如：
                INFO filters 日期筛选 >= 2025-01-01: 保留 1000 行
            这样在大型项目里，一眼就能看出是哪行代码打的日志。

        2. 层级继承
            Python 的 logger 是树状结构。
            getLogger(__name__) 创建的 logger 会自动继承根 logger 的配置（输出格式、级别、输出到文件还是控制台等），
            不需要每个模块单独配置 handler。

        3. 为什么不用 print
            print 无法分级、无法关闭、无法重定向到文件。
            用 logging 可以在生产环境把级别调到 WARNING 以上，这些 info 日志就自动不输出，零开销。


    二、filter_by_date 的功能
        在 DataFrame 中按 date 列做闭区间筛选，返回 start_date <= date <= end_date 的行：
            - 两个参数都是可选的：只传 start_date 就是"大于等于某日"，只传 end_date 就是"小于等于某日"，都传就是区间，都不传就是原样返回。
            - 返回的是新 DataFrame（不影响原对象），且索引被重置为 0, 1, 2...


    三、编写逻辑拆解
        mask = pd.Series(True, index=df.index)
        整段代码最巧妙的地方。
        它创建了一个全为 True 的布尔序列，长度和 df 一致。
        这样后面不管有没有传日期参数，都可以统一用 &= 做"与"操作：
            - 如果 start_date 和 end_date 都没传，mask 全程保持全 True，df[mask] 就是原表。
            - 如果只传了 start_date，mask 先被更新成 date >= start_dt，然后 end_date 分支不执行，最终只按起始日筛选。
            - 如果两个都传了，mask 先后被 &= 两次，最终是同时满足两个条件的行。
        这种写法比"先判断参数再分别写 if-elif-else"要简洁得多，而且天然支持扩展（比如再加一个 end_time 参数，直接再加一行 &= 就行）。

        mask &= df["date"] >= start_dt
        这里 &= 是逐元素逻辑与，等价于 mask = mask & (df["date"] >= start_dt)。
        注意必须加括号，因为 & 的优先级高于 >=。

        return df[mask].reset_index(drop=True)
        布尔索引取出满足条件的行，reset_index(drop=True) 把索引重新排成 0, 1, 2...，避免筛选后索引断层。
        （比如原来索引是 0, 5, 8, 12，下游按位置取值会出错）

    四、filter_by_channel
        1. 提前返回（Early Return）
            channels=None 语义是"不筛选"，直接原样返回，避免后续无意义的集合运算。
            guard clause(防卫子句) 写法，减少嵌套层级。

        2. 用集合交集做"容错匹配"
            整段函数最关键的逻辑。
            & 是集合交集，意思是：只保留"用户请求的"且"数据里真实存在的"渠道。
            这样做的好处是不会因为用户多写了一个不存在的渠道就直接崩溃，而是尽量满足能匹配的部分。

        3. 全不匹配时抛错
            如果交集为空（用户请求的渠道一个都不在数据里），说明筛选条件完全无效，继续跑下去会得到空表。
            这里主动抛 ValueError，并把可用渠道列出来，方便调用方排查——比如是不是渠道名拼错了（"douyin" vs "抖音"）。

        4. 差集做警告
            - 是集合差集，算出"用户要了但数据里没有"的渠道。
            这一步其实是对第二步的补充说明：
                交集已经拿到了能用的部分，但用户可能不知道自己写的某些渠道被静默丢弃了，所以打个 warning 提醒。

        5. 布尔索引筛选
            最后用 isin 取出匹配的行，打日志，重置索引返回。

    五、filter_df
        前面两个筛选函数的"组装层"，负责把日期和渠道筛选串成一条流水线。
        1. 整体结构：链式调用
            典型的 pipeline 模式：上一步的输出作为下一步的输入。先按日期切出时间窗口，再在时间窗口内按渠道过滤。
            顺序上其实可以互换，但通常先日期后渠道更合理——因为日期筛选往往能砍掉更多数据，减少后续 isin 的计算量。

        2. 去重操作
            drop_duplicates() 默认对所有列做去重，即只有两行在所有列上完全一致才会被删掉。
            这里放去重的意图是兜底——防止上游数据本身有重复行，筛选后仍然残留。
            注意：如果原始数据里有唯一标识列（比如 id、batch_id），drop_duplicates() 会完全失效，因为每行的 id 都不同，永远不可能重复。
                真正有意义的去重应该在清洗阶段按业务主键（比如 date + channel + product）做一次，筛选层不该再管这件事。

        3. 空结果校验
            防御性编程：如果筛选条件太严导致结果为空，主动报错而不是让空表流到下游（下游算均值、求和时会得到无意义的结果或报错）。
            【17 两个优化点】

        4. 日志
            在 pipeline 末尾打一条汇总日志，方便追踪数据量变化。
            可修改未同时记录输入行数，形成"输入 → 输出"的对比，比如：【18】
                logger.info(f"筛选完成: {len(df)} → {len(result)} 行")

    六、三个函数的协作关系

        df (原始数据)
          ▼
        filter_by_date()   ← 切时间窗口
          ▼
        filter_by_channel() ← 切渠道子集
          ▼
        drop_duplicates()   ← 兜底去重（建议移除）
          ▼
        assert / ValueError ← 空结果拦截
          ▼
        result (干净子集)

        filter_by_date 和 filter_by_channel 是原子操作，各自独立可复用；filter_df 是组合操作，提供一键筛选的便利接口。
        这种"原子 + 组合"的分层设计是工程上的好习惯——下游如果只需要按日期筛，直接调 filter_by_date 就行，不用被迫带上渠道参数。

    二、日期筛选函数测试类 TestFilterByDate
        1. test_full_range：正常日期范围筛选
            最常见的使用场景：给定一个完整的月份区间，筛选结果应该满足：
                - 结果非空：len(result) > 0，说明数据里确实有 9 月的记录。
                - 下边界正确：最小日期 ≥ 2025-09-01，没有漏掉起始日之前的数据。
                - 上边界正确：最大日期 ≤ 2025-09-30，没有超出结束日。
            三条断言合起来就是：结果严格落在 [start_date, end_date] 闭区间内。

        2. test_single_day：单日边界测试
            专门测起止日期相同的边界情况：
                - start_date == end_date 时，区间退化为一个点，语义上应该只保留这一天的数据。
                - all(result["date"] == pd.Timestamp("2025-09-15")) 确保所有行的日期都精确等于这一天，不会混入相邻日期的数据。
            这个用例能暴露一个常见 bug：如果实现里用了 > 或 < 而非 >= / <=，单日筛选就会返回空表。
            【22 可选优化项】

        3. test_no_overlap：无交集筛选
            筛选区间与数据完全不重叠的情况。
                - 数据是 2025 年 9 月生成的，筛选 2020 年 1 月，显然不会有匹配行。
                - 断言结果为空，确保函数在这种情况下不会报错、不会返回脏数据，而是干净地返回一个空 DataFrame。
            这里有一个设计上的取舍：
                filter_by_date 本身允许返回空表（它不抛异常），但上层的 filter_df 会在最后用 assert 拦截空结果。

    三、渠道筛选函数测试类 TestFilterByChannel
        1. test_single_channel：单渠道筛选
            最基础的使用场景：
                - 传入单个渠道名 ["抖音"]，结果非空。
                - all(result["channel"] == "抖音") 确保每一行的 channel 列都是 "抖音"，没有混入其他渠道的数据。
            这是最直接的"筛选后数据纯净性"校验。

        2. test_multiple_channels：多渠道筛选
            验证传入多个渠道时：
                - 结果非空。
                - set(result["channel"].unique()).issubset({"抖音", "淘宝"}) 用集合的 issubset 断言：
                    结果中出现的所有渠道必须是请求渠道的子集。
            这里用 issubset 而不是 == 是更稳妥的写法——因为数据里可能只有 "抖音" 没有 "淘宝"，结果集是 {"抖音"}，
            它仍然是 {"抖音", "淘宝"} 的子集，用例不会误报失败。

        3. test_nonexistent_channel：不存在的渠道应报错
            验证请求的渠道在数据中完全不存在时，函数应抛出 ValueError。
                - pytest.raises(ValueError) 是 pytest 的上下文管理器，断言代码块内必须抛出指定异常，否则测试失败。
                - 这里故意传了一个带空格的 " nonexistent_channel "，既测试了"渠道不存在"的分支，也顺带验证了空格不会意外匹配到真实渠道
                    （如果实现里有 strip() 处理，这个用例可能会因为匹配不到而抛错，取决于具体实现）。

        4. test_none_channels：不传渠道应原样返回
            验证 channels=None 的语义是"不筛选"：
                - 返回的 DataFrame 行数与输入完全一致，说明函数直接透传了原始数据，没有做任何过滤。
            这是对 guard clause（提前返回分支）的测试，确保"不传参数"不会误触发后续逻辑。

    metrics.py
    指标计算模块

    一、calc_channel_summary 渠道维度聚合及衍生指标计算
        1. 核心聚合：groupby + 命名聚合
            pandas 的命名聚合语法（Named Aggregation），是 0.25 版本之后推荐的写法：
                - groupby("channel")：按渠道分组，每个渠道变成结果中的一行。
                - total_gmv=("gmv", "sum")：语义是"对 gmv 列求和，结果列名叫 total_gmv"。
                - days=("date", "nunique")：用 nunique（去重计数）算出该渠道在数据中覆盖了多少个不同的日期，后面算日均 GMV 要用。
                - .reset_index()：把 channel 从索引变回普通列，方便后续计算和展示。
            一步到位，不用先 agg 再 rename，代码可读性很好。

        2. 衍生指标：用 np.where 做除零保护
            四个衍生指标：
                指标	            公式	                    含义
                ctr	            点击量 / 曝光量 × 100	    点击率（%）
                cpc	            花费 / 点击量	            单次点击成本
                gmv_per_user	GMV / 新用户数	        单用户贡献 GMV
                avg_daily_gmv	总 GMV / 天数	        日均 GMV
            关键在于除零保护：np.where(分母 > 0, 分子/分母, 0)。
            如果分母为 0（比如某个渠道没有曝光），直接除会得到 inf 或 NaN，用 np.where 兜底成 0，避免下游计算炸掉。
            np.where 是向量化操作，比逐行 apply 快得多，在数据量大时优势明显。

    二、calc_weekly_comparsion 计算周环比并对比
        先把数据按“周 + 渠道”聚合，再用 shift(1) 拿到每个渠道上一周的 GMV，最后算环比。
        1. 函数整体流程
            s1:df.copy()：避免修改原始 DataFrame，符合数据分析函数的好习惯。
            s2:生成两个周维度列：
                - week：ISO 周数，1–53。
                - year_week：形如 2025-W39，方便按自然周分组展示。
            需要注意的是，isocalendar().week 和 strftime("%U") 的周划分规则不完全一样。
            前者是 ISO 周，后者是“以周日为起始的周数”。如果数据跨年，可能会出现 year_week 和 ISO 周不一致的情况。
            生产环境里更推荐统一用 ISO 年周，比如：
                【29 一个待优化项】

        2. 按周和渠道聚合
            把原始明细数据压缩成周度渠道表：
                - 每个 (year_week, channel) 组合变成一行。
                - weekly_gmv 是该渠道该周的 GMV 总和。
                - weekly_clicks、weekly_cost 同理。

        3. shift(1)
            shift(1) 是 pandas 里非常常用的错位取值方法。
            它的含义是：把当前列的值整体向下移动 1 行。
            groupby("channel") 保证了每个渠道内部独立错位。
            排序后的数据可能是这样的：
                year_week	channel	weekly_gmv
                2025-W38	抖音	    100
                2025-W39	抖音	    150
                2025-W40	抖音	    130
                2025-W38	淘宝	    80
                2025-W39	淘宝	    90
            执行 groupby("channel")["weekly_gmv"].shift(1) 后：
                year_week	channel	weekly_gmv	prev_gmv
                2025-W38	抖音	    100	        NaN
                2025-W39	抖音	    150	        100
                2025-W40	抖音	    130	        150
                2025-W38	淘宝	    80	        NaN
                2025-W39	淘宝	    90	        80
            可以看到：
                - 每个渠道的第一周，prev_gmv 是 NaN，因为没有“上一周”的数据。
                - 第二周开始，prev_gmv 就是该渠道上一周的 weekly_gmv。
                - 淘宝的 prev_gmv 不会误取到抖音的数据，因为 groupby("channel") 做了隔离。
            如果不加 groupby("channel")，直接 shift(1)，就会把抖音的上一周错配到淘宝上，结果完全错误。

        4. 环比计算
            环比 = (本周GMV - 上周GMV) / 上周GMV × 100
            np.where 做了两层保护：
                - prev_gmv.notna()：排除第一周没有上周数据的情况。
                - prev_gmv > 0：排除上周 GMV 为 0 的情况，避免除零。
            不满足条件时返回 None，表示“无法计算环比”。

        【30 一个优化点关于计算后的类型统一】

        5. 总结
            步骤	        代码	                                        作用
            生成周列	    dt.isocalendar().week / strftime	        把日期映射到自然周
            周度聚合	    groupby(["year_week", "channel"]).agg(...)	每个渠道每周一条汇总
            取上周值	    groupby("channel")["weekly_gmv"].shift(1)	每个渠道独立错位取上一周 GMV
            算环比	    np.where(...)	                            有上周数据且上周 GMV > 0 时才计算
            shift(1) 本质就是“取上一行”，配合 groupby 就变成了“取同组上一行”，是做环比、同比、移动平均时最常用的工具之一。


    三、calc_top_channels 排序取 Top N 及 calc_daily_trend 按天汇总趋势
        1. calc_top_channels
            流程为：
                a. groupby("channel")["gmv"].sum()：按渠道汇总 GMV，得到一个 Series，索引是渠道名，值是 GMV 总和。
                b. sort_values(ascending=False)：按 GMV 从高到低排序。
                c. head(top_n)：取前 top_n 个，默认是 3。
            返回值是一个 Series，不是 DataFrame。如果下游需要表格形式，可以加一步：
                return channel_gmv.head(top_n).reset_index(name="total_gmv")
            这样会变成两列：channel 和 total_gmv，更方便画图或导出。

        2. calc_daily_trend
            按日期维度做汇总：
                a. groupby("date")：每天一行。
                b. 聚合出当天的 GMV、点击、花费、曝光。
                c. 最后算一个日度点击率 daily_ctr，同样用 np.where 做了除零保护。
            函数返回的表很适合画折线图：x 轴是 date，y 轴可以选 daily_gmv 或 daily_ctr，一眼就能看出趋势波动。

    charts.py

    一、加载样式配置 及 _get_colors 获取配色方案 及 plot_daily_gmv_trend 绘制每日 GMV 趋势折线图
        1. 加载样式
            把图表样式从代码里抽离出来，放到 style.json 里统一管理：
                - os.path.dirname(__file__)：当前脚本所在目录。
                - os.path.join(..., "..", "config", "style.json")：往上退一层，再进入 config/style.json。
                - 用 json.load 读成字典，后面所有图表都从 STYLE 里取字号、宽高、DPI、配色等参数。
            好处是：改样式不用动绘图函数。比如要统一把 DPI 从 100 改成 200，只改 JSON 就行，所有图表自动生效。
            这段代码在模块导入时就执行。如果 style.json 不存在或格式错误，整个模块会直接报错。

        2. 循环取色
            这是一个内部工具函数（以下划线开头），负责按数量取配色：
                - STYLE.get("colors", [...])：优先用 JSON 里的配色，没有就用默认五色调。
                - i % len(colors)：取模循环。比如只有 5 个颜色但需要 8 个，第 6 个会回到第 1 个颜色，不会越界。
                - 返回值是颜色列表，供 ax.plot、ax.barh、ax.scatter 使用。
            这种设计让渠道数量变化时配色仍然稳定，不会因为渠道从 3 个变成 7 个而报错。

        3. plot_daily_gmv_trend：每日 GMV 折线图
            先创建画布，宽高从配置里取，保证所有图表尺寸一致。
            a. 主折线 + 填充
                - ax.plot：画日 GMV 折线，取第一个颜色，线宽 2，无标记点。
                - ax.fill_between：在折线下方做浅色填充（alpha=0.1），增强视觉层次，让趋势更"饱满"。
            b. 日移动平均线
                - rolling(7).mean()：7 日滑动平均，平滑掉单日波动，更容易看出趋势方向。
                - 虚线样式 -- + 第二个颜色，和主折线区分开。
                - if len(daily_df) > 7 是保护：数据不足 7 天时 rolling(7) 会产生大量 NaN，画出来没意义。
            c. 日期轴格式化
                这是时间序列图的关键部分：
                    - WeekdayLocator(interval=1)：每个工作日放一个刻度（周一到周五）。
                    - DateFormatter("%m-%d")：刻度标签显示为"月-日"，如 09-15。
                    - rotation=45：日期标签旋转 45°，避免重叠。
            d. 标题、标签、图例、网格
                - fontweight="bold"：标题加粗。
                - legend：显示"日GMV"和"7日移动平均"两个图例。
                - grid(alpha=0.3)：浅灰色网格，辅助读值但不抢眼。
                - plt.tight_layout()：自动调整边距，防止旋转后的日期标签被裁掉。
            e. 保存与关闭
                - plt.savefig：保存到指定路径，DPI 从配置取。
                - bbox_inches="tight"：裁剪多余白边，确保标签不被裁掉。
                - plt.close(fig)：非常重要。批量生成多张图时，不 close 会持续占用内存，最终导致 OOM。
                - 返回 save_path，方便调用方知道保存到了哪里。

    一、设置日志 和 load_rules 加载规则配置
        异常检测模块的基础设施：日志记录和规则配置加载。
        1. 设置日志
            Python 标准库 logging 的初始化配置，核心做了三件事：
                a.日志级别
                    level=logging.INFO：只记录 INFO 及以上级别（INFO、WARNING、ERROR、CRITICAL）的日志。
                    DEBUG 级别的日志会被过滤掉。
                    生产环境通常设 INFO，调试时改成 DEBUG。
                b. 日志格式
                    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s"
                    定义了每条日志的模板：
                        占位符	            含义	            示例输出
                        %(asctime)s	        时间戳	        2025-09-15 14:32:01,123
                        %(levelname)s	    级别名	        INFO、WARNING
                        %(name)s	        logger 名称	    __main__、anomaly_detector
                        %(message)s	        日志内容	        已加载异常检测规则: [...]
                    组合起来长这样：
                        2025-09-15 14:32:01,123 [INFO] __main__: 已加载异常检测规则: ['抖音', '淘宝', '快手']
                c. 双输出目的地（handlers）
                        FileHandler：把日志同时写入 logs/run.log 文件，方便事后审计和排查。
                        StreamHandler：把日志输出到标准输出（控制台/终端），方便运行时实时观察。
                    这就是所谓的双写——文件存档 + 控制台实时看，调试和生产都能用。
                    注意：
                        basicConfig 只在日志系统第一次配置时生效。
                        如果前面已经有 handler 被添加过，再调用 basicConfig 不会重复添加。
                        另外 FileHandler 的 logs/ 目录需要提前存在，否则文件写入会抛 FileNotFoundError。
                        更稳妥的写法是：
                            os.makedirs("logs", exist_ok=True)
                        放在 basicConfig 之前。

        2. load_rules：加载异常检测规则配置
            这个函数的职责很明确：从 YAML 配置文件里读异常检测规则，返回一个字典。
            参数设计
                config_path=None 用了 Python 常见的可选路径模式：
                    - 不传参数时：自动根据当前文件路径推导默认路径 config/rules.yaml（项目根目录下的 config 文件夹）。
                    - 传参时：可以指定任意路径，方便单元测试用内存中的假配置覆盖。
            文件读取
                - 用 yaml.safe_load 而不是 yaml.load，这是安全规范——safe_load 不会执行 YAML 中的任意 Python 对象，
                    防止配置文件被注入恶意代码。
                - 编码指定 utf-8，避免 Windows 上默认编码不一致导致乱码。
            日志记录
                加载成功后打一条 INFO 日志，把渠道规则的关键打印出来，方便确认配置是否生效。
                用了 .get('channel_rules', {}) 做兜底，即使配置里没写 channel_rules 键也不会报错。
            典型的 rules.yaml:

                  method: iqr

                channel_rules:
                  抖音:
                    method: mad

                  淘宝:

    二、detect_anomaly_mad 中位数绝对偏差异常检测 和 detect_anomaly_iqr 四分位距异常检测
        两个函数都是稳健异常检测：不用均值和标准差，而是用中位数、四分位数，避免被极端值带偏。
        1. detect_anomaly_mad：中位数绝对偏差
            逻辑是：
                a.找中心：center = series.median()，用中位数而不是均值。
                b.算偏差：abs(Xi - median)，看每个点离中位数有多远。
                c.取典型偏差：对这些绝对偏差再取中位数，得到 MAD。
                d.校正尺度：乘以 1.4826，让 MAD 在正态分布下近似标准差。
                e.判定异常：如果某点偏离中位数超过 k * MAD，就判为异常。
            max(mad, 1e-6) 是为了防止 MAD 为 0。比如数据全是同一个值，MAD 就是 0，不保护一下就会除以 0 或阈值失效。
            MAD 的优点是抗污染能力强：即使数据里有不少极端值，中位数和中位数绝对偏差也不会被轻易拉偏。

        2. detect_anomaly_iqr：四分位距
            逻辑是：
                a.算 Q1、Q3：25% 分位数和 75% 分位数。
                b.算 IQR：IQR = Q3 - Q1，表示中间 50% 数据的跨度。
                c.定边界：
                    下界：Q1 - k * IQR
                    上界：Q3 + k * IQR
                d.判定异常：低于下界或高于上界的点视为异常。
            这就是箱线图里识别离群点的经典规则，k=1.5 是 Tukey 提出的常用标准。

        对比：
            维度	        MAD	                IQR
            中心估计	    中位数	            Q1/Q3
            离散度量	    绝对偏差的中位数	    四分位距
            抗极端值能力	更强	                较强
            适用场景	    数据可能有少量剧烈尖峰	通用异常筛查、箱线图思路
            参数含义	    k=3 类似 3σ 规则	    k=1.5 是箱线图默认

        在模块中给 detect_anomalies 提供了两种检测引擎：
            配置里写 method: mad 就走 MAD，写 method: iqr 就走 IQR。
            这样不同渠道可以用不同敏感度，比如波动大的渠道用更严格的 MAD，波动小的渠道用默认 IQR。

    三、detect_anomalies 整个异常检测模块的主调度函数
        按渠道分组，给每个渠道匹配规则，调用 MAD/IQR 检测器，最后把异常行拼成一张表。
        1. 加载规则
            如果外部没有直接传入规则字典，就从 config/rules.yaml 加载。这样既支持配置化运行，也方便测试时直接传入假规则。

        2. 取出渠道规则与全局兜底规则
            channel_rules：各渠道自己的检测配置，比如抖音用 MAD、淘宝用 IQR。
            global_rule：默认规则。如果某个渠道没有单独配置，就用全局规则兜底。

        3. 按渠道分组检测
            这里按 channel 分组，每个渠道单独检测。
            不同渠道的 GMV 量级、波动性可能差很多，如果混在一起检测，小渠道的异常会被大渠道淹没。

        4. 选择检测方法
            根据配置里的 method 字段选择检测器。如果配置写错了，不会直接崩溃，而是降级到 IQR 并打一条 WARNING 日志。

        5. 收集异常行
            只有确实检出异常时才记录日志，避免日志里全是"未检测到异常"的噪音。

        6. 计算偏离度
            偏离度 = 该点偏离中位数的距离 / 缩放后的 MAD。
            这个值比单纯标记"异常/正常"更有用：
                偏离度 5 和偏离度 50，严重程度完全不同。后续做报表时可以按偏离度排序，优先排查最严重的那些。

        7. 拼接结果并整理列顺序
            最后用 pd.concat 把所有渠道的异常拼成一张表，并按预设列顺序排列：
            用 existing_cols 过滤防止原始数据里没有某些列时报错。

    四、detect_anomalies_global 全局异常检测
        模块里的兜底检测：不按渠道分组，直接把整张表当成一个整体来筛异常。

            区别只是 center 和 spread 用的是全表数据。

            全局检测 vs 按渠道检测
            维度	        按渠道检测	            全局检测
            基准	        各渠道自己的中位数/IQR/MAD	全表统一的中位数/IQR/MAD
            能发现什么	某渠道自身的异常波动	    跨渠道的极端异常（如某渠道 GMV 远超其他所有渠道）
            灵敏度	    高，小渠道的异常不会被淹没	低，大渠道主导基准
            适用场景	    日常监控各渠道健康度	    快速扫一眼有没有"离谱"的数据

            使用建议
                两者可以配合使用：
                    a.先跑 detect_anomalies_global，看有没有跨渠道的极端异常（比如数据录入错误、单位搞错）。
                    b.再跑 detect_anomalies，按渠道细查各自的波动。
                注意：全局检测对量级差异大的数据不太友好。
                    比如抖音日均 GMV 100 万，小红书日均 1 万，全局中位数会被抖音主导，小红书的正常波动在全局视角下可能永远检不出异常，
                    而抖音的小幅波动反而可能被标成异常。
                    所以全局检测更适合量级相近的渠道，或者作为第一道粗筛。


    五、串联
        数据处理、可视化、异常检测三个模块串起来，整个项目就是一条完整的 ETL → 分析 → 出图 流水线。
        整体数据流：
            原始销售数据 (CSV/Excel)
                ↓
            数据清洗模块
            (load_and_clean, filter_data, compute_metrics)
                ↓
            中间数据 (daily_df, weekly_df, channel_summary)
                          ↓
                ↓         ↓              ↓
            可视化模块    异常检测模块    指标计算
            (plot_*)    (detect_*)    (ROI/CTR等)
                ↓         ↓              ↓
            PNG 图片     异常记录表     汇总指标
                ↓
            报告/告警/看板

        模块间的依赖关系：
            上游模块	产出	                            下游消费
            数据清洗	df（干净的销售表）	                可视化、异常检测
            指标计算	channel_summary（含 CTR/ROI）	可视化（渠道对比图）
            异常检测	anomalies.csv	                告警邮件/钉钉机器人
            可视化	PNG 图片	PDF                     报告/前端看板

        三个模块的分工：
            数据清洗模块：负责"把数据变干净"——去重、补空值、类型转换、日期解析。
            异常检测模块：负责"把问题数据揪出来"——用 MAD/IQR 识别异常行，输出偏离度。
            可视化模块：负责"把结论画出来"——趋势图、对比图、散点图，一图胜千言。
            三者通过 DataFrame 这个共同语言衔接：上游输出 DataFrame，下游接收 DataFrame。
            这样每个模块都可以独立测试、独立替换。
            比如以后想把 MAD 换成 Z-score，只需要改 anomaly_detection.py，其他两个模块完全不用动。

        可优化点：
            1. 统一入口配置：把日期范围、渠道列表、输出路径都提到一个 config.yaml 里，main() 只读配置。
            2. 异常告警：检测到异常时自动发钉钉/飞书消息，带上偏离度最高的几条。
            3. 定时调度：用 cron 或 Airflow 每天凌晨跑一次，自动生成昨日报告。
            4. 缓存中间结果：清洗后的 df 存成 Parquet，避免每次都从原始 CSV 重算。



    exporter.py
    用 openpyxl 从零构建一个带格式的 Excel 报表。

    生成前的配置
        os.makedirs(..., exist_ok=True)：确保输出目录存在。
                如果 output_path 是 output/report.xlsx，就自动创建 output/ 文件夹，避免保存时报 FileNotFoundError。
        Workbook()：创建一个空工作簿，默认带一个空 sheet（wb.active 指向它）。

    一、Sheet1：汇总概览
        1. 设置标题
            merge_cells("A1:G1")：合并 A1:G1 共 7 列，做宽标题栏。
            标题内容从数据里动态取最小/最大日期，所以每次跑报表标题会自动更新。
            样式四件套：
                - 字体：微软雅黑 14 号加粗白字
                - 填充：2E86AB 蓝绿色实心背景
                - 对齐：水平垂直都居中
                - 行高：35 磅，让标题栏看起来更舒展

        2. 表头行（第 3 行）
            - 第 2 行留空，第 3 行放表头。
            - 表头用另一种颜色 A23B72（紫红色）区分于标题的蓝绿色，形成视觉层次。
            - enumerate(headers, 1) 从 1 开始计数，对应 Excel 的列号。

        3. 边框样式（复用）
            定义一个细线四边边框对象，后面每个数据单元格都复用这个 thin_border，避免重复创建。

        4. 填充数据行
            数据从第 4 行开始（标题 1 行 + 空行 1 行 + 表头 1 行 = 3，所以 i + 4）。
            第一列（渠道名）左对齐，其余数值列居中对齐。

        5. 数值格式
            openpyxl 默认把所有数值当普通数字，不会自动加千分位、小数位。
            通过 number_format 显式指定：
                列	        字段	                格式	        显示效果
                2, 5	    GMV / 花费	        #,##0.00	1,234,567.89
                3, 4, 6	    曝光 / 点击 / 用户	#,##0	    123,456
                7	        CTR	                0.0	        3.5
                8, 9	    CPC / 日均GMV	    0.00	    12.34

        6. 列宽
            get_column_letter(1) → 'A'，get_column_letter(2) → 'B'，以此类推。
            GMV 列给 15 字符宽，因为金额数字长；CTR/CPC 给 10 就够了。

        【一个修改点，单元格字体设置两次，赋值会被覆盖，不影响运行，删除一行，改了以后删掉这行】

        整体思路
            Sheet1 的构建模式是典型的 "标题 → 表头 → 数据 → 样式" 四段式，后面 Sheet2、Sheet3 都复用这套模板。
            核心技巧是：
                用 merge_cells 做标题栏
                用 PatternFill 做色块区分层级
                用 Border + Alignment 做表格感
                用 number_format 控制数值显示


    二、Sheet2：周度趋势表
        展示各渠道每周 GMV 以及环比变化。
        1. 前置判断
            只有当周度数据不为空时才创建这个 sheet，避免生成空表。
        2. 标题
            合并 A1:D1 四列，居中显示标题。
            没有设置背景色和行高，比 Sheet1 的标题更简洁。
        3. 表头
            - 第 2 行同样留空。
            - 表头用橙色 F18F01，和 Sheet1 的紫红、Sheet1 标题的蓝绿形成区分，一眼就能看出是哪个 sheet。
            - 这里字体设置没有冗余，一次到位。
        4. 数据行 + 环比格式化
            这是 Sheet2 的关键逻辑：
                - gmv_woq 是 Week-over-Week 环比变化率（比如 5.3 表示 +5.3%）。
                - pd.notna() 判断是否有值：第一周没有上一周可对比，所以是 NaN，显示为 -。
                - f"{woq_val:+.1f}%" 格式化成带符号的百分比字符串：
                    +5.3%（涨）
                    -12.7%（跌）
                    +0.0%（持平）
            + 号是格式说明符里的 +，强制正数也显示加号，视觉上涨跌对比更直观。
        5. 填充单元格
            复用 thin_border，全部居中对齐。
        6. 条件格式：跌幅标红
            Sheet2 里唯一的动态样式：
                - 只对第 4 列（环比变化）生效。
                - 如果跌幅超过 20%（比如 -25.3%），就把字体改成红色加粗，起到警示作用。
                - try/except 兜底，防止解析失败崩溃。
                - isinstance(val, str) 判断是因为 woq_str 已经被格式化成字符串了（带 % 号），不能直接当数字比较。

            for i, w in enumerate([10, 12, 15, 12], 1):

    insight.py 最终汇总
        负责把前面算好的汇总数据、周度趋势、异常记录转成一份结构化的 Markdown 文本报告。
        一、整体概览与渠道排名
            用一个 lines 列表逐行收集内容，最后用 "\n".join(lines) 拼成完整文本。
            这是生成 Markdown 报告时很常见的写法，比反复字符串拼接更高效、更清晰。
            1. 整体数据汇总
                这里从 channel_summary 里把各渠道的指标再聚合一次，得到全渠道合计：
                    total_gmv：总成交额
                    total_clicks：总点击
                    total_cost：总花费
                    total_users：总新增用户
                【一个比较大的优化点】
            2. 输出整体指标
                格式化说明：
                    格式	        含义	                示例
                    :,.0f	    千分位 + 无小数	    1,234,567
                    :,	        千分位 + 保留原始小数	123,456
                    :.1f	    保留 1 位小数	        3.5
                    :.2f	    保留 2 位小数	        1.23
                    **...**	    Markdown 加粗	    1,234,567
                末尾 \n 是为了让两段之间空一行，Markdown 渲染更舒服。
            3. 渠道 GMV 排名表
                这里用 Markdown 表格输出渠道排名：
                    sort_values("total_gmv", ascending=False)：按 GMV 从高到低排序。
                    pct = row["total_gmv"] / total_gmv * 100：计算该渠道 GMV 占总 GMV 的百分比。
                    {i+1}：【序号可优化】
            4. 最佳渠道点评
                这里用 idxmax() 找到 GMV 最高的那一行，然后输出一句“最佳渠道点评”。
                这句的作用是：不只给表格，还额外提炼一个可阅读的结论，方便业务同学一眼看到重点。
                但要注意，如果 channel_summary 为空，idxmax() 会报错。
                【优化，添加保护】

            第一部分的核心逻辑就是：
                先算全渠道合计，再给渠道排名表，最后点出表现最好的渠道。
            它负责回答“这段时间整体怎么样、哪个渠道最强”。
