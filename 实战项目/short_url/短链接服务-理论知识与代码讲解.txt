我还是觉得有必要补一个前言

短链接服务（URL Shortener） 是一种将长网址转换为短网址的网络服务，在数字营销、社交媒体传播和日常使用中扮演着重要角色。

什么是短链接服务？
    短链接服务本质上是一个URL映射与重定向系统。它将一个较长的原始网址
    （如 https://www.example.com/products/category/subcategory/item?id=12345&ref=abc）转换成一个简短的链接
    （如 https://short.link/aB3x）。
    当用户访问这个短链接时，服务会通过 HTTP 301/302 重定向，自动将用户跳转到原始的目标页面。

    其核心工作流程为：
        生成阶段：用户提交长链接 → 服务端生成唯一短码 → 建立短码与长链接的映射关系存入数据库
        访问阶段：用户点击短链接 → 服务端查找短码对应的原始URL → 执行重定向

短链接服务的意义：
    实用价值：
        节省字符空间：在早期 Twitter（现 X）限制 140 字符的时代尤为重要，短链接大幅节省了宝贵的字符数
        美化链接外观：将冗长、含参数的URL变为简洁美观的短链接，提升用户体验
        便于分享传播：短链接更容易复制、记忆和口头传达，降低了传播门槛
        跨平台适配：在短信、二维码、名片等字符受限的场景中，短链接几乎是刚需

    数据分析价值：
        点击量统计：追踪链接被访问的总次数
        用户画像分析：获取访问者的地理位置、设备类型、操作系统等信息
        时间维度分析：了解链接在不同时间段的点击趋势
        转化追踪：结合营销漏斗，衡量推广效果

    商业价值：
        品牌定制：支持自定义短域名（如 brand.co/xxx），强化品牌形象
        A/B 测试：同一短链接可动态指向不同落地页，用于测试转化效果
        链接生命周期管理：可设置过期时间、访问密码、访问次数限制等
        防欺诈与安全过滤：部分服务会在重定向前扫描目标页面，拦截恶意网站

技术实现要点：
    环节	        关键考量
    短码生成	    哈希算法、自增ID+Base62编码、雪花算法等
    存储方案	    键值对数据库（如 Redis）、关系型数据库
    重定向策略	301（永久重定向，利于SEO）vs 302（临时重定向，利于统计）
    高并发处理	CDN缓存、分布式架构、限流熔断

Q：短链接是如何实现跨平台适配的？
    短链接的跨平台适配，核心在于短链接本身与平台无关，它只是一个标准的 HTTP/HTTPS URL，而跨平台的能力则由短链接服务端的逻辑和客户端的运行环境共同实现。

    短链接本质上就是一个标准的 Web URL（如 https://short.link/aB3x），而 HTTP/HTTPS 协议是互联网最通用的协议。
    无论用户是在浏览器、App、短信、邮件还是二维码中点击，最终都会发起一个 HTTP 请求，服务端统一处理重定向。这意味着：
        - 不需要针对不同平台做不同的链接格式
        - 任何能发起 HTTP 请求的客户端都能使用短链接

    服务端重定向的自适应
        当用户点击短链接后，服务端会收到一个 HTTP 请求，请求头中包含了客户端的详细信息。服务端可以据此做出不同的响应：
            - User-Agent 识别：通过请求头中的 User-Agent 字段，判断用户使用的设备类型（iOS / Android / PC / 平板）和浏览器类型
            - 动态重定向：根据设备类型，将用户重定向到不同的目标页面。例如：
                iOS 用户 → 跳转到 App Store 下载页
                Android 用户 → 跳转到应用市场或 APK 下载页
                PC 用户 → 跳转到网页版
            - Deep Link / Universal Link 支持：如果用户已安装 App，服务端可以返回特定的 URL Scheme
                （如 myapp://page/123）或 Universal Link，直接唤起 App 内的对应页面，而非打开浏览器

    字符与编码的兼容性
        短链接在设计上就考虑了跨平台兼容性：
            - 纯 ASCII 字符：短码通常只使用 a-z、A-Z、0-9 等字符，避免特殊符号在不同平台中被转义或截断
            - 固定长度：短链接长度可控且较短，不会在短信（160字符限制）、Twitter 等平台中被截断
            - 无歧义编码：避免使用容易混淆的字符（如 0 和 O、1 和 l），确保在任何字体和平台下都能正确识别

    二维码场景的适配
        短链接在二维码中的跨平台适配尤为典型：
            - 短链接字符短 → 生成的二维码矩阵密度低 → 扫码识别率高
            - 不同手机系统（iOS / Android）的相机或扫码工具都能识别标准 URL 并自动跳转
            - 服务端根据扫码设备的 User-Agent 返回适配内容

    数据统计的跨平台归因
        短链接服务在重定向过程中，会记录以下信息来实现跨平台的数据追踪：
            维度	    获取方式
            设备类型	解析 User-Agent
            操作系统	解析 User-Agent
            地理位置	通过 IP 地址反查
            来源渠道	通过 UTM 参数或 Referer 头
            浏览器	解析 User-Agent
        这使得运营人员可以在一个后台看到同一短链接在不同平台上的表现差异，实现跨平台的数据归因分析。

    总结：
        短链接的跨平台适配并非在链接本身做特殊处理，而是利用 HTTP 协议的通用性 + 服务端的智能重定向逻辑 + 客户端信息的自动识别，实现"一个链接，
        多端适配"的效果。这也是短链接作为基础设施的核心优势之一。

    （四）数据库设计
        app/models/db.py

        要点简述：
            - short_code 加唯一索引，这是查询最频繁的字段。
            - original_url 长度设为 2048，覆盖绝大多数 URL。
            - expires_at 支持短链过期功能，是产品层面的常见需求。
            - 用 BigInteger 做主键和点击计数，防止数据量增长后溢出

        解析：
            用 SQLAlchemy（Python 最主流的 ORM 框架）定义了短链接服务的核心数据表 url_mappings，也就是整个系统的“数据地基”。
            1. 导入部分
                - Column：定义表中的列（字段）
                - BigInteger：64位整数，范围远大于普通 Integer，适合高并发场景下的自增主键
                - String(n)：变长字符串，n 为最大长度
                - DateTime：日期时间类型
                - func.utcnow()：SQLAlchemy 提供的数据库层面的 UTC 时间函数，生成时间时由数据库执行
                - Index：定义索引，用于加速查询
                - Base：SQLAlchemy 的声明式基类，所有模型类都要继承它，ORM 才能识别和管理这些表
            2. 表定义
                类名 UrlMapping 是 Python 层面的模型名
                __tablename__ 指定实际在数据库中的表名为 url_mappings
            3. 各字段解析
                字段	            类型	            约束	                作用
                id	            BigInteger	    主键，自增	        每行记录的唯一标识，用 BigInteger 而非 Integer 是因为短链接服务数据量增
                                                                    长快，Integer 上限约 21 亿，BigInteger 上限约 922 亿亿，基本不会溢出
                short_code	    String(10)	    唯一、非空、有索引	    短码，如 aB3x。长度 10 意味着用 Base62 编码最多可表示 62¹⁰ ≈ 839 万亿
                                                                    个短码，绰绰有余
                original_url	String(2048)	非空	                原始长链接。2048 是浏览器的通用 URL 长度上限
                created_at	    DateTime	    非空，默认当前时间	    记录创建时间，func.utcnow() 确保使用 UTC 时间，避免时区问题
                expires_at	    DateTime	    可为空	            过期时间，nullable=True 表示可选——为空则永不过期，有值则到期后不再重定向
                click_count	    BigInteger	    非空，默认 0	        点击次数统计。用 BigInteger 是因为热门链接的点击量可能非常大
            4. 索引设计
                这里显式创建了一个名为 idx_short_code 的索引。
                实际上，由于 short_code 字段已经声明了 unique=True，SQLAlchemy 会自动为其创建唯一索引，所以这个显式索引有一定冗余。
                不过保留它也不会有问题，可以理解为一种显式声明意图的写法，让代码的可读性更强。
                *** 索引是整个表最关键的优化——短链接服务的核心操作就是"根据短码查原始URL"，没有索引的话每次重定向都要全表扫描，数据量一大就会非常慢。
            5. 调试方法
                定义对象的字符串表示形式，方便在调试和日志中快速识别记录，比如打印出来就是 <UrlMapping(id=1, short_code='aB3x')>，
                比看一堆原始数据直观得多。

        对应的建表 SQL：
            CREATE TABLE url_mappings (
                id BIGINT AUTO_INCREMENT PRIMARY KEY,
                short_code VARCHAR(10) NOT NULL UNIQUE,
                original_url VARCHAR(2048) NOT NULL,
                created_at DATETIME(3) DEFAULT CURRENT_TIMESTAMP NOT NULL,
                expires_at DATETIME(3) NULL,
                click_count BIGINT DEFAULT 0 NOT NULL
            ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

        讲解：
            短链接服务核心表 url_mappings 的 MySQL 建表语句，与之前的 SQLAlchemy 模型完全对应。
            1. 字段定义解析
                字段	            类型与约束	                                设计意图
                id	            BIGINT AUTO_INCREMENT PRIMARY KEY	        主键。使用 BIGINT（最大约 922 亿亿）而非 INT（最大约 21 亿），
                                                                            是因为短链接服务数据增长极快，避免未来主键溢出；
                                                                            AUTO_INCREMENT保证插入时自动生成唯一递增 ID。
                short_code	    VARCHAR(10) NOT NULL UNIQUE	                短码。VARCHAR(10) 支持 Base62 编码下约 839 万亿种组合；
                                                                            NOT NULL 确保短码不能为空；
                                                                            UNIQUE 约束保证短码全局唯一，同时 MySQL 会自动为 UNIQUE
                                                                            列创建唯一索引，加速查询。
                original_url	VARCHAR(2048) NOT NULL	                    原始链接。2048 是主流浏览器支持的 URL 最大长度上限；
                                                                            NOT NULL 确保每条记录都有对应的长链接。
                created_at	    DATETIME DEFAULT CURRENT_TIMESTAMP NOT NULL	创建时间。DEFAULT CURRENT_TIMESTAMP 让数据库在插入时自动填充
                                                                            当前时间，无需应用层传值；
                                                                            NOT NULL 保证时间戳一定存在。
                expires_at	    DATETIME NULL	                            过期时间。NULL 表示可选——为空则链接永久有效，有值则到期后停止重定
                                                                            向，支持“限时短链”功能。
                click_count	    BIGINT DEFAULT 0 NOT NULL	                点击计数。BIGINT 应对热门链接的高点击量；DEFAULT 0 确保新记录初
                                                                            始计数为 0；NOT NULL 避免空值导致统计异常。
                (DATETIME(3)，支持 3 位小数秒)
            2. 索引设计
                由于 short_code 已有 UNIQUE 约束，MySQL 会自动创建唯一索引，加速 WHERE short_code = ? 查询（即短链接重定向的核心操作）。
            3. 表级配置
                - ENGINE=InnoDB：MySQL 默认存储引擎，支持事务、行级锁和外键，适合高并发读写场景（短链接服务的重定向是高频读操作，
                        InnoDB 的缓冲池能显著提升性能）。
                - DEFAULT CHARSET=utf8mb4：字符集设为 utf8mb4，而非 utf8。utf8 在 MySQL 中仅支持 3 字节 UTF-8，无法存储 emoji 和部分生僻字；
                        utf8mb4 支持完整 4 字节 UTF-8，避免原始链接中包含特殊字符时插入失败。
                - COLLATE=utf8mb4_unicode_ci：排序规则设为 Unicode 不区分大小写（ci = case insensitive）。
                        这意味着查询 WHERE short_code = 'ABC' 和 'abc' 会被视为相同，符合短码通常不区分大小写的业务习惯
                        （若需区分大小写，应改为 utf8mb4_bin）。
            4. 与 SQLAlchemy 模型的对应关系
                SQLAlchemy 模型
                    BigInteger, primary_key=True, autoincrement=True
                    String(10), unique=True, nullable=False, index=True
                    String(2048), nullable=False
                    DateTime, default=func.utcnow(), nullable=False
                    DateTime, nullable=True
                    BigInteger, default=0, nullable=False

                SQL 建表语句
                	BIGINT AUTO_INCREMENT PRIMARY KEY，完全一致
                	VARCHAR(10) NOT NULL UNIQUE
                	VARCHAR(2048) NOT NULL，完全一致
                	DATETIME DEFAULT CURRENT_TIMESTAMP NOT NULL，func.utcnow() 对应 CURRENT_TIMESTAMP
                	DATETIME NULL，全一致
                	BIGINT DEFAULT 0 NOT NULL，完全一致


    （五）异步数据库连接
        app/models/database.py

        要点简述：
            - pool_size=20：连接池保持 20 个常驻连接。
            - max_overflow=10：高峰期最多额外创建 10 个连接。
            - expire_on_commit=False：提交后不使对象过期，避免异步上下文中懒加载报错。

        解析；
            短链接服务的异步数据库连接层，基于 SQLAlchemy 2.0+ 的异步引擎构建。
            解决传统同步 ORM 在高并发 Web 服务中“阻塞事件循环”的致命问题。
            1. 声明式基类
                所有数据模型（如之前的 UrlMapping）都必须继承这个类，SQLAlchemy 才能识别并管理它们。
                单独定义：将 Base 放在独立的 database.py 中，避免模型文件和引擎配置互相导入导致的循环引用。
            2. 异步引擎创建
                参数	                    值	                    设计意图
                DATABASE_URL	        mysql+aiomysql://...	必须使用 aiomysql 异步驱动，而非默认的 pymysql（同步）
                pool_size=20	        20	                    连接池保持 20 个常驻连接，避免频繁创建/销毁连接的开销
                max_overflow=10	        10	                    当 20 个连接都被占用时，允许临时多创建 10 个连接应对突发流量，用完即释放
                pool_pre_ping=True	    True	                关键生产配置：每次从池中取连接前先发一个轻量级 ping，自动剔除已断开的死连接，
                                                                避免“MySQL server has gone away”错误
                echo=settings.DEBUG	    False/True	            开发时设为 True 可看到所有生成的 SQL，生产环境关闭避免日志爆炸
                连接池总容量 = pool_size + max_overflow = 30，这意味着服务最多同时处理 30 个数据库操作，超过的请求会排队等待。
                对于小项目来说这个值足够，若 QPS 超过 1000 再考虑调大。
            3. 异步会话工厂
                - async_sessionmaker：线程安全的会话工厂，每次调用 async_session() 返回一个新的独立会话。
                - expire_on_commit=False：极其重要的配置。
                    默认情况下，commit() 后 SQLAlchemy 会将对象属性标记为“过期”，下次访问时会自动查库刷新。
                    但在异步场景中，这种隐式查询会导致 MissingGreenlet 错误（因为不能在非 await 上下文中执行 IO）。
                    设为 False 后，commit 后对象属性仍然可用，避免意外触发同步查询。
            4. 依赖注入生成器
                FastAPI 依赖注入的标准写法，实现了三个核心保障：
                    自动事务管理：业务代码只需关注 CRUD 操作，无需手动 commit/rollback/close
                    异常安全：任何未捕获的异常都会触发回滚，不会产生脏数据
                    连接泄漏防护：finally 块确保连接一定被归还到池中，即使发生未知错误
                使用：
                    @router.get("/{short_code}")
                    async def redirect(short_code: str, db: AsyncSession = Depends(get_db)):
                        # db 已经是一个可用的、带事务管理的异步会话
                        result = await db.execute(select(UrlMapping).where(...))
                        ...
            整体架构意义
                这段代码构成了整个应用的数据访问基础设施：
                    异步非阻塞：配合 aiomysql，数据库 IO 不会阻塞事件循环，单进程即可支撑数百并发
                    连接复用：连接池避免了 TCP 握手和 MySQL 认证的重复开销
                    生产就绪：pre_ping + 自动回滚 + 连接泄漏防护，三重保险
                    解耦设计：业务代码完全不感知连接池、事务管理等底层细节
            注意事项：get_db 中的 commit 是“请求级别”的事务边界。
                    如果一个路由需要多个独立事务（比如先写日志再写业务数据），不应依赖此处的自动 commit，而应在业务代码中手动控制事务。
                    但对于短链接服务这种“一次请求一次写入”的场景，当前设计完全适用。


    （六）Pydantic 请求/响应模型
        app/models/schemas.py

        要点简述：
            Pydantic 的 field_validator 在数据进入业务逻辑之前就完成校验，这就是快速失败（Fail-Fast）原则。

        解析：
            使用 Pydantic V2 定义了短链接服务的三个核心数据模型，分别对应“创建请求”、“详情响应”和“重定向响应”。
            它们构成了 API 的契约层，负责数据校验、序列化和 ORM 对象转换。

            1. UrlCreate（创建短链请求体）
                - url: str：接收用户传入的原始长链接。
                        这里没有直接用 HttpUrl 类型，而是用 str + 自定义验证器。
                        因为 HttpUrl 会自动规范化 URL（如补全路径、处理编码），可能导致用户输入的原始 URL 被修改，而短链接服务必须精确保存用户原始输入。
                - expires_at: datetime | None = None：可选的过期时间。
                        使用 Python 3.10+ 的联合类型语法，None 表示永久有效。FastAPI 会自动将 JSON 中的 ISO 格式字符串
                        （如 "2026-12-31T23:59:59"）解析为 datetime 对象。
                - @field_validator("url")：Pydantic V2 的字段验证器（V1 中叫 @validator）。两个校验规则与数据库设计完全对齐：
                        协议检查：只允许 http:// 和 https://，防止 javascript:、data: 等危险协议注入
                        长度检查：上限 2048，与数据库 VARCHAR(2048) 一致，避免插入时报错

                HttpUrl 虽然校验更严格，但会做 normalization（例如把 HTTP://Example.COM 转为 http://example.com/）。
                短链接服务作为“透明代理”，不应篡改用户原始 URL，否则可能导致某些对大小写或路径敏感的链接失效。

            2. UrlResponse（短链详情响应体）
                - 字段映射：与 UrlMapping 数据库模型一一对应，click_count 默认值为 0，兼容旧数据或异常情况。
                - from_attributes = True：关键配置（Pydantic V2 中替代了 V1 的 orm_mode = True）。
                    启用后，可以直接将 SQLAlchemy 模型实例转换为响应模型：
                        # db_url 是 SQLAlchemy UrlMapping 实例
                        response = UrlResponse.model_validate(db_url)
                    Pydantic 会通过属性访问（db_url.short_code）而非字典键（db_url["short_code"]）读取数据，完美适配 ORM 对象。
                - 自动序列化：FastAPI 返回此模型时，datetime 字段会自动转为 ISO 8601 字符串（如 "2026-09-01T10:30:00Z"），无需手动格式化。

            3. UrlRedirect（重定向响应体）
                极简设计：仅包含目标 URL，用于 API 形式的重定向接口（非 HTTP 302 跳转）。
                使用场景：当客户端需要以 JSON 形式获取目标地址（如前端 SPA 自行处理跳转、移动端预加载判断）时使用。
                        若直接返回 HTTP 302，则不需要此模型，直接在路由中 return RedirectResponse(url=...) 即可。

            流程	        模型	            方向	                作用
            创建短链	    UrlCreate	    Client → Server	    校验输入合法性，拦截非法 URL
            查询/列表	    UrlResponse	    Server → Client	    安全暴露数据，隐藏内部字段（如 id）
            重定向(API)	UrlRedirect	    Server → Client	    轻量级目标地址返回

            这三个模型覆盖了短链接服务的核心交互契约，且与数据库设计、业务逻辑形成了完整闭环。


2. 短码生成算法 + 核心接口实现

    （一）短码生成算法——理论对比
        方案一：自增ID + Base62编码
            - 原理：利用数据库自增主键，将其转换为 Base62 进制字符串。
            - 优点：绝对无冲突，长度可控（7位 Base62 可表示 62^7 ≈ 3.5 万亿个短码），实现简单。
            - 缺点：自增 ID 暴露了业务量，容易被爬虫按序遍历。
            - 适用场景：内部系统、对安全性要求不高的短链服务。

        方案二：MD5/SHA256哈希 + 冲突处理
            - 原理：对原始 URL 做哈希，取前 N 位作为短码；冲突时追加随机盐或重试。
            - 优点：不暴露业务量，相同 URL 生成相同短码（天然去重）。
            - 缺点：存在哈希碰撞风险，需要数据库唯一约束兜底，冲突时重试有性能开销。
            - 适用场景：对 URL 去重有强需求、并发量中等的场景。

        方案三：发号器 + 随机打散
            - 原理：使用 Redis INCR 或雪花算法生成全局唯一 ID，再与随机数混合后做 Base62 编码。
            - 优点：兼顾唯一性和不可预测性，高性能，无冲突。
            - 缺点：实现复杂度较高，依赖 Redis 或分布式 ID 生成器。
            - 适用场景：高并发、对安全性有要求的公网短链服务。

        目前采用方案一（Base62）作为基础实现，Day 3 用 Redis 优化为方案三。


    （二）Base62 编码实现
        app/core/hash.py

        解析：
            短链接生成器（Short URL Generator）的核心编码模块。
            主要功能是将长 URL 转换为一个紧凑的、由字母和数字组成的短码（Short Code）。

            1. Base62 字符集定义
                Base62 是一种使用 62 个可打印 ASCII 字符来表示数值的编码方式。
                相比 Base64，它去除了 +、/、= 等特殊符号，生成的字符串是 URL Safe 的，可以直接放在网址路径中无需转义。
                字符映射：
                    0-9 (10个)
                    a-z (26个)
                    A-Z (26个)
                总计 62 个字符，索引范围 0~61。
                信息密度：每个 Base62 字符可以表示 log2(62) ≈ 5.95 bit 的信息。
                        8 位 Base62 字符串可以表示 62**8 ≈ 2.18×10**14 种组合，远超 32 位整数的范围。

            2. Base62 编码函数 (encode_base62)
                本质上是一个十进制转 62 进制的过程，与“十进制转二进制”的原理完全相同，只是除数从 2 变成了 62。
                    步骤	    操作	                    说明
                    1	    divmod(num, 62)	        同时获取商和余数
                    2	    ALPHABET[remainder]	    余数映射为对应字符
                    3	    num = 商	            用商继续下一轮除法
                    4	    reversed(result)	    关键：因为先得到的余数是低位，需要反转

                假设 num = 125：
                    1. 125 ÷ 62 = 2 ... 1 → 字符 '1' (索引1)
                    2. 2 ÷ 62 = 0 ... 2 → 字符 '2' (索引2)
                    3. 结果反转后为 "21"
                验证：
                    2×62**1 + 1×62**0 = 124 + 1 = 125

                边界处理：num == 0 时直接返回 '0'，避免 while 循环不执行导致返回空字符串。

            3. Base62 解码函数 (decode_base62)
                核心算法：霍纳法则（Horner's Method）
                这是进制转换的逆过程，采用多项式求值的高效写法：
                    "abc"62 = a×62**2 + b×62**1 + c×62**0
                霍纳法则将其改写为嵌套乘法，避免幂运算：
                    =((a×62+b)×62+c)
                每读入一个字符，就将当前累积值乘以基数再加上该字符的值。时间复杂度 O(n) ，比逐项计算幂次高效得多。

                假设 传入 "21"：
                    BASE = 62
                    ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
                    字符索引映射：'2' → 索引 2，'1' → 索引 1
                    迭代轮次	当前字符char	ALPHABET.index(char)	计算过程 (num = num * 62 + index)	更新后的num
                    初始状态	—	        —	                    —	                                0
                    第 1 轮	'2'	        2	                    0 × 62 + 2	                        2
                    第 2 轮	'1'	        1	                    2 × 62 + 1	                        125
                最终返回
                    函数返回 num = 125
                数学验证
                    与 Base62 的位权展开完全一致：
                        "21"62 = 2×62**1 +1×62**0 =124+1=125
                    恰好对应前文 encode_base62(125) 的输出结果 "21"，编码与解码互为逆运算，验证通过。

                霍纳法则的精妙之处在于：不需要预先知道字符串长度，也不需要计算幂次。
                每读入一个新字符，之前累积的结果自动“左移一位”（乘以基数），然后加上当前位的值。
                这使得整个解码过程只需一次线性遍历，时间复杂度为 O(n) ，且仅使用一个累加变量，空间复杂度为 O(1)。

            4. 短码生成函数 (generate_short_code)
                工作流程:
                    URL + Salt/SecretKey
                        ↓
                    MD5 Hash (128bit / 32位十六进制)
                        ↓
                    截取前8位十六进制 (32bit)
                        ↓
                    转为十进制整数 (max: 0xFFFFFFFF ≈ 42.9亿)
                        ↓
                    Base62 编码 → 短码 (最长6位)

                关键设计决策分析:
                    决策	            说明
                    加盐/Salt	    防止相同 URL 在不同环境下生成相同短码；增加彩虹表攻击难度
                    MD5 而非 SHA	    此处不需要密码学安全性，只需要均匀分布的哈希；MD5 速度更快
                    截取前8位hex	    8位十六进制 = 32 bit = 最大约 42.9 亿种组合。对于大多数短链服务足够
                    Base62 编码	    32 bit 整数用 Base62 表示最多 6 个字符 (62**6 ≈ 568亿 > 42.9亿 )，非常紧凑

                碰撞风险与应对:
                    当前方案存在碰撞风险。
                        - 生日悖论：当短码数量达到约 42.9^2亿 ≈ 65,000 时，碰撞概率就达到 50%。
                        - 实际安全上限：通常在几十万到百万级别就需要考虑碰撞问题。
                        - 兜底策略（注释中提到）：
                            1. 数据库对 short_code 字段加 UNIQUE 约束
                            2. 插入失败时，更换 salt 或追加自增 ID 重新生成
                            3. 或者改用 自增 ID + Base62 方案（无碰撞，但可预测）

                当前方案是一个经典且正确的短链编码实现，Base62 编解码部分数学上严谨，哈希截断方案在中小规模场景下实用，
                但在大规模生产环境中需要配合数据库唯一约束和重试机制来保证可靠性。

                演示：
                    假设 URL = https://example.com，settings.SECRET_KEY = "my_secret"
                    1. 拼接原始字符串
                        raw = f"{url}{salt or settings.SECRET_KEY}"
                        # salt 为空字符串 ""，falsy → 使用 settings.SECRET_KEY
                        # raw = "https://example.commy_secret"
                        注意：当前方案中 URL 和 salt 之间没有分隔符。
                            这意味着 url="abc", salt="def" 与 url="abcd", salt="ef" 会产生相同的 raw 字符串。
                            生产环境中建议加入分隔符，如 f"{url}|{salt}"。
                    2. 计算 MD5 哈希
                        md5_hash = hashlib.md5(raw.encode("utf-8")).hexdigest()
                        # md5("https://example.commy_secret")
                        # = "a3f5b7c9d2e4f6a8b1c3d5e7f9a2b4c6"  ← 示例值（32位十六进制）
                        输入：UTF-8 编码的字节串
                        输出：32 个十六进制字符（128 bit）
                        MD5 在此处的作用：均匀散列，而非密码学安全
                    3. 截取并转换为整数
                        num = int(md5_hash[:8], 16)
                        # 取前8位: "a3f5b7c9"
                        # int("a3f5b7c9", 16) = 2750822345
                            属性	    值
                            截取长度	8 位十六进制
                            比特宽度	32 bit
                            数值范围	0 ~ 4,294,967,295 (0xFFFFFFFF)
                            本例数值	2,750,822,345
                    4. Base62 编码
                        将 2750822345 转为 Base62 字符串：
                            2750822345 ÷ 62 = 44368102 ... 21  → ALPHABET[21] = 'l'
                            44368102  ÷ 62 = 715614    ... 34  → ALPHABET[34] = 'y'
                            715614    ÷ 62 = 11542     ... 10  → ALPHABET[10] = 'a'
                            11542     ÷ 62 = 186       ... 10  → ALPHABET[10] = 'a'
                            186       ÷ 62 = 3         ... 0   → ALPHABET[0]  = '0'
                            3         ÷ 62 = 0         ... 3   → ALPHABET[3]  = '3'
                        收集余数对应字符（从低位到高位）：['l', 'y', 'a', 'a', '0', '3']
                        反转后得到最终短码："30aayl"
                    5. 完整数据流总结
                        "https://example.com" + "my_secret"
                                ↓
                        "https://example.commy_secret"
                                ↓ MD5
                        "a3f5b7c9d2e4f6a8b1c3d5e7f9a2b4c6"
                                ↓ 截取前8位
                        "a3f5b7c9"
                                ↓ int(_, 16)
                        2750822345
                                ↓ encode_base62
                        "30aayl"     ← 最终短码（6位）
                    关键特性验证：
                        - 确定性：相同 URL + 相同 SecretKey → 永远生成 "30aayl"，无需查库即可还原（但反向不可逆）
                        - 紧凑性：32 bit 整数被压缩为仅 6 个字符
                        - URL 安全：输出仅含 [0-9a-zA-Z]，无需 URL 编码
                        - 雪崩效应：URL 改变一个字符，MD5 输出完全不同，短码也完全不同
                    碰撞问题：虽然 32 bit 有 42.9 亿种组合，但根据生日悖论，当生成约 65,000 个短码时碰撞概率即达 50%。
                    此方案适合中小规模场景，大规模使用务必配合数据库唯一约束 + 重试机制，或改用自增 ID 方案。


        补充：
            - 关于其 “反向不可逆”
                “反向不可逆”指的是：无法通过生成的短码（如 "30aayl"）反推出原始的 URL（https://example.com）。
                这并非因为 Base62 编码本身不可逆（Base62 解码是完全可逆的），而是因为整个生成链路中存在两个单向函数（One-way Function），
                导致信息在转换过程中被永久丢失。
                1. MD5 哈希的单向性（核心原因）
                    这是最根本的原因。MD5 是一种密码学哈希函数，其设计初衷就是不可逆的。
                        信息压缩：任意长度的输入（URL + Salt）被压缩为固定 128 bit 的输出。
                                根据鸽巢原理，无穷多的输入对应有限个输出，必然存在多对一映射，数学上不存在唯一的逆函数。
                        雪崩效应：输入的微小变化会导致输出剧烈变化，使得从输出推导输入在计算上不可行。
                        结果：即使拿到了完整的 32 位 MD5 哈希值 a3f5b7c9...，也无法还原出 https://example.commy_secret。
                2. 截断导致的信息丢失
                    代码中只取了 MD5 的前 8 位十六进制：
                        num = int(md5_hash[:8], 16)  # 丢弃了后 24 位十六进制（96 bit 信息）
                        - 原始 MD5 有 128 bit 信息量。
                        - 截取后仅剩 32 bit，75% 的信息被直接丢弃。
                        - 即使未来有人破解了 MD5 的逆向算法，仅凭这 32 bit 的片段也无法还原完整的哈希值，更不用说原始 URL 了。

                步骤	操作	                    是否可逆	    说明
                ①	URL + Salt → raw 字符串	可逆	        如果知道拼接规则和分隔符，可以拆分
                ②	raw → MD5 哈希	        不可逆	    哈希函数的单向性
                ③	MD5 → 截取前8位	        不可逆	    信息被永久丢弃
                ④	整数 → Base62 字符串	    可逆	        decode_base62("30aayl") = 2750822345

                准确地说：Base62 编解码这一层是可逆的，但它包裹的内核（MD5 + 截断）是不可逆的。
                        最终效果就是整个 generate_short_code 函数是单向的。

                正因为不可逆，短链服务必须依赖数据库存储映射关系：
                    短码 "30aayl"  →  查库  →  https://example.com
                用户访问 short.url/30aayl 时，服务器不是“解密”或“反算”出原始 URL，而是拿 "30aayl" 作为 key 去数据库里 lookup 对应的长链接。
                所以碰撞风险时必须用数据库唯一约束兜底
                    —— 因为算法本身无法区分两个不同 URL 碰巧生成的相同短码，只有数据库记录才能做到精确映射。


    （三）核心业务逻辑层
        app/services/shortener.py

        要点简述：
            - Cache-Aside 模式：读时查缓存，miss 后查库回填。
            - Redis INCR 原子性：单线程执行命令，天然原子。
            - 点击计数异步化：先写 Redis，定时批量同步 MySQL，避免每次重定向都写库。

        解析：
            采用了 “Redis 原子发号 + Base62 编码” 的方案，彻底解决 MD5 截断方案的碰撞问题。

            1. 库导入解析
                导入模块	                作用	                                    关键注意点
                AsyncSession	        替代同步 Session，所有 DB 操作都需 await	必须配合异步驱动（如 asyncpg）
                select	                构建 SELECT 查询，返回 Result 对象	        比原生 SQL 更安全，防注入
                redis.asyncio.Redis	    异步 Redis 客户端	                        与同步版 API 一致，但全是协程
                datetime.now(timezone.utc)	    获取 UTC 时间

            2. create_short_url 方法逐行详解
                该方法实现了 URL 去重 → ID 生成 → 短码编码 → 持久化 → 缓存预热 的完整链路。
                Step 1: URL 去重检查
                    用定长哈希值替代变长原始 URL 做查重查询，从而大幅提升数据库索引效率。
                    第一行：计算哈希值
                        调用模型上的静态方法，对传入的原始 URL 做 SHA-256 哈希，得到一个固定 64 字符的十六进制字符串。
                        "https://example.com/very/long/path?a=1&b=2"
                        → "a3f2b8c1d4e5...（64字符）"
                        把一个长度不可控的字符串（几十到几千字符），压缩成一个长度固定的标识符，后续所有查询都基于这个定长值进行。
                    第二~三行：用哈希值查数据库
                        等价 SQL：SELECT * FROM url_mappings WHERE url_hash = 'a3f2b8c1d4e5...'
                        WHERE url_hash = 'a3f2...'，字段是 VARCHAR(64)，索引键固定且短，B-Tree 遍历更快，每个索引页能塞更多条目
                    第四行：提取查询结果
                        scalar_one_or_none() 是 SQLAlchemy 2.0 的方法
                        含义：如果查询结果恰好一行，返回该行的 ORM 对象；如果零行，返回 None；如果多行，抛出异常
                        正常情况下 url_hash 有唯一索引，不可能出现多行，所以这里要么是 None（没查到），要么是一个 UrlMapping 对象
                    第五~八行：过期判断 + 复用
                        条件	                        含义	                        行为
                        existing 为 None	        数据库里没有这个 URL 的记录	    跳过 if，继续往下生成新短码
                        existing.expires_at is None	有记录，且永不过期	            直接复用，返回已有短码
                        existing.expires_at > now	有记录，且还没过期	            直接复用，返回已有短码
                        existing.expires_at <= now	有记录，但已过期	            不满足 if 条件，跳过，继续生成新短码
                        查到了且没过期 → 直接返回；查不到或已过期 → 继续往下走，生成新短码。
                    整体流程：
                        传入 original_url
                               ↓
                        计算 SHA-256 哈希（64字符定长）
                               ↓
                        WHERE url_hash = ? 查数据库（走 B-Tree 索引，O(log n)）
                               ↓
                        ┌─ 查到 + 未过期 → 直接返回已有短码（去重成功）
                        └─ 没查到 / 已过期 → 继续生成新短码
                Step 2: Redis INCR 原子发号
                    为什么不用数据库自增 ID？
                        - DB 自增在高并发下是瓶颈（锁竞争、写入放大）
                        - Redis INCR 是单线程原子操作，QPS 可达 10万+
                        - 天然分布式友好，多实例共享同一个计数器
                    返回值：单调递增的正整数（1, 2, 3, ...），保证全局唯一，彻底消除碰撞风险。
                    容灾考虑：Redis 重启后计数器归零会导致短码冲突。生产环境应：
                        - 使用 RDB/AOF 持久化
                        - 启动时从 DB 查最大 ID 回填 Redis：SET short_url:id_generator {max_id} NX
                Step 3: Base62 编码
                    next_id	        Base62 短码	说明
                    1	            1	        最小值
                    62	            10	        进位
                    1,000,000	    4c92	    百万级仅 4 位
                    62^7 ≈ 3.5万亿	10000000	7 位可支撑万亿级短链
                    相比 MD5 方案，此方案的短码更短、有序、无碰撞。
                Step 4: 写入数据库
                    flush() vs commit()：
                        - flush() 将 SQL 发送到数据库执行，获取生成的主键等，但不提交事务
                        - 适合在事务中后续还需要使用该对象的场景
                        - 最终由上层统一 commit()，保证“DB 写入 + Redis 写入”的事务一致性
                    注意：
                        一致性风险：如果 flush() 成功但后续 Redis 写入失败，DB 中有记录但缓存中没有。
                                下次读取时会触发 cache miss 回填，不会丢数据，但首次访问会慢一次。
                Step 5: 缓存预热
                    写入时机：创建时立即写入缓存，避免首个请求穿透到 DB（Cache Aside 的主动预热变体）。
                    TTL 对齐：Redis key 的过期时间与业务 expires_at 保持一致，确保过期短链不会被缓存“续命”。
                    ex 参数：以秒为单位设置过期时间，None 表示永不过期。

                整体架构总结：
                    create_short_url 请求
                        ↓
                    [Step1] DB 查重 ──命中且有效──→ 直接返回已有短码
                        ↓ 未命中
                    [Step2] Redis INCR 获取全局唯一 ID
                        ↓
                    [Step3] Base62 编码 → 短码
                        ↓
                    [Step4] DB flush 持久化映射关系
                        ↓
                    [Step5] Redis SET 预热缓存（带 TTL）
                        ↓
                        返回 UrlMapping
                - 用 Redis 原子计数器替代哈希截断，从根本上消除了碰撞问题；
                - 用 Base62 编码自增 ID，使短码更短且有序；
                - 用缓存预热 + TTL 对齐，兼顾了性能和过期语义的正确性。

            补充：
                数据库不会允许两个不同 URL 共用同一个短码，系统会在写入时直接拦截碰撞并重新生成，确保查询时一个短码永远只对应一条记录。
                1. 写入阶段：唯一索引拦截碰撞
                    数据库表对 short_code 字段设有 UNIQUE 唯一索引：
                        当第二个 URL 尝试写入已存在的短码时，数据库会直接拒绝插入并抛出异常，该记录根本不会入库。
                        因此查询时不存在“一个短码对应两条记录”的情况。
                2. 业务层：捕获异常并重试生成
                    业务代码捕获数据库抛出的唯一约束冲突异常后，会触发重试机制：
                        在原 URL 后拼接随机字符串（如 UUID 或 "DUPLICATE" 后缀）改变输入，重新哈希生成新短码，再次尝试写入，循环直到成功。
                3. 完整碰撞处理流程
                    URL_A 和 URL_B 碰巧生成相同短码 "abc123"
                            ↓
                    URL_A 先写入 → 成功 → 数据库记录: "abc123" → URL_A
                            ↓
                    URL_B 尝试写入 → 唯一索引冲突 → 数据库拒绝
                            ↓
                    业务层捕获异常 → 拼接随机盐重新生成 → 得到新短码 "xyz789"
                            ↓
                    URL_B 用 "xyz789" 再次写入 → 成功
                            ↓
                    最终结果：
                        "abc123" → URL_A  （唯一映射）
                        "xyz789" → URL_B  （唯一映射）
                4. 生产环境三层防线
                    层级	    机制	                作用
                    第一层	Redis SETNX 预检	    写入前用原子操作检查短码是否已存在，提前拦截大部分冲突
                    第二层	数据库唯一索引	        最终兜底，即使并发穿透 Redis，DB 层也能保证不写入重复短码
                    第三层	业务层重试	        捕获冲突异常后加盐重新生成，确保最终成功

                “自增 ID + Base62”方案优势：
                    通过 Redis INCR 生成全局唯一递增 ID 再转 Base62，从数学上保证了每个 ID 对应唯一短码，彻底消除了碰撞可能。
                    是一些大厂从 MD5 哈希方案切换到自增方案的核心原因
                        —— 不需要碰撞检测、不需要重试、不需要唯一索引兜底，架构更简洁、性能更高。
                    总结来说，碰撞在写入阶段就被拦截了，根本不会进入数据库。
                    查询时一个短码永远只对应一条记录，不存在“该返回哪个”的歧义。

            3. get_original_url
                短链服务的核心读取路径——用户访问短链接时，通过短码找到原始 URL 并跳转。
                整体采用经典的 Cache Aside 模式（先查缓存，miss 再查库）。
                Step 1：先查 Redis 缓存
                    用 short_url:{短码} 作为 Redis key 去查缓存。
                    这是整个方法最高频的路径
                        —— 绝大多数请求都会在这一步直接命中缓存返回，不会打到数据库。
                    Step 1.1：缓存命中 → 快速返回
                        缓存命中后做两件事：
                            异步更新点击计数：_increment_click_count 通常是在 Redis 里做 INCR，非常轻量，不阻塞主流程
                            返回原始 URL：这里有一个类型兼容处理——redis-py 默认返回 bytes，但如果客户端配置了 decode_responses=True，
                                    返回的就是 str。这段代码用 isinstance 判断做了兼容，确保无论哪种配置都能正确返回字符串
                Step 2：Cache Miss → 查数据库
                    缓存没命中（可能是首次访问、缓存过期、或 Redis 故障），回退到数据库查询。
                    等价 SQL：
                        SELECT * FROM url_mappings WHERE short_code = 'xxxxx'
                    short_code 字段上有唯一索引，查询效率是 O(log n)。
                    Step 2.1：数据库也没找到 → 返回 None
                        数据库里也没有这个短码的记录，说明短码无效或不存在，直接返回 None，上层会返回 404。
                    Step 2.2：检查是否过期
                        即使数据库里有记录，还要检查业务过期时间：
                            情况	                行为
                            expires_at 为 None	永不过期，跳过这个 if，继续往下走
                            expires_at < now	已过期，返回 None（上层返回 404/410）
                            expires_at >= now	未过期，继续往下走
                Step 3：回填缓存（Cache Backfill）
                    数据库查到了有效记录，但缓存里没有（cache miss），所以要把结果回填到 Redis，让后续请求直接走缓存。
                        - TTL 对齐：缓存的过期时间与业务 expires_at 保持一致，确保过期的短链不会被缓存"续命"
                        - ex=ttl：以秒为单位设置 Redis key 的过期时间，None 表示永不过期
                Step 4：更新点击计数
                    无论是缓存命中还是 DB 回填，最终都会走到这里更新点击量。
                    通常实现是在 Redis 里做 INCR click_count:{short_code}，后续由定时任务批量落库。

                整体流程图：
                    用户访问短链接 /abc123
                            ↓
                    Redis GET short_url:abc123
                            ↓
                    ┌─ 命中 → 更新点击计数 → 返回 URL（99% 的请求走这条路）
                    │
                    └─ 未命中 → 查数据库 WHERE short_code = 'abc123'
                                ↓
                            ┌─ 没找到 → 返回 None（404）
                            ├─ 已过期 → 返回 None（404/410）
                            └─ 有效 → 回填 Redis（带 TTL）→ 更新点击计数 → 返回 URL

                与 create_short_url 的对称关系：
                    操作	    create（写入）	        get（读取）
                    缓存策略	预热：创建时主动写入 Redis	回填：miss 时从 DB 补写 Redis
                    TTL	对齐 expires_at	            对齐 expires_at
                    过期检查	查重时判断是否复用	        查到后判断是否返回
                    点击计数	无	                    每次访问都 +1
                两者配合形成了一个完整的读写闭环：
                    写入时预热缓存避免首次穿透，读取时回填缓存保证后续命中，TTL 与业务过期时间严格对齐，确保过期语义一致。

            4. _increment_click_count
                "先写 Redis，后续定时批量同步到数据库"的异步点击计数方案，方法签名：
                    - 以 _ 开头，表示这是一个私有方法，只在类内部被 get_original_url 调用，外部不应直接使用
                    - 返回 None，调用方不需要关心它的返回值，只需要"触发"这个动作即可
                第一行：构造 Redis key
                    用 short_url:clicks: 作为前缀 + 短码拼接成 Redis key。比如短码是 abc123，最终 key 就是：
                        short_url:clicks:abc123
                    命名约定上用 short_url: 前缀，方便后续用 SCAN short_url:clicks:* 批量扫描所有点击计数器。
                第二行：原子递增
                    INCR 是 Redis 的原生命令，行为是：
                        - key 不存在 → 自动初始化为 0，然后 +1，结果为 1
                        - key 已存在 → 在原有值基础上 +1
                关键特性：
                    特性	            说明
                    原子性	        即使 1000 个并发请求同时 INCR 同一个 key，最终结果也一定是 1000，不会丢失
                    O(1) 时间复杂度	纯内存操作，微秒级响应，完全不会阻塞主流程
                    自动创建	        不需要提前 SET 初始化，首次 INCR 自动从 0 开始

                光往 Redis 里 INCR 还不够，最终需要把累计的点击数持久化到数据库。这部分由定时任务完成，流程是：
                    每次访问 → Redis INCR（实时，微秒级）
                            ↓
                    定时任务（如每 60 秒）
                            ↓
                    SCAN click_count:* → GETDEL → UPDATE MySQL → 删除 key

                为什么不在这里直接写数据库？
                    假设一个热门短链 1 秒被访问 1000 次：
                        - 直接写 DB：1000 次 UPDATE ... SET click_count = click_count + 1，行锁竞争严重，数据库扛不住
                        - 先写 Redis：1000 次 INCR，纯内存操作，零竞争；定时任务只需要 1 次 UPDATE 把累计值写回 DB
                    这就是"写缓冲"的思想——用 Redis 吸收高频写入，定时批量合并后落库，把数据库压力从 O(请求量) 降到 O(定时频率)。

            补充：
                - INCR 命令的全称
                    INCR 就是 increment（增量、递增）的缩写，并不是某个多词短语的缩写。
                    在 Redis 中，INCR 命令的作用是：
                        将 key 存储的字符串值解析为 64 位有符号整数，然后原子地加 1 并返回新值。
                    如果 key 不存在，Redis 会先将其初始化为 0，再执行 +1，最终结果为 1。

                - Redis 内部存储的值本质上都是字符串（SDS），INCR 执行时会经历以下过程：
                    1. 读取：从 Redis 中取出 key 对应的字符串值
                    2. 解析：将字符串解析为 64 位有符号整数
                        （C 语言中的 int64_t，范围是 -9,223,372,036,854,775,808 ~ 9,223,372,036,854,775,807）
                    3. 计算：在解析后的整数值上 +1
                    4. 写回：将计算结果转回字符串，存回 Redis
                    INCR 操作的对象虽然对外表现为"数字"，但底层始终是字符串存储、解析后计算、再写回字符串。
                    所以如果 key 里存的是非数字字符串（比如 "hello"），INCR 会直接报错。

                - 解析为整数后 +1 的意义是什么？
                    核心意义在于 Redis 底层统一用字符串存储所有值，必须先解析为整数才能执行数学运算，同时能进行类型安全校验与溢出检测。
                    1. 存储与计算分离
                        Redis 没有独立的"整数类型"，所有值对外统一表现为字符串（SDS）。
                        INCR 是数学运算命令，字符串 "42" 本身无法直接 +1，必须先解析为数值类型才能执行加法。
                    2. 类型安全校验
                        解析过程同时充当了类型检查。
                        如果 key 里存的是 "hello" 等非数字内容，解析会直接失败并报错，防止对非数值数据执行无意义的数学运算。
                    3. 溢出检测
                        限定为 64 位有符号整数（int64_t）后，Redis 可以明确检测计算结果是否超出范围。
                        （-9,223,372,036,854,775,808 ~ 9,223,372,036,854,775,807）
                        一旦溢出，直接报错而非静默回绕，避免产生难以排查的 bug。
                    4. 与 INCRBYFLOAT 形成互补
                        INCR 走整数路径，INCRBYFLOAT 走浮点数路径。
                        明确区分两条路径后，整数场景不会引入浮点精度问题，浮点场景也能获得足够的精度支持。
                    整个流程可概括为：字符串（存储）→ 整数（计算）→ 字符串（写回）。
                    解析为整数是连接"存储格式"与"数学运算"的必要桥梁，既保证了计算的正确性，又提供了类型安全和溢出保护。


    （四）API 路由层
        app/api/routes/shortener.py

        要点简述 301 vs 302：
            - 301（永久重定向）：浏览器缓存结果，后续请求不再经过服务，无法统计点击量。
            - 302（临时重定向）：每次请求都经过服务，可统计点击量，短链接服务应选 302。

        解析：
            post 短链服务的创建入口
            1. 路由装饰器
                - /shorten：接口路径，完整 URL 类似 POST /shorten
                - response_model=UrlResponse：
                    FastAPI 会自动将返回值序列化为 UrlResponse 格式的 JSON，同时用这个模型做响应数据校验和文档生成
                - status_code=201：RESTful 规范中，资源创建成功应返回 201 Created，而不是默认的 200 OK
            2. 函数签名与依赖注入
                参数	                来源	                说明
                payload: UrlCreate	请求体（JSON）	    FastAPI 自动解析请求体并校验字段，UrlCreate 里定义了 url（必填）和
                                                        expires_at（可选）等字段
                db	                Depends(get_db)	    从依赖函数获取异步数据库会话，请求结束后自动关闭连接
                redis_client	    Depends(get_redis)	从依赖函数获取异步 Redis 客户端
                FastAPI 的依赖注入机制——路由函数不需要自己管理数据库连接和 Redis 连接的创建与销毁，全部由框架自动处理。
            3. 核心业务逻辑
                - 实例化 Service：把 db 和 redis_client 注入到 ShortenerService 中，之前的服务类
                    （Redis 原子发号 → Base62 编码 → DB 持久化 → 缓存预热）
                - 调用 create_short_url：传入原始 URL 和过期时间，返回 UrlMapping ORM 对象
                - 返回结果：FastAPI 会根据 response_model=UrlResponse 自动将 ORM 对象序列化为 JSON 响应

            GET 重定向路由(用户访问短链时，最终就是打到这个接口上)
            1. 路由路径
                {short_code} 是路径参数，FastAPI 会自动从 URL 中提取。比如用户访问：
                    GET /4c92
                short_code 的值就是 "4c92"。
                 注意：这个路由没有固定前缀，意味着它会匹配所有 GET /xxx 的请求。
                    所以它必须放在所有其他 GET 路由之后注册，否则会把 /shorten 等路径也"吃掉"。
            2. 函数参数
                参数	                来源	                说明
                short_code: str	    URL 路径参数	        从 /{short_code} 中自动提取
                db	                Depends(get_db)	    异步数据库会话
                redis_client	    Depends(get_redis)	异步 Redis 客户端
            3. 核心逻辑：查原始 URL
                调用 get_original_url 方法，走的是：
                    Redis 缓存命中 → 直接返回
                           ↓ 未命中
                    MySQL 查询 → 回写 Redis 缓存 → 返回
                           ↓ 未找到
                    返回 None
            4. 404 处理
                get_original_url 返回 None 意味着两种情况：
                    - 短码根本不存在（从未创建过）
                    - 短链已过期（expires_at 已过当前时间）
                两种情况统一返回 404，响应体为：
                    {
                        "detail": "Short URL not found or expired"
                    }
            5. 302 重定向
                RedirectResponse 是 FastAPI 内置的响应类，它会返回一个带有 Location 头的 HTTP 响应，浏览器收到后自动跳转到目标 URL。
                最终返回的 HTTP 响应大致是：
                    HTTP/1.1 302 Found
                    Location: https://www.example.com/very/long/path

            为什么用 302 而不是 301？
                状态码	含义	        浏览器行为
                301	    永久重定向	浏览器会缓存重定向结果，下次直接访问目标 URL，不再经过短链服务
                302	    临时重定向	浏览器每次都经过短链服务，确保点击计数准确
            如果用了 301，用户第二次点击同一个短链时，浏览器直接从缓存跳转到目标 URL，_increment_click_count 根本不会被触发，
            点击统计就彻底失效了。

            整体流程:
                用户点击短链 https://s.example.com/4c92
                        ↓
                GET /4c92 → redirect_short_url(short_code="4c92")
                        ↓
                ShortenerService.get_original_url("4c92")
                        ↓
                    ┌─ 找到 → 302 Redirect → 浏览器跳转到原始 URL
                    └─ 未找到 → 404 Not Found


    （五）应用入口
        app/main.py

        启动命令：
            uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

        解析：

            1. 导入部分
                - FastAPI：框架核心类，用于创建应用实例
                - settings：集中管理配置项（应用名、调试模式等），通常基于 Pydantic 的 BaseSettings 从环境变量或 .env 文件加载
                - shortener, stats：两个路由模块，分别对应短链操作和统计功能
            2. 创建应用实例
                title：应用名称，会显示在自动生成的 Swagger 文档（/docs）页面标题上
                debug：调试模式开关，开启后异常会返回详细堆栈信息，生产环境必须关闭
            3. 注册路由

                    - 负载均衡器：只把流量转发给健康检查通过的实例
                    - 监控告警：检测服务是否宕机
            整体结构：
                app = FastAPI(...)
                        ↓

3. Redis 缓存策略优化
    （一）缓存架构设计
        短链接服务是典型的读多写少场景（一个短链接可能被访问成千上万次，但只创建一次），缓存的价值极大。
        多级缓存架构图：
        客户端 → 本地缓存(L1) → Redis(L2) → MySQL(L3)
                 ↑ miss          ↑ miss
                 └── 回填 ────────┘
        多级缓存的好处：
            - L1（本地缓存）：进程内内存，纳秒级访问，但多进程/多实例间不共享。
            - L2（Redis）：跨进程共享，毫秒级访问。
            - L3（MySQL）：持久化存储，作为最终数据源。


    （二）本地缓存实现
        基于 cachetools.TTLCache 实现的本地缓存类，适用于热点数据缓存。
        app/services/cache.py

        要点简述：
            - TTLCache 自动淘汰过期条目，无需手动清理。
            - maxsize 控制内存占用上限，防止内存溢出（OOM）。
            - 本地缓存适合热点数据，访问速度极快，但需注意多实例间的数据一致性。

    （三）缓存三大问题的实战解决
        1. 缓存穿透——布隆过滤器
            问题：攻击者用大量不存在的短码发起请求，每次都穿透缓存打到数据库。
            app/services/bloom.py

        要点简述：
            - 布隆过滤器的核心特性：假阳性和零假阴性。
            - 误判率与 bit_size 和 hash_count 相关，空间越大、哈希函数越多，误判率越低。
            - 在短链接场景中：每创建一个短码就 add 到布隆过滤器，查询时先 might_contain，若返回 False 则直接拒绝，避免查库。

        补充：
            - 布隆过滤器的作用
                布隆过滤器（Bloom Filter）是一种空间效率极高的概率型数据结构，用于快速判断一个元素是否属于某个集合。
                1. 核心能力
                    它只能回答一个问题："这个元素可能存在，还是一定不存在？"
                    判断结果	    含义
                    "一定不存在"	100% 准确，该元素从未被插入过
                    "可能存在"	有一定误判率，元素可能插入过，也可能没有
                    简单说：漏判率为 0，但存在误判率。
                2. 在短链服务中的典型用途
                    快速过滤不存在的短码，避免无效的数据库查询。
                    用户访问 GET /4c92
                            ↓
                        布隆过滤器判断
                            ├─ "一定不存在" → 直接返回 404，不查 Redis 也不查 DB
                            └─ "可能存在"   → 继续走 Redis → DB 查询流程
                    好处是：大量恶意请求或随机猜测的短码会被布隆过滤器在第一层就拦截掉，根本不会打到 Redis 和数据库上，极大减轻后端压力。
                3. 工作原理（简述）
                    插入 "abc"
                        ↓
                    多个哈希函数分别计算哈希值 → 映射到位数组的多个位置 → 全部置为 1

                    查询 "abc"
                        ↓
                    同样的哈希函数计算 → 检查对应位置
                        ├─ 全部为 1 → "可能存在"
                        └─ 有 0     → "一定不存在"
                4. 优缺点
                    优点	                            缺点
                    空间占用极小（百万级数据只需几百 KB）	有误判率（可配置，通常 < 1%）
                    查询速度 O(k)，k 为哈希函数个数	    不支持删除操作
                    不存储原始数据，隐私性好	        随着插入量增大，误判率逐渐升高

        解析：
            1. 构造函数 __init__
                - 参数说明
                    参数	        默认值	                        含义
                    bit_size	1 << 24（即 2²⁴ = 16,777,216）	位数组的总位数，约 1600 万位
                    hash_count	5	                            每个元素用几个哈希函数映射
                - 位数组的创建
                    bytearray 是 Python 中的可变字节序列，每个字节 8 位。因为位数组的最小存储单位是字节，所以需要把位数换算成字节数：
                        bit_size = 16,777,216 位
                        字节数   = 16,777,216 ÷ 8 = 2,097,152 字节 ≈ 2 MB
                - 两个参数的关系：
                    bit_size 和 hash_count 共同决定了布隆过滤器的误判率。一般来说：
                        - bit_size 越大 → 位越稀疏 → 误判率越低，但占用内存越多
                        - hash_count 存在一个最优值，太少哈希碰撞不够充分，太多反而加速位数组填满
                    对于默认的 1600 万位 + 5 个哈希函数，在插入约 100 万个元素时，误判率大约在 1% 左右。
            2. _get_positions
                对同一个元素，计算出它在位数组中需要置位（或检查）的多个位置。
                - 模拟多个哈希函数
                    标准布隆过滤器需要 k 个独立的哈希函数。但实际工程中，计算 k 个不同哈希函数开销较大。这里用了一个经典技巧：
                        用同一个哈希函数（MurmurHash3），通过不同的 seed 来模拟多个独立的哈希函数。
                    - item：要插入/查询的元素（比如短码 "4c92"）
                    - seed=i：每次循环用不同的种子（0, 1, 2, 3, 4），产生不同的哈希值
                    - signed=False：返回无符号整数（0 ~ 2³²-1），避免出现负数
                - 取模映射到位数组范围
                    哈希值可能是一个很大的数（最大 2³²-1），但位数组只有 bit_size 位，所以用 % bit_size 把哈希值映射到合法范围
                    [0, bit_size-1] 内。
                    举子：
                        假设 hash_count=5，对短码 "4c92" 计算：
                            seed=0 → mmh3("4c92", seed=0) = 3847291053 → % 16777216 → 位置 124567
                            seed=1 → mmh3("4c92", seed=1) = 1928374650 → % 16777216 → 位置 5678902
                            seed=2 → mmh3("4c92", seed=2) = 4019283746 → % 16777216 → 位置 839210
                            seed=3 → mmh3("4c92", seed=3) = 2847193048 → % 16777216 → 位置 3921048
                            seed=4 → mmh3("4c92", seed=4) = 918273645  → % 16777216 → 位置 7182736
                    最终返回 [124567, 5678902, 839210, 3921048, 7182736]，这 5 个位置就是 "4c92" 在位数组中的"指纹"。
            3. add
                将元素的所有哈希位置在位数组中标记为 1。
                - 从位索引到字节+位偏移
                    bytearray 按字节寻址，所以需要把一个全局的位位置 pos 拆成两部分，例：
                        pos = 13

                        byte_idx = 13 // 8 = 1    ← 第 1 个字节（从 0 开始）
                        bit_idx  = 13 % 8  = 5    ← 该字节内的第 5 位
                - 置位操作
                    经典的位运算置位：
                        - 1 << bit_idx：构造一个只有第 bit_idx 位为 1 的掩码。比如 bit_idx=5 时，掩码是 00100000（二进制）
                        - |=：按位或操作，将目标位设为 1，其他位保持不变
                        原值:  00000000
                        掩码:  00100000   (1 << 5)
                        ─────────────────
                        结果:  00100000   ← 第 5 位被置为 1
                - 完整流程
                    "4c92"
                        ↓ _get_positions
                    [124567, 5678902, 839210, 3921048, 7182736]
                        ↓ 对每个位置
                    byte_idx = pos // 8, bit_idx = pos % 8
                    bit_array[byte_idx] |= (1 << bit_idx)
                        ↓
                    5 个位被置为 1
                - 三者的协作关系
                    add("4c92")
                        ↓
                    _get_positions("4c92")     ← 用 5 个不同 seed 的 MurmurHash3 算出 5 个位置
                        ↓
                    对每个位置执行位运算置 1    ← 在 bytearray 中定位字节和位，用 |= 置位

                    might_contain("4c92")
                        ↓
                    _get_positions("4c92")     ← 同样的方式算出 5 个位置
                        ↓
                    检查这 5 个位置是否全为 1
                        ├─ 全为 1 → 返回 True（可能存在）
                        └─ 有 0   → 返回 False（一定不存在）
                _get_positions 是 add 和 might_contain 共享的核心计算逻辑，保证了同一个元素在插入和查询时使用完全相同的哈希位置，
                这是布隆过滤器正确性的基础。
