一、用户行为分析指标定义
    1. 活跃度指标
        活跃度指标用于衡量用户在特定时间段内的使用频率，是评估产品健康度和用户粘性的核心指标。

        - 日活跃用户(DAU)：指统计一日（24小时）内，登录或使用了产品的去重用户数。DAU的计算公式为：
            DAU = 当日复访用户数 + 当日新增用户数
            复访用户指已注册但非首次登录的用户，新增用户指当天首次注册的用户。
        - 周活跃用户(WAU)：指统计一周（7天）内，至少登录或使用过产品一次的去重用户数。周活的计算公式为：
            WAU = 统计周期内登录用户数(去重)
        - 月活跃用户(MAU)：指统计一个月（30天）内，至少登录或使用过产品一次的去重用户数。月活的计算公式为：
            MAU = 统计周期内登录用户数(去重)

        [DAU与MAU的比率（DAU/MAU）是衡量用户粘性的关键指标，比率越高表示用户粘性越强]

    2. 留存率指标
        留存率是衡量用户持续使用产品能力的重要指标，它反映了用户在首次使用产品后，能否在后续特定时间段内再次使用。

        - 次日留存率：指用户在首次使用产品后，第二天再次使用的用户比例。计算公式为：
            次日留存率 = (T+1日活跃的新用户数 / T日新用户总数) × 100%
        - 7日留存率：指用户在首次使用产品后，第七天再次使用的用户比例。计算公式为：
            7日留存率 = (T+7日活跃的新用户数 / T日新用户总数) × 100%
        - 30日留存率：指用户在首次使用产品后，第30天再次使用的用户比例。计算公式与7日留存类似，只需将时间窗口调整为30天。

        留存率的计算需要明确初始用户和后续活跃的定义边界。
        初始用户通常指在特定日期（T日）首次使用产品的用户，后续活跃指在T+N日（N为1、7、30天）再次使用产品的用户。

    3. 漏斗分析
        漏斗分析是一种用于追踪用户行为路径并评估各阶段转化效率的数据分析方法，常用于分析注册流程、购买流程等多步骤用户行为。

        漏斗分析的核心概念
            - 漏斗阶段：将用户从首次接触产品到完成目标行为的路径划分为多个阶段，如注册→首页浏览→商品添加→下单→支付。
            - 转化率：指从上一阶段进入当前阶段的用户比例，计算公式为：
                转化率 = (当前阶段用户数 / 前一阶段用户数) × 100%
            - 流失率：指在当前阶段流失的用户比例，计算公式为：
                流失率 = 1 - 转化率

        漏斗图绘制：通常使用横向柱状图展示各阶段的用户数量，柱状图从左到右依次降低，直观呈现用户流失情况。也可以使用面积图展示各阶段的转化率百分比。

            执行逻辑：
            df.isnull()：生成布尔值矩阵。
            .values：将 Pandas 的布尔矩阵转换为底层的 NumPy 数组（ndarray）。这一步是为了提高后续计算的效率，避免 Pandas 的索引对齐开销。
            .any()：NumPy 的方法。只要数组中有任何一个元素是 True，就返回 True；如果全是 False，才返回 False。
            返回值：布尔值（True 或 False）。

            # 删除包含缺失值的⾏

            2. 填充均值时，mean() 会忽略空值吗？

                        这意味着它在求和与计数时，会直接跳过那些缺失的数据，只使用有效数据进行计算。


    2. 重复值处理
        【检测重复值】
            # 检测DataFrame中所有列完全相同的重复⾏
            df.duplicated().sum()
            # 检测指定列的重复值
            df.duplicated(subset=['user_id', 'order_id']).sum(

        讲解：
            1. 关于第一行代码
                标记规则：df.duplicated() 会逐行检查，发现某一行与它前面的某一行所有列的值都完全相同，把这一行标记为 True（即记为 1）。
                它只标记重复行中的“后续行”。
                也就是说，第一次出现的那一行会被标记为 False（保留为原始行），只有第二次、第三次及以后出现的相同行才会被标记为 True。
                求和：最后用 .sum() 对这些 True/False 求和，得出的结果就是“多出来的、完全重复的行数”。

            2. 关于第二行代码 df.duplicated(subset=[...]).sum()
                指定了 subset 参数时，Pandas 就不再看所有的列了，而是只比较指定的几列（比如 user_id 和 order_id）。
                只要这两列的值与前面的行相同，哪怕其他列的值不一样，它也会被判定为重复并标记为 True。
                同样地，.sum() 算出的是基于这两列判断出的多余重复行数。

        补充：
            判断重复的代码的时间复杂度不是 n*n，而是接近 n。
            1. 底层真相：哈希表（Hash Table）
                Pandas 的 duplicated() 方法底层并没有使用嵌套循环去逐行比对，而是使用了哈希表（Hash Table）机制。
                （类似于 Python 中的 set 或字典）
                它的实际执行逻辑是这样的：
                    1. Pandas 在内存中创建一个空的哈希表。
                    2. 它从上到下遍历 DataFrame 的每一行。
                    3. 对于当前行，它计算出一个哈希值（Hash），然后去哈希表里“查字典”：
                        - 如果哈希表里没有这个哈希值，说明是第一次出现，标记为 False，并把这个哈希值存入哈希表。
                        - 如果哈希表里已经存在这个哈希值，说明前面已经出现过一模一样的行，标记为 True。
                    4. 继续处理下一行。
                因为哈希表的“查找”和“插入”操作的平均时间复杂度都是 O(1) ，所以遍历 n 行数据的总时间复杂度就是 O(n)。

            2. 为什么感觉还是有点慢？
                虽然时间复杂度是线性的 O(n) ，但在数据量极大（比如几千万行）时，你依然会感觉到耗时，这主要是因为：
                    - 哈希计算开销：对于包含多列的 DataFrame，Pandas 需要把每一行的多个值组合起来计算哈希值，这个计算本身是有 CPU 开销的。
                    - 内存与缓存：当哈希表变得极其庞大时，可能会超出 CPU 的缓存（Cache）大小，导致频繁的内存交换，从而拖慢速度。

            3. 优化建议
                - 只检查关键列（使用 subset）：
                    千万不要对整个大表做 df.duplicated()。
                    如果只关心某几个 ID 是否重复，一定要加上 subset 参数。
                    参与哈希计算的列越少，速度越快：
                        # 比 df.duplicated() 快得多
                        df.duplicated(subset=['user_id']).sum()

        【删除重复值】
            # 删除所有列完全相同的重复⾏
            df.drop_duplicates inplace=True)
            # 仅根据指定列删除重复⾏
            df.drop_duplicates(subset=['user_id', 'order_id'], keep='last', inplace=True)
            # 重置索引
            df.reset_index(drop=True, inplace=True

        讲解：
            1. keep 参数除了 'last' 还有哪些？
                除了 'last'，keep 参数还有两个常用的值：
                'first'（默认值）：保留重复项中第一次出现的行，删除其后所有重复的行。
                False：删除所有的重复项，一个都不保留。也就是说，只要存在重复，这些行会被全部剔除

            2. 重置索引时的 drop=True 是什么意思？
                在 Pandas 中，当删除了某些行（比如去重后），索引（index）通常会变得不连续（例如从 0, 1, 3, 4 变成了这样）。
                使用 reset_index() 可以重新生成连续的整数索引（0, 1, 2, 3）。
                此时，drop 参数决定了如何处理旧的索引：
                    - drop=True（丢弃旧索引）：
                        直接生成新的默认整数索引，彻底丢弃原来的索引信息26。这是最常用的做法，因为旧的索引通常已经没有业务意义了。
                    - drop=False（默认值，保留旧索引）：
                        如果不加 drop=True（即默认 drop=False），Pandas 不会直接丢弃旧索引，而是会把旧索引变成 DataFrame 中的一列，
                        默认列名叫 'index'。

            总结来说：df.reset_index(drop=True) 的语义非常明确，就是“丢掉旧索引、换新编号”。

        在实际的数据清洗工作中，我们通常只关心数据本身，旧的索引往往没有实际意义。
        因此，强烈建议每次重置索引时都加上 drop=True，这样可以避免表格中意外多出无用的 index 列，防止在后续合并（merge）或导出（to_csv）
        时引发莫名其妙的报错。


    3. 异常值处理
        【统计⽅法检测异常值】
            # Z-score⽅法
            from scipy import stats
            z = np.abs(stats.zscore(df['column_name']))
            df = df[z < 3]  # 去除Z-score⼤于3的异常值

            # IQR⽅法
            Q1 = df['column_name'].quantile(0.25)
            Q3 = df['column_name'].quantile(0.75)
            IQR = Q3 - Q1
            df = df[(df['column_name'] > Q1 - 1.5 * IQR) & (df['column_name'] < Q3 + 1.5
            # 丢掉旧索引、换新编号，并且直接修改原表，不产生新对象
            df.reset_index(drop=True, inplace=True)

        讲解：
            Z-score（3-Sigma 原则）
                核心原理：Z-score 衡量的是一个数据点距离平均值有多少个标准差。公式为：Z = (X - μ) / σ。
                代码解释：
                    - stats.zscore()：计算该列每个数据的 Z-score。
                    - np.abs()：取绝对值。因为我们既关心“极大值”（正数），也关心“极小值”（负数），只要偏离均值太远就算异常。
                    - z < 3：根据统计学中的 3-Sigma 原则，在正态分布中，99.7% 的数据都落在均值加减 3 个标准差的范围内。
                            因此，绝对值大于 3 的数据被判定为异常值。
                适用场景：数据近似正态分布（钟形曲线）。
                弱点：Z-score 对异常值本身非常敏感！因为均值（μ）和标准差（σ）都会被极端异常值拉偏，导致异常值看起来“没那么异常”，从而漏检。

            IQR（四分位距法）（基于箱线图）
                核心原理：IQR（四分位距）是数据中间 50% 的范围。它通过寻找数据的“边界”来判定异常值，而不是依赖均值。
                代码解释：
                    - Q1 和 Q3：分别计算数据的第 25 百分位数和第 75 百分位数。
                    - IQR = Q3 - Q1：计算中间 50% 数据的跨度。
                    - Q1 - 1.5 * IQR 到 Q3 + 1.5 * IQR：这是箱线图（Boxplot）中定义正常数据范围的经典公式。
                    - 最后一步使用 &（逻辑与）：筛选出同时满足“大于下限”且“小于上限”的数据，也就是剔除了两端的所有异常值。
                适用场景：数据不满足正态分布，或者数据中存在大量极端值时。
                优势：Q1、Q3 和 IQR 都是基于排序的“稳健统计量”（Robust Statistics），它们完全不受极端异常值的影响。
                        因此，IQR 方法在实际业务中比 Z-score 更常用、更可靠。

            对比维度	        Z-score (3-Sigma)	    IQR (箱线图法)
            判定标准	        距离均值超过 3 个标准差	    超出 [Q1-1.5IQR, Q3+1.5IQR] 范围
            数据分布要求	    必须近似正态分布	        无要求（非参数方法）
            对异常值的敏感度	高（容易被异常值带偏）	    低（极其稳健）
            实战推荐度	    2 仅限正态分布）	        5 首选方案

        【文本数据清洗】
            python
            # 使用正则表达式替换非文本字符
            import re
            df['text_column'] = df['text_column'].str.replace(r'[^A-Za-z0-9\s]', '', regex=True)

            # 使用str访问器进行文本处理
            df['text_column'] = df['text_column'].str.strip()   去除前后空格
            df['text_column'] = df['text_column'].str.lower()   转换为小写

        讲解：
            清洗文本数据，将指定列中除了“英文字母、数字、空格”之外的所有特殊字符全部剔除。
            1. .str.replace() 函数
                在 Pandas 中，普通的 .replace() 方法通常用于替换整个单元格的值（比如把 0 换成 NaN）。
                而当需要替换字符串内部的某些字符时，必须加上 .str 访问器，调用 .str.replace() 方法。
                它等价于 Python 内置的字符串替换或正则表达式模块中的 re.sub() 方法。

            2. 参数解析
                这行代码传递了三个参数：
                    - r'[^A-Za-z0-9\s]'（pat）：即匹配模式（Pattern），告诉 Pandas 要去找什么样的字符。
                            这里传入的是一个正则表达式（前面的 r 代表 raw string，即原始字符串，防止转义字符被 Python 提前解析）。
                    - ''（repl）：即替换内容（Replacement）。
                            这里是一个空字符串，意思是“把匹配到的字符替换为空”，也就是删除它们。
                    - regex=True（参数）：显式地告诉 Pandas，第一个参数是一个正则表达式，而不是普通的字面量字符串。
                            虽然这是默认值，但在写正则时显式加上它，代码的意图会更清晰。

            3. 正则表达式 [^A-Za-z0-9\s] 深度拆解
                这是这行代码的核心，属于正则表达式中的“字符类取反”语法：
                    - [...]（字符类）：表示匹配括号内的任意一个字符。
                    - ^（取反符号）：当 ^ 紧跟在左方括号 [ 后面时，表示“非”或“排除”。即匹配不在括号内的任何字符。
                    - A-Za-z0-9（白名单范围）：
                        A-Z：所有大写英文字母
                        a-z：所有小写英文字母
                        0-9：所有数字
                    - \s（空白字符）：代表空格（Space）、制表符（Tab）、换行符等空白字符。
                综合起来：[^A-Za-z0-9\s] 的意思就是：
                    匹配任何“不是英文字母、不是数字、也不是空白字符”的字符（比如标点符号 !@#、特殊符号等）。
                例如：
                    “Hello, World! 123 @2024” to “Hello World 123 2024”

        补充：
            关于“正则表达式本身的匹配规则”和“字符串替换函数的执行机制”
            .str.replace() 函数的底层机制：全局替换（Global Replacement）。
            1. 正则表达式只负责“找”，不负责“找几次”
                在 [^A-Za-z0-9\s] 这个正则表达式中，没有加任何量词，它的默认规则是：每次只匹配 1 个字符。
                    - 遇到第一个特殊字符（比如 !），它匹配成功。
                    - 遇到第二个特殊字符（比如 @），它再次匹配成功。
            2. .replace() 函数自带“全局扫描”机制
                在 Python 和 Pandas 中，字符串的替换函数（底层调用的是 re.sub()）默认就是全局替换的。
                它的执行逻辑是：
                    1. 从字符串的最左边开始，向右逐个字符扫描。
                    2. 只要发现当前字符符合正则表达式的规则，就立刻把它替换成目标字符（这里是空字符串）。
                    3. 替换完成后，继续向右扫描下一个字符，直到字符串的末尾。


    4. 时间类型转换
        【转换为datetime类型】
            转换为datetime类型：
            # 转换字符串为datetime
            df['event_time'] = pd.to_datetime(df['event_time'], errors='coerce')
            # 处理不同时间格式
            df['event_time'] = pd.to_datetime(df['event_time'], format='%Y-%m-%d %H:%M:%S')
            # 设置时区
            df['event_time'] = pd.to_datetime(df['event_time'], unit='ms', errors='coerce').dt.tz_localize('UTC')\
                                .dt.tz_convert('Asia/Shanghai')

        讲解：
            1. errors='coerce' 是什么意思？
                在将字符串转换为日期时间时，数据中难免会包含格式错误、无法识别的“脏数据”（例如 "Unknown"、"2022-02-30" 等）。
                errors 参数就是用来控制 Pandas 遇到这些错误时的行为的。
                errors='coerce' 的含义是：强制转换。
                当 Pandas 遇到无法解析的字符串时，它不会抛出异常中断程序，而是将其强制转换为 NaT（Not a Time，Pandas 中的时间缺失值，
                        类似于数值中的 NaN）。
                补充说明：该参数的默认值是 'raise'（遇到错误直接报错），另一个可选值是 'ignore'（遇到错误则保留原始字符串）。
                在实际的数据清洗工程中，使用 'coerce' 是最常见、最安全的做法，它可以保证代码顺利跑完，
                        后续再用 isnull() 检查并处理这些 NaT 值即可。

            2. 若原始数据时间格式不统一（如有的精确到小时，有的仅精确到天），如何转换？
                如果你显式指定了 format='%Y-%m-%d %H:%M:%S'，Pandas 会要求所有数据都必须严格匹配这个格式，一旦遇到仅精确到天
                （如 "2022-01-01"）的数据，就会报错或变成 NaT。
                针对格式不统一的情况，有以下几种最佳解决方案：
                    方案一：直接省略 format 参数（推荐）。
                            pd.to_datetime 默认具备强大的自动识别能力，能够自动推断并解析多种常见的混合日期格式。
                    方案二：使用 format='mixed'。
                            如果你的数据确实包含多种格式，可以显式传入 format='mixed'。
                            这会告诉 Pandas 独立尝试解析每一行的格式，而不是仅根据第一行来推断，这是处理异构数据最稳健的选择。
                    方案三：结合 errors='coerce'。
                            无论使用哪种方案，都建议加上 errors='coerce'，这样即使有极少数完全无法识别的格式，也会被安全地转换为 NaT，
                                    而不会导致整列转换失败。

            3. 设置时区的代码中用到了哪些函数？
                第三行代码 pd.to_datetime(...).dt.tz_localize('UTC').dt.tz_convert('Asia/Shanghai')
                是一条非常经典的时区处理链式操作，涉及以下三个核心函数：
                    - pd.to_datetime(..., unit='ms', errors='coerce')：
                        首先将原始数据（这里假设是毫秒级的时间戳）转换为 Pandas 的日期时间对象。
                        此时生成的是“朴素时间”（tz-naive），即只有时间数值，但没有时区标签。
                    - .dt.tz_localize('UTC')：
                        作用是“贴标签”。
                        它告诉 Pandas：“这些没有时区的时间，原本就是属于 UTC 时区的”。
                        这一步不会改变时间的具体数值，只是给它打上了 UTC 的时区标识，使其变成“感知时间”（tz-aware）。
                    - .dt.tz_convert('Asia/Shanghai')：
                        作用是“换算数值”。
                        在已经拥有时区标签的基础上，将时间从 UTC 转换到目标时区（上海，即 UTC+8）。
                        这一步会改变时间的显示数值（例如自动加上 8 小时），但底层的绝对时间点保持不变。
                数据转换的顺序是 “朴素时间” -> “感知时间” -> “数值换算”

        补充：
            关于 .dt 和 .str 和其他访问器（Accessors）
            在 Pandas 中，当我们需要对某一列（Series）中的元素内部进行批量操作时，不能直接对整个列使用 Python 原生的方法。
            为了解决这个问题，Pandas 设计了“访问器”机制，它们就像是给 Series 加装的“专用工具箱”。
            1. .dt (Datetime Properties)
                作用：专门用于处理日期和时间数据。
                常用功能：提取年、月、日、星期，或者进行时区转换。
                示例：df['date_col'].dt.year（提取年份），df['date_col'].dt.day_name()（提取星期几）。
            2. .str (String Methods)
                作用：专门用于处理字符串数据。
                常用功能：大小写转换、正则替换、截取、分割等。
                示例：df['text_col'].str.upper()（转大写），df['text_col'].str.contains('abc')（是否包含某子串）。
            3. .cat (Categorical)
                作用：专门用于处理类别型（Categorical）数据。类别型数据通常用于存储那些只有固定几个选项的列（如性别、省份、订单状态）。
                常用功能：查看类别、重命名类别、修改类别的顺序。
                示例：df['status_col'].cat.categories（查看有哪些类别），
                        df['status_col'].cat.rename_categories({'old': 'new'})（重命名类别）。
            4. .sparse (Sparse)
                作用：专门用于处理稀疏数据（Sparse）。当一列数据中绝大部分都是同一个值（比如 99% 都是 0，只有 1% 是 1）时，
                        使用稀疏数组可以极大地节省内存。
                常用功能：获取稀疏数据的密度、填充值等。
                示例：df['sparse_col'].sparse.density（计算非零值的比例）。
            5. .plot (Plotting)
                作用：专门用于数据可视化。
                常用功能：快速绘制折线图、柱状图、散点图等。
                示例：df['value_col'].plot.hist()（画直方图），df['value_col'].plot.bar()（画柱状图）。
            6. .list (List-like / Extension Arrays)
                作用：在较新的 Pandas 版本中，用于处理包含列表（List）的列。
                常用功能：计算列表长度、获取列表中的特定元素。
                示例：df['list_col'].list.len()（计算每行列表中元素的个数）。


三、指标计算⽅法

    1. ⽇活计算
        【SQL 实现】
            -- 按天计算⽇活
            SELECT DATE(event_time) AS dt, COUNT(DISTINCT user_id) AS dau
            FROM user Activity
            GROUP BY DATE(event_time);

            -- 考虑时区（UTC转上海时间）
            SELECT DATE(event_time AT TIME ZONE 'Asia/Shanghai') AS dt,
            COUNT(DISTINCT user_id) AS dau
            FROM user Activity
            GROUP BY DATE(event_time AT TIME ZONE 'Asia/Shanghai');
        讲解：
            1. 基础版 DAU 统计（不考虑时区）
                时间截断：DATE(event_time) 函数会将包含时分秒的 event_time 字段截断为日期格式（2024-01-01 14:30:00 to 2024-01-01）。
                分组聚合：GROUP BY DATE(event_time) 按照截断后的日期进行分组，把同一天的所有行为记录归拢到一起。
                去重计数：COUNT(DISTINCT user_id) 在每个日期分组内，对 user_id 进行去重。
                        无论一个用户当天登录或操作了多少次，都只记为 1 人。最终计算出每天的独立活跃用户数。

            2. 进阶版 DAU 统计（考虑时区转换）
                在基础版之上增加了 AT TIME ZONE 'Asia/Shanghai'，主要用于解决数据库服务器时区与业务时区不一致的问题。
                （例如数据库存储的是 UTC 时间，但业务需要按北京时间统计）
                AT TIME ZONE 函数：这是 PostgreSQL 等数据库提供的时区转换函数。
                        它会将 event_time 从数据库的默认时区（通常是 UTC）转换为指定的目标时区（这里是 Asia/Shanghai，即 UTC+8）。
                行为意义：如果服务器在 UTC 时区，北京时间 2024-03-01 00:30:00 在数据库里存的是 2024-02-29 16:30:00。
                        如果不进行时区转换直接用 DATE() 截取，记录会被错误地算作 2 月 29 日的活跃用户，导致每日零点前后的数据出现断层或重复。
                执行顺序：查询会先将 event_time 转换为上海时间，然后再用 DATE() 函数截取日期，最后按转换后的日期进行分组和去重计数。
        注意：
            1. 必须使用 DISTINCT：活跃用户强调的是“独立人数”，如果漏掉 DISTINCT 写成 COUNT(user_id)，同一个用户的多次行为会被重复计算，
                导致 DAU 虚高。
            2. GROUP BY 的字段必须对齐：SELECT 子句中用来分组的表达式（如 DATE(...)），必须与 GROUP BY 子句中的表达式完全一致。
            3. 时区转换的替代写法：AT TIME ZONE 是 PostgreSQL 的语法；如果你使用的是 MySQL，对应的时区转换函数是
                CONVERT_TZ(event_time, '+00:00', '+08:00')。

        【Python 实现】
            import pandas as pd

            # 读取数据并转换为datetime类型
            df = pd.read_csv('user_activity.csv')
            df['event_time'] = pd.to_datetime(df['event_time'])

            # 设置时区（如果数据是UTC时间）
            df['event_time'] = df['event_time'].dt.tz_localize('UTC').dt.tz_convert('Asia/Shanghai')

            # 按天计算日活
            # 将时间部分归零（变成当天的 00:00:00），底层仍是向量化操作，速度更快
            dau = df.groupby(df['event_time'].dt.normalize())['user_id'].nunique()
        讲解：
            1. 数据读取与基础类型转换
                逻辑：首先将 CSV 文件读入 Pandas 的 DataFrame。
                    接着，将 event_time 列从普通的字符串（String）转换为 Pandas 的 datetime64 类型。
                    只有转换为时间类型后，才能进行后续的时区处理和日期提取。
            2. 时区处理（UTC 转上海时间
                逻辑：这与你之前问过的 SQL 中的 AT TIME ZONE 逻辑完全对应。
                    - .dt.tz_localize('UTC')：给原本没有时区标签的时间“贴标签”，声明它们属于 UTC 时区。
                    - .dt.tz_convert('Asia/Shanghai')：将时间数值换算为北京时间（UTC+8）。
                目的：确保后续按天统计时，是以北京时间的零点为界限，而不是 UTC 的零点，防止跨天数据错乱。
            3. 核心：按天计算日活（DAU）
                第一步：提取日期 (df['event_time'].dt.normalize())
                    利用 .dt 访问器，将部分时间归零（例如把 2024-03-01 14:30:00 变成 2024-03-01 00:00:00）。
                第二步：按日期分组 (groupby(...))
                    以提取出的纯日期作为分组键（Group Key），将同一天的所有用户行为记录归拢到同一个组里。
                第三步：组内去重计数 (['user_id'].nunique())
                    在每个日期分组内，提取 user_id 列，并调用 .nunique()（Number of Unique）方法，计算该组内不重复的用户 ID 数量。
                    (nunique()方法用于计算DataFrame或Series中不同元素的数量)
                最终结果：变量 dau 会变成一个 Series，它的索引（index）是日期，值（values）是对应日期的独立活跃用户数。


    2. 留存率计算
        【SQL 实现（7 ⽇留存率）】
            -- 计算7日留存率
            WITH t0_users AS (
                SELECT user_id
                FROM user_activity
                WHERE DATE(event_time) = '2026-08-10'
                GROUP BY user_id
            ),
            t7_users AS (
                SELECT user_id
                FROM user_activity
                WHERE DATE(event_time) = '2026-08-17'
                GROUP BY user_id
            )
            SELECT
                -- 优化点1：t7_users 内部已去重，直接 COUNT 即可计算留存人数
                COUNT(t7_users.user_id) AS retained_users,

                -- 优化点2：t0_users 内部已去重，直接 COUNT 即可计算总人数
                COUNT(t0_users.user_id) AS total_users,

                -- 优化点3：分子分母同步替换，保留 * 1.0 确保计算结果为浮点数
                COUNT(t7_users.user_id) * 1.0 / COUNT(t0_users.user_id) AS retention_rate
            FROM t0_users
            LEFT JOIN t7_users ON t0_users.user_id = t7_users.user_id;

        讲解：
            核心思想：以基准日（8月10日）的活跃用户为“锚点”，通过左连接（LEFT JOIN）去匹配7天后（8月17日）的回访用户，
                    并利用 COUNT 对 NULL 值的天然过滤特性，一步到位地算出留存率。
            1. 构造基准用户群（t0_users）
                逻辑：从行为表中筛选出 2026-08-10 当天的活跃用户，并通过 GROUP BY user_id 进行去重。
                作用：生成一个绝对不重复的基准用户集合，作为后续计算的主表（分母）。
            2. 构造回访用户群（t7_users）
                同理，作为后续计算的关联表（分子来源）。
            3. 关联并计算留存率
                关联逻辑：以 t0_users 为主表，LEFT JOIN 关联 t7_users。
                    - 如果某个用户在 8月17日有活跃，两表匹配成功，t7_users.user_id 会显示该用户的 ID。
                    - 如果某个用户在 8月17日没有活跃，匹配失败，t7_users.user_id 会显示为 NULL。
                指标计算：
                    - COUNT(t7_users.user_id) AS retained_users：在 SQL 中，COUNT(列名) 会自动忽略 NULL 值。
                        因此，它刚好完美地统计出了“匹配成功（即7日后依然活跃）”的用户数，即留存分子。
                    - COUNT(t0_users.user_id) AS total_users：因为 t0_users 是主表，且内部已经通过 GROUP BY 去重，
                            所以它绝对没有重复值和 NULL 值。直接 COUNT 即可得到基准日的总人数，即留存分母。
                    - * 1.0：将分子乘以 1.0，是为了防止在部分数据库（如旧版 MySQL）中整数除法导致结果被截断为 0，
                            确保最终计算出带有小数点的浮点数比率。

        补充：
            1. WITH ... AS ... 的语法
                这是 SQL 中的 CTE（Common Table Expression，公共表表达式） 语法。
                作用：你可以把它理解为一个“临时表”或“临时变量”。它允许你在执行主查询之前，先定义一个或多个子查询，并给它们起个名字。
                优势：
                    - 提高可读性：把复杂的嵌套查询（子查询里套子查询）拆解成了线性的、按步骤执行的逻辑，就像写代码时的函数一样。
                    - 避免重复计算：如果同一个子查询在后面的代码中需要被多次引用，使用 CTE 只需要写一次即可。
                语法结构：WITH 临时表名 AS (子查询), 临时表名2 AS (子查询2) SELECT ... FROM 临时表名 ...
            2. GROUP BY 的去重功能
                最核心的特性之一。
                当对某一列（如 user_id）使用 GROUP BY 时，数据库会将所有相同的 user_id 归拢到同一个“组”里。
                在最终的查询结果集中，每个组只会输出一行数据。因此，结果集中绝对不会出现重复的 user_id。
                虽然 SELECT DISTINCT user_id 也能实现去重，但在很多数据库的底层执行计划中，GROUP BY 和 DISTINCT 的性能几乎是一样的，
                        甚至 GROUP BY 在某些场景下更优，因为它是为聚合操作（如 COUNT, SUM）设计的。

        综合性比较强的补充：
            为什么不直接使用 retained_users * 1.0 / total_users 计算留存率？
                核心原因：在 SQL 标准中，同一个 SELECT 子句内定义的别名，不能互相引用。
                        因为它们在逻辑上是并行生成的，而不是串行赋值的。

                这段 SQL 代码的执行顺序，需要分两个层级来看：首先是全局的 CTE（WITH 子句）执行顺序，其次是核心 SELECT 语句内部的逻辑执行顺序。
                1. 全局执行顺序（CTE 的优先级）
                    在 SQL 中，WITH 定义的 CTE（公共表表达式）相当于临时表，它们必须先于主查询执行。因此，全局的执行顺序是：
                        1. 执行 t0_users CTE：扫描 user_activity 表，筛选 2026-08-10 的数据并 GROUP BY 去重，生成临时表 t0_users。
                        2. 执行 t7_users CTE：扫描 user_activity 表，筛选 2026-08-17 的数据并 GROUP BY 去重，生成临时表 t7_users。
                        3. 执行主查询（最后的 SELECT 语句）：基于上面生成的两个临时表进行关联和聚合计算。
                2. 核心 SELECT 语句内部的执行顺序
                    当数据库引擎开始执行最后一段主查询时，它并不是按照人类阅读代码的从上到下的顺序执行的。
                    SQL 的逻辑执行顺序如下：
                        第一步：FROM t0_users
                            动作：加载基准日（8月10日）的用户数据作为主表。这是所有后续操作的“数据基座”。
                        第二步：LEFT JOIN t7_users ON t0_users.user_id = t7_users.user_id
                            动作：将主表与回访表（8月17日用户）进行左连接。
                            结果：生成一张虚拟的宽表。这张表保留了 t0_users 的所有行。
                                如果匹配成功，会带上 t7_users.user_id；
                                如果匹配失败，t7_users.user_id 的位置会被填充为 NULL。
                        第三步：GROUP BY（隐式发生）
                            动作：虽然代码中没有显式写出 GROUP BY，但因为 SELECT 中使用了聚合函数 COUNT()，
                                数据库引擎会隐式地将整张虚拟表作为一个单一的分组来进行聚合计算。
                        第四步：SELECT 中的聚合计算
                            动作：在聚合后的结果集上，计算各项指标：
                                - 计算 COUNT(t7_users.user_id)：忽略 NULL，得出留存人数（分子）。
                                - 计算 COUNT(t0_users.user_id)：统计总行数，得出基准人数（分母）。
                                - 计算除法 * 1.0 / ...：得出留存率。
                        第五步：生成最终结果
                            动作：将计算出的 retained_users、total_users 和 retention_rate 作为最终的单行结果返回给用户。

                因为 retained_users 和 total_users 这两个别名，是在第四步（SELECT 阶段）才被定义和计算出来的。
                当数据库引擎在第四步准备计算除法时，它自己还不知道这两个别名代表什么数值，所以会直接报错。

        【Python实现（7日留存率）】
            import pandas as pd
            from datetime import datetime, timedelta

            # 读取数据并转换为datetime类型
            df = pd.read_csv('user_activity.csv')
            df['event_time'] = pd.to_datetime(df['event_time'])

            # 统计用户首次活跃日期
            first_login = df.groupby('user_id').agg(
                first_login_date=('event_time', 'min')
            ).reset_index()

            # 合并首次登录日期到原始数据
            df = pd.merge(df, first_login, on='user_id')

            # 设置T日（基准日期）
            t_date = datetime(2026, 8, 10)

            # 计算每个用户在T日之后的活跃天数
            df['days_diff'] = (df['event_time'] - df['first_login_date']).dt.days

            # 提取T日新增用户
            t0_users = first_login[first_login['first_login_date'] == t_date]

            # 统计T日新增用户在T+7日的活跃情况
            retained_users = df[(df['user_id'].isin(t0_users['user_id'])) & (df['days_diff'] == 7)]['user_id'].unique()

            # 计算留存率
            retention_rate = len(retained_users) / len(t0_users) if len(t0_users) > 0 else 0

        讲解：
            1. 数据读取与类型转换
                逻辑：将 CSV 读入内存，并将时间字符串转换为 Pandas 的 datetime 类型，为后续的日期运算做准备。
            2. 提取用户的“首次活跃日期”
                逻辑：按 user_id 分组，取 event_time 的最小值（.min()）。
                目的：找出每个用户在这个产品中的绝对首次活跃时间。
                    reset_index() 将结果转换为普通的 DataFrame，并重命名列为 first_login_date。
            3. 计算行为距离首次登录的天数差
                逻辑：
                    1. 使用 merge 将首次登录日期“贴”回原始行为表中。
                    2. 将当前行为时间减去首次登录时间，并通过 .dt.days 提取出相差的天数。
                目的：将绝对时间转化为相对时间（生命周期天数）。
                    例如，用户首次登录是 8月1日，他在 8月8日又登录了，那么这条记录的 days_diff 就是 7。
            4. 筛选 T日新增用户（分母）
                逻辑：从首次登录表中，精确筛选出在 2026-08-10 这一天首次活跃的用户。
                目的：这批用户构成了计算留存率的分母（总基准人数）。
            5. 筛选 T+7日依然活跃的用户（分子）
                逻辑：在原始行为表中同时满足两个条件：
                    1. df['user_id'].isin(t0_users['user_id'])：必须是 T日（8月10日）的新增用户。
                    2.df['days_diff'] == 7：这条行为记录距离他们首次登录刚好过去了 7 天（即 T+7 日）。
                目的：找出这批新增用户中，在 T+7 日有过行为的独立用户集合（分子）。
                    .unique() 确保即使一个用户在 T+7 日登录了多次，也只被计算一次。
            6. 计算留存率
                逻辑：分子长度除以分母长度。
                防御性编程：代码最后加了 if len(t0_users) > 0 else 0 的判断。
                    这是非常严谨的做法，防止当 T日没有任何新增用户时，分母为 0 导致代码抛出 ZeroDivisionError（除零错误）。
