Python 多线程基础理论

    1.1 线程基础概念
        Python 的 threading 模块提供了一种在单个进程内部并发地运行多个线程的方式。
        线程是进程内的执行单元，共享进程的内存空间。
        在操作系统中，进程是资源分配的基本单位，而线程是 CPU 调度的基本单位。
        一个进程可以包含多个线程，这些线程共享进程的内存空间和系统资源。
        与进程相比，线程的创建和切换开销更小，通信更方便，但需要更谨慎地处理同步问题。

        线程生命周期：
            - 新建状态：线程对象创建后，尚未调用start()方法
            - 就绪状态：线程调用start()方法后进入就绪队列等待调度
            - 运行状态：线程获得 CPU 时间片开始执行
            - 阻塞状态：线程等待 I/O 操作或其他资源时进入阻塞
            - 终止状态：线程执行完毕或因异常终止

    1.2 多线程与并发编程理论
        并发是指系统能够处理多个任务的能力，这些任务在时间上可以交替执行，给人一种 “同时” 执行的感觉。
        多线程是实现并发的重要手段之一。
        Python 线程是真正的操作系统线程，由操作系统调度，但在执行 Python 字节码时受到全局解释器锁 (GIL) 的限制。
        这意味着 Python 多线程是并发（交替执行），不是并行（同时执行）。

            线程的优势：
                - 特别适用于 I/O 密集型任务，如文件操作或网络请求，因为大部分时间花在等待外部资源上
                - 线程比进程更轻量级，内存需求更低，因为它们共享相同的内存空间

    1.3 全局解释器锁 (GIL) 的影响
        全局解释器锁 (GIL) 是 CPython 解释器中的一个互斥锁，确保同一时刻只有一个线程在执行 Python 字节码。
        GIL 的存在是为了保证 Python 对象的内存管理在多线程环境下的线程安全。

            GIL 的工作原理：
                - 只有持有 GIL 的线程才能操作 Python 对象或调用 Python 的 C API
                - 解释器会定期在字节码指令之间切换线程，以模拟并发效果
                - 在阻塞 I/O 操作（如文件读写）时，GIL 会被释放，允许其他线程执行

            GIL 对性能的影响：
                - 对于 CPU 密集型任务，多线程可能不会带来性能提升，反而由于 GIL 的存在导致性能下降
                - 对于 I/O 密集型任务，多线程依然是一种有效的并发手段

        Python 支持多线程，但 GIL 让多线程在 CPU 密集型任务中无法并行，只能并发

        补充：
            为什么，对于 CPU 密集型任务，多线程可能不会带来性能提升，反而由于 GIL 的存在导致性能下降？

            对于 CPU 密集型任务，在 Python（特指 CPython 解释器）中使用多线程不仅无法带来性能提升，
            反而可能导致性能下降，其根本原因在于 全局解释器锁（GIL） 的限制。
            我们可以从以下三个层面来深度剖析这个现象：
            1. GIL 的“单行道”机制（无法真正并行）
                GIL 本质上是一把互斥锁。
                它强制规定：同一时刻，只能有一个线程在执行 Python 字节码。
                对于 CPU 密集型任务（如复杂的数学计算、图像处理、大循环等），线程需要持续占用 CPU 进行运算。
                由于 GIL 的存在，即使你的电脑拥有 8 核或 16 核 CPU，Python 的多线程也无法让多个计算任务同时在不同核心上运行。
                它们只能在一个核心上“排队”轮流执行，本质上是“伪并行”。
            2. 额外的“过路费”开销（导致性能下降）
                既然无法并行，因为引入了额外的线程切换开销，多线程反而比单线程更慢，因为：
                    抢锁与释放：线程在运行时需要不断争夺 GIL，执行完一小段时间（或遇到 I/O）后又要释放 GIL，
                              这个“抢锁-释放”的过程本身就需要消耗 CPU 资源。
                    上下文切换：操作系统在多个线程之间进行调度和切换时，需要保存和恢复线程的状态（上下文），这也会产生额外的时间成本。
                因此，对于纯计算任务，多线程的总耗时 = 实际计算时间 + 线程切换与抢锁的额外开销。、
                这使得它的表现往往不如没有任何切换开销的单线程，实测中多线程的耗时甚至可能是单线程的 1.1 到 1.5 倍。
            3. 直观对比：为什么 I/O 密集型任务不受影响？
                为了更清晰地理解，我们可以对比一下两种任务类型在 GIL 下的表现：
                任务类型	    典型场景	                    GIL 的影响	                                性能表现
                CPU 密集型	科学计算、图像处理、复杂循环	    线程全程争夺 GIL，无法并行，且有切换开销	        多线程 ≤ 单线程（甚至更慢）
                I/O 密集型	网络爬虫、文件读写、数据库查询	线程在等待 I/O 时会主动释放 GIL，让其他线程执行	多线程 >> 单线程（显著提升）

            如何解决 CPU 密集型任务的并发瓶颈？
            如果你需要在 Python 中高效处理 CPU 密集型任务，建议跳出 threading 模块，采用以下方案：
                - 使用多进程（multiprocessing）： 这是最标准的解决方案。
                        每个进程都有自己独立的 Python 解释器和 GIL，可以真正利用多核 CPU 实现并行计算。
                - 使用 C 扩展或底层库： 像 NumPy、TensorFlow 等库，其底层的繁重计算是用 C/C++ 实现的，
                        在执行这些计算时会主动释放 GIL，从而实现真正的并行。
                - 尝试无 GIL 的解释器： 例如 Jython 或 IronPython，或者关注 Python 3.13 以后实验性的无 GIL 模式。

    1.4 线程同步机制
        Python 提供了多种线程同步原语，用于解决线程间的竞态条件和数据一致性问题：

        基础同步原语：
            Lock（互斥锁）：最基础的锁对象，不属于任何线程，在 Python 中是一个同步原语对象
            RLock（可重入锁）：允许同一线程多次获取锁，用于递归函数场景
            Condition（条件变量）：总是与某种锁关联，允许一个或多个线程等待直到被另一个线程通知
            Semaphore（信号量）：管理一个内部计数器，每个acquire()调用减少计数器，每个release()调用增加计数器
            Event（事件）：最简单的线程间通信机制之一，一个线程发出事件信号，另一个线程等待该事件

        上下文管理器支持：
            从 Python 3.8 开始，Lock、RLock、Condition、Semaphore和BoundedSemaphore对象都可以用作with语句的上下文管理器，
            提供更简洁的锁管理方式。


    2.1 线程创建与启动
        2.1.1 基础线程创建
        创建线程最常见的方式是通过threading.Thread类，指定目标函数和参数

            t = threading.Thread(target=crawl, args=(link,), kwargs={"delay": 2})
            threading.Thread(): 创建线程对象
                - target=crawl: 指定线程要执行的函数是 crawl。
                - args=(link,): 传递位置参数。注意 (link,) 后面的逗号不能少，否则 Python 会把它当成字符串而不是元组。
                - kwargs={"delay": 2}: 传递关键字参数。这里强制将 delay 设置为 2 秒，覆盖了函数定义中的默认值 3 秒。
            t.start(): 启动线程。一旦启动，线程会立即开始运行 crawl 函数。

            t.join(): 这是一个阻塞调用
                主线程（运行主程序的线程）会在这里等待，直到所有子线程（t）都执行完毕。
                如果没有这一步，主线程可能在子线程还没来得及打印结果时就结束了程序。

            线程创建要点：
                - 使用 threading.Thread 类创建线程对象
                - target 参数指定线程要执行的目标函数
                - args 参数以元组形式传递位置参数
                - kwargs 参数以字典形式传递关键字参数
                - 调用 start() 方法启动线程，而不是直接调用 run() 方法
                    - start() = 开启新线程 + 并发
                    - run() = 普通方法调用 + 不开启新线程 + 串行
                    - 想做多线程，必须用 start()！
                    - 直接调用 run() 等于没开线程！

        补充：
            1、 为什么“开始”没有乱，而“结束”乱了？
                代码运行结果中，crawl started for ... 通常是分行显示的，而 crawl ended for ... 却经常连在一起。
                这其实是一个概率问题，并非绝对：
                    Started (开始)：线程启动非常快，通常在 time.sleep() 之前就完成了所有输出。
                            如果主线程调度均匀，它们往往能各自独占一个时间片完成输出。
                    Ended (结束)：所有线程都在同一时刻（大约 2 秒后）从“睡眠”中醒来。
                            此时，多个线程几乎同时争抢 CPU 和 I/O（屏幕输出）资源，冲突（Collision）的概率大大增加。
                可以使用 线程锁(Lock) 或 强制刷新(Flush) 解决该问题

            2、 为什么 print() 不能保证“原子性”？
                多线程并发访问标准输出（print）时产生的竞态条件导致的。
                虽然在 Python 中，单个 print() 语句在代码层面是一行，但在操作系统和控制台（Terminal/Console）的眼里，它其实包含两个步骤：
                    1. 写入内容：将字符串（例如 "crawl ended for https://peps.python.org"）写入标准输出缓冲区。
                    2. 写入换行符：写入 \n（换行符），触发光标回到下一行行首。
                在多线程环境下，线程 A 和线程 B 是由操作系统调度的。当一个线程正在执行第 1 步时，CPU 可能会切换到另一个线程。
                这就导致了执行输出时输出的时序可能出现问题
                情况完全符合多线割的预期行为 "换行符 \n 并不能防止其他线程在它之前插入内容”

            3、 args参数以元组形式传递位置参数的好处是什么?
                1. 保持函数定义的简洁与纯粹
                    使用 args 传参，你的目标函数（target）不需要做任何特殊的修改，只需要按照正常的逻辑定义位置参数即可。
                    相比之下，如果不使用 args，你可能需要通过全局变量传参，或者继承 Thread 类并重写 __init__ 和 run 方法来传递属性，
                    这会让简单的任务变得非常繁琐。
                2. 保证参数传递的顺序与安全性
                    元组（Tuple）是一种不可变序列，且严格保持元素的顺序。
                        - 顺序一致：args 里的元素会严格按照从左到右的顺序，一一映射到目标函数的位置参数上。
                        - 数据安全：因为元组不可变，在线程启动和参数解析的过程中，不会出现参数被意外修改的风险。
                3. 极高的灵活性与兼容性
                    args 完美契合了 Python 函数调用的底层机制（即 func(*args) 的解包形式）。
                        - 任意数量：无论你的函数需要 1 个参数还是 10 个参数，都可以全部打包进一个元组里传递。
                        - 任意类型：元组里可以容纳字符串、数字、列表、字典甚至自定义对象等任意类型的参数。
                        - 混合使用：它还可以和 kwargs（以字典形式传递关键字参数）搭配使用，同时满足位置参数和关键字参数的传递需求。

            补充的补充：
                args=(link,)，当元组中只有一个元素时，末尾的逗号绝对不能省略！
                    - args=(link,)：Python 会将其识别为一个包含 link 的元组，线程启动时能正确解包出 link 传给函数。
                    - args=(link)：如果没有逗号，Python 会把它当作普通的括号运算，最终 args 接收到的只是 link 这个字符串本身。
                            线程在尝试解包字符串时，会把字符串拆成一个个字符，导致参数数量不匹配的报错
                            （例如：crawl() takes 2 positional arguments but 13 were given）

            4、 使用 args/kwargs 和 继承 Thread 类
                - 使用 args/kwargs：就像你拿着一个打包好的包裹（函数）和一张写满地址信息的快递单（参数），
                        直接交给快递员（Thread 类）让他去派送。
                        简单直接，适合单次、零散的任务。
                - 继承 Thread 类：就像你自己成立了一个专门的“快递分部”（自定义类）。
                        你提前把地址、货物、派送要求都录入到分部的系统里（__init__ 初始化属性），
                        然后你的分部里有一套完整的派送流程（run 方法）。
                        这适合长期、复杂、需要高度定制化的派送任务。
                所以，当你觉得简单的 args/kwargs 无法满足你对代码结构、状态管理的需求时，你会主动选择去继承 Thread 类。

            5、 t.join()
                让主线程“原地等待”，直到所有子线程都执行完毕
                1. 核心作用：阻塞当前线程
                    当主线程执行到 t.join() 这行代码时，它会被阻塞（暂停），进入等待状态。
                    主线程会一直停在这里，直到线程 t（子线程）把它的任务全部跑完，主线程才会“苏醒”并继续往下执行后续的代码。
                2. 为什么要用 join()？
                    假设没有这行 for t in threads: t.join()：
                        - 主线程会飞快地启动完所有的子线程（打印完所有的 started）。
                        - 然后主线程会直接走到程序的末尾。
                        - 后果：主程序会直接结束退出。由于主进程都退出了，那些还在后台 sleep 等待的子线程会被强制“杀掉”，
                                导致根本看不到 crawl ended 的输出。
                    加上 join() 后，主线程就会乖乖地在循环里等着每一个子线程把活干完，确保所有任务都能顺利收尾。
                3. 进阶用法：设置超时时间
                    join() 还可以接收一个 timeout 参数（单位是秒）。
                    意思是：“我最多等你这么久，时间一到不管你跑没跑完，我都要继续往下走了”
                        t.join(timeout=2)  # 最多等待子线程 t 2秒钟
                    这在处理一些可能卡死的后台任务时非常有用，可以防止主程序被无限期地挂起

            6、 for 循环并不是让线程“依次执行完毕”，而是“依次等待它们结束”
                1. 线程的“执行”和主线程的“等待”是两码事
                    - 子线程的执行（早已同时发生）：在你之前的代码 for link in links: ... t.start() 中，
                            所有的子线程已经被同时启动了。它们正在后台并发地跑着（比如都在同时 sleep 倒计时）。
                    - 主线程的等待（现在正在发生）：现在的这个 for t in threads: t.join() 循环，约束的仅仅是主线程的行为。
                            它的意思是：主线程走到 t1.join() 时，就停下来盯着 t1，直到 t1 结束；然后主线程再走到 t2.join()，盯着 t2……
                2. 按照加入顺序“等待” ≠ 按照加入顺序“结束”
                    虽然主线程是严格按照 threads 列表里的顺序（加入的顺序）去执行 join() 的，但这完全不影响子线程实际的结束顺序。
                    举个生动的例子：
                    假设（主线程）让三个跑步运动员（子线程 t1, t2, t3）同时起跑。
                        - t1 跑得最慢，需要 10 秒。
                        - t2 跑得最快，只需要 3 秒。
                        - t3 跑得不快不慢，需要 5 秒。
                    for t in threads: t.join() 就像是这样一个流程：
                        - 先盯着 t1（t1.join()）。虽然 t1 跑得最慢，但必须等到第 10 秒它冲过终点，才会移开视线。
                        - 当移开视线去盯着 t2（t2.join()）时，会发现 t2 早在第 3 秒就已经跑完并在终点休息了。
                                所以 t2.join() 会瞬间返回，因为不需要再等了。
                        - 接着你着 t3（t3.join()），同样，t3 在第 5 秒就已经跑完了，所以这里也是瞬间返回。
                    结论就是：
                        - 主线程确实是按照 t1 -> t2 -> t3 的加入顺序去执行“等待”这个动作的。
                        - 但子线程实际跑完（结束）的顺序，依然是看它们自己的速度（t2 -> t3 -> t1），并不会因为你 join 的顺序而改变。
                    总耗时是 “最慢线程的运行时间 + 极其微小的线程创建与切换开销”。
                    但在实际应用中，这个微小的开销几乎可以忽略不计，所以我们通常直接认为总耗时等于最慢的那个任务的时间

        2.1.2 继承 Thread 类方式
            另一种创建线程的方式是继承threading.Thread类并重写run()方法
                class MyThread
            这种方式更适合需要自定义线程行为的场景，可以在run()方法中实现复杂的线程逻辑

            thread.start() ✅（正确用法）:
                - 会创建一个新的线程
                - 在新线程里自动调用 run() 方法
                - 真正实现多线程、并发执行

            thread.run() ❌（错误用法）
                - 不会创建新线程
                - 就在当前主线程直接运行函数
                - 相当于普通函数调用，不是多线程！
                - 会阻塞当前线程

    2.2 线程同步与锁机制
        2.2.1 Lock 基础使用
            Lock是最基础的锁对象，用于保护共享资源，确保同一时间只有一个线程访问
                class Counter

            with self.lock = 加锁作用：同一时间，只有一个线程能执行 count +=1

        补充：
            1、 为什么必须写 with self.lock: 包裹 count +=1？
                count += 1 不是原子操作！不是一步完成！
                在底层会分成 3 步：读取 count 当前的值 -> 计算 值+1 -> 写回 count
                多线程同时执行会产生线程安全问题(数据竞争)，使输出的结果与预期不符(次处计算的值应该低于500000)

                它的作用只有一个：让同一时间，只有一个线程能执行 count +=1

                with 写法是 Python 最安全、最简洁的写法：
                    with self.lock:
                        self.count += 1
                    等价于（但更安全）：
                    self.lock.acquire()  # 加锁
                    self.count += 1
                    self.lock.release()  # 解锁
                with 会自动加锁、自动解锁，就算报错也不会死锁，最安全！

            2、 为什么可以写 100_000？
                100_000 就是 100000，写法不同，数值完全一样！Python 支持在数字里用下划线 _ 做千分位分隔，只是为了好看、好读，不影响计算！
                任何数字都可以加 “_” ,如：
                    1_000_000_000  # 10亿
                    123_456        # 123456
                    0.000_001      # 0.000001

            3、 并发和并行的区别
                - 并发 (Concurrency)：一个核心，快速切换，看上去一起跑，同一时刻只有一个任务在真正执行
                - 并行 (Parallelism)：多个核心，同时干活，同一时刻多个任务真的一起在跑
                1. 并发
                    - 单核 CPU 也能实现
                    - 靠时间片轮转，操作系统不停切换线程 / 任务
                    - 交替执行，宏观一起跑，微观串行
                    - Python 多线程属于并发（受 GIL 限制，同一时刻只有 1 个线程执行）
                2. 并行
                    - 必须多核 CPU
                    - 多个核心同时各自执行一个任务
                    - 微观也是同时执行
                    - Python 多进程可以实现真正并行

                维度	            并发 Concurrency	    并行 Parallelism
                CPU 核心	        单核 / 多核都可以	    必须多核
                同一时刻	        只有 1 个任务运行	    多个任务同时运行
                执行方式	        交替切换、时分复用	    同时独立运行
                形象理解	        一人多活 轮流干	    多人多活 一起干
                Python 体现	    多线程（并发）	        多进程（并行）
